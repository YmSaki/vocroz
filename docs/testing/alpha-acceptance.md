# Alpha 受け入れテストの実機確認手順

この文書は、仕様書の Alpha 受け入れテスト AT-A01〜A17 を Windows の実機で確かめるための手順書です。
CI で確かめられない部分（音出し、デバイスの抜き差し、画面、インストーラー、実回線）を対象にします。
各テストについて、操作の手順、合否の基準、残す証拠を書きます。

仕様書は合格の条件として、ログや測定値などの証拠をそろえることを求めています。
画面のキャプチャや「動いた」という報告だけでは合格にしません。
そのため、どのテストも「何を記録すれば、後から第三者が合否を判断できるか」を先に決めてから操作します。

テストは実施できる環境の順に並べています。

| 区分 | 必要な環境 | テスト |
| --- | --- | --- |
| A. 1 台で確かめる | Windows PC 1 台（と仮想マシン） | AT-A01、A09、A04、A08、A07、A13、A12、A11（署名を除く部分）、追加項目 X1、X2 |
| B. LAN の 2 台で確かめる | 同じ LAN の Windows PC 2 台 | AT-A03、A05、A06、A17、A14、A02 と A16 の予行、A15 |
| C. WAN が要る | 別回線の PC（最終的に子機 3 台）、ランデブーサーバーの VPS | AT-A02、A16 |
| D. 署名が要る | コード署名証明書、署名済みの 2 つのバージョン | AT-A10、A11（Authenticode の部分）、A01 の最終確認 |

区分 A と B は 2026-11-12〜13 の実機確認で行い、C と D は回線と証明書がそろってから行います。

## 1. 準備

### 1.1 機材

| 名前 | 役割 | 条件 |
| --- | --- | --- |
| PC-A | 親機（`remote-pa` の親機モードと `pa-engine`）。区分 B では子機 1 台も兼ねる | Windows 11 x64。USB オーディオインターフェースを 1 台つなぐ（AT-A07 で抜くため） |
| PC-B | 子機（`remote-pa` の子機モード）。複数の子機を `--data-dir` で分けて同時に動かす | Windows 10 22H2 以降か Windows 11 の x64 |
| VM-Clean | クリーン導入の確認用（AT-A01、A12） | 開発ツールを入れていない Windows の仮想マシン。Hyper-V の場合はチェックポイントを取れる状態にする |

PC-A の Windows の既定の出力デバイスは、USB インターフェースではなく内蔵スピーカーなどの別のデバイスにし、音量を上げておきます。
AT-A07 で、デバイスを抜いたときに音が既定のデバイスへ流れたら、すぐに耳で気付けるようにするためです。

### 1.2 確認用の道具

製品には含めず、確認のためだけに使います。

| 道具 | 用途 | 使うテスト |
| --- | --- | --- |
| [clumsy](https://jagt.github.io/clumsy/)（WinDivert、管理者権限） | UDP への遅延、欠損、重複、順序の入れ替え、改ざんの注入 | AT-A06、A17、A15 |
| Wireshark か `pktmon`（Windows 標準） | パケットキャプチャ | AT-A17、A02 |
| 出力の録音（Audacity の WASAPI ループバック、または PC-A の出力を別の機器で録音） | 音切れ、古い音の再生、承認前の無音を波形で残す | AT-A03〜A08、A13、A15 |
| テスト音（子機ごとに周波数の違う正弦波。例: 440 Hz、660 Hz、880 Hz） | どの子機の音かを耳とスペクトルで区別する | AT-A03、A05、A15 |
| Process Explorer か PowerShell の `Get-Process` | メモリとハンドル数の記録 | AT-A15 |
| Windows Sandbox か Hyper-V | クリーンな環境 | AT-A01、A12 |

テスト音は、子機ごとに別の入力（マイク、ライン入力、仮想ケーブル）から入れます。
同じ PC で複数の子機を動かす場合は、仮想ケーブル（VB-CABLE など）を子機ごとに分けると、それぞれに別のテスト音を入れられます。

### 1.3 ビルドとインストール

1. 確認する main のコミットを決め、`git rev-parse --short HEAD` の値を記録する。すべての証拠にこの値を付ける。
2. `installer/README.md` の手順でインストーラーを作る。`out/installer/VOCROZ-Setup-<バージョン>.exe` を PC-A、PC-B、VM-Clean に配る。
3. 区分 A の AT-A11 と区分 D 用に、バージョンだけを変えた 2 つ目のビルドを作る（1.5）。

署名証明書が届くまでのインストーラーは未署名です。
SmartScreen の警告は「詳細情報」→「実行」で進めます。SmartScreen の表示そのものは区分 D で確かめます。

### 1.4 ランデブーサーバー

VPS が用意できるまでは、PC-A でランデブーサーバーを動かします。

```powershell
cd infra/rendezvous
go build ./cmd/rendezvous
.\rendezvous.exe -http :8080 -udp :3478
```

親機と子機の接続先を `http://<PC-A の LAN のアドレス>:8080` と UDP 3478 に向けます。
接続先の設定方法は `pa-engine` と `remote-pa` の組み立て（E1 #21、E2 #22）で決まります。決まったら、この節に追記します。

Windows Defender ファイアウォールの確認が出たら、プライベートネットワークだけを許可します。
VOCROZ はファイアウォールの規則を追加しない設計なので（`docs/adr/0008-runtime-behavior.md`）、確認が出ること自体は不具合ではありません。

### 1.5 更新の確認用の鍵とパッケージ

AT-A10 と A11 では、確認用の Ed25519 の鍵を使います。本番の鍵とは別に作り、確認が終わったら破棄します。

```powershell
cd tools/release
go run . keygen -out $env:USERPROFILE\vocroz-test-update.key   # 表示された公開鍵を控える
```

控えた公開鍵を `-DVOCROZ_UPDATE_PUBLIC_KEY=<公開鍵>` に渡して、旧バージョン（例: 0.1.0）と新バージョン（例: 0.1.1）の 2 つをビルドします。
新バージョンの `vocroz-app-0.1.1.zip` を HTTPS で取得できる場所（GitHub の pre-release など）に置き、マニフェストに署名します。

```powershell
go run . sign -key $env:USERPROFILE\vocroz-test-update.key -version 0.1.1 `
  -url https://<置き場所>/vocroz-app-0.1.1.zip -package ..\..\out\installer\vocroz-app-0.1.1.zip > manifest.txt
```

アプリがマニフェストを取りに行く URL の設定方法は E2 で決まります。決まったら、この節に追記します。

### 1.6 起動のしかた

| 起動するもの | コマンド |
| --- | --- |
| 親機 | スタートメニューの「VOCROZ（親機）」、または `vocroz.exe` |
| 子機 | スタートメニューの「VOCROZ（子機）」、または `vocroz.exe --mode=client` |
| 同じ PC の 2 台目以降の子機 | `vocroz.exe --mode=client --data-dir=%LOCALAPPDATA%\VOCROZ-test\c2`（`c3`、`c4` …と分ける） |
| 詳しいログが要るとき | 上のコマンドに `--log-level=debug` を付ける |
| 更新確認を止めるとき | `--no-update-check`（区分 A、B では基本的に付ける） |

`vocroz.exe` は `%LOCALAPPDATA%\Programs\VOCROZ\` にあります。
単一インスタンスの範囲は「ユーザー × `--data-dir` × モード」なので、`--data-dir` を分ければ同じ PC で複数の子機を起動できます（`docs/adr/0007-launch-interface.md`）。

### 1.7 データの置き場所

| 場所 | 内容 |
| --- | --- |
| `%LOCALAPPDATA%\Programs\VOCROZ\` | インストール先（`vocroz.exe`、`app-<バージョン>\`、`current.txt`） |
| `%LOCALAPPDATA%\VOCROZ\`（`--data-dir` の既定） | `settings.json`、`logs\`、`crash\`、`cache\`、`updates\` |

仕様書は保存先を `%LOCALAPPDATA%\RemotePAConsole\` と書いていますが、`docs/adr/0007-launch-interface.md` の `%LOCALAPPDATA%\VOCROZ\` を正とします。

## 2. 記録のしかた

### 2.1 証拠の置き場所

証拠は PC-A の作業フォルダに、テストごとに分けて置きます。

```text
evidence/<実施日>/<テスト ID>/
  result.md          合否、実施者、コミット、環境、気付いたこと
  logs/              該当時間帯の <data-dir>\logs\ のコピー（親機、各子機）
  recordings/        出力の録音（WAV）
  captures/          パケットキャプチャ（pcapng）
  metrics/           CSV などの測定値
  screens/           画面のキャプチャ（補足。これだけでは証拠にしない）
```

`evidence/` はリポジトリに入れません（`.gitignore` に登録済み）。
ログ、キャプチャ、クラッシュダンプには IP アドレスや音声バッファが含まれうるためです。
Issue #24 には `result.md` の内容と、必要な抜粋だけを貼ります。

### 2.2 `result.md` の書式

```markdown
# AT-Axx <題名>

- 判定: 合格 / 不合格 / 保留（理由）
- 実施日時: 2026-11-12 14:05〜14:20
- コミット: abc1234（remote-pa --version の出力も書く）
- 環境: PC-A Windows 11 23H2 / USB IF <機種> / PC-B Windows 10 22H2、LAN（有線 1 GbE）
- 手順からの逸脱: なし

| 確認 | 結果 | 証拠 |
| --- | --- | --- |
| 手順 3: ホイールで値が変わらない | OK | screens/03-wheel.mp4 |

## 気付いたこと
```

### 2.3 判定と不具合の扱い

- **合格**: すべての確認が基準を満たし、証拠がそろっている。
- **不合格**: 基準を満たさない確認が 1 つでもある。「不具合」テンプレートで Issue を作り、`result.md` に Issue 番号を書く。
- **保留**: 機能が未実装、または道具や環境がなくて確かめられない。何が足りないかを書く。

1 つの不具合につき Issue を 1 つ作ります。
再現手順には、この文書のテスト ID と手順の番号、コミット、`remote-pa --version` の出力、OS のバージョン、デバイス名を書き、該当するログの抜粋を添えます。

区分 A と B の結果は、Issue #24 にテストごとのコメントでまとめます。

## 3. 区分 A: 1 台で確かめる

### AT-A01 クリーン導入

**確かめること**: 開発ツールのないクリーンな Windows x64 にインストーラーで導入でき、WebView2 Runtime が用意され、アプリの一覧に登録されて起動すること。

**手順**

1. VM-Clean のチェックポイントを取る（AT-A12 でも使う）。
2. VM-Clean で WebView2 Runtime の有無を記録する。`HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}`（コンピューター単位）と `HKCU\Software\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}`（ユーザー単位）の `pv` を読む。Windows 11 には標準で入っているので、未導入の場合を確かめるには WebView2 のない Windows 10 の VM を使う。
3. 導入前の状態を記録する（付録 A のスクリプト）。
4. 一般ユーザー（管理者ではないアカウント）でインストーラーを実行する。UAC の昇格を求められないことを確かめる。
5. 導入後に、スタートメニューの「VOCROZ（親機）」と「VOCROZ（子機）」、設定の「インストールされているアプリ」の VOCROZ を確かめる。
6. 両方のショートカットから起動し、それぞれ親機の画面と子機の画面が表示されることを確かめる。
7. `remote-pa --version` をインストール先の `app-<バージョン>\` で実行し、出力を記録する。
8. 導入後の状態を記録し（付録 A）、手順 3 と比べる。

**合否の基準**

- 昇格なしで導入が完了する。
- WebView2 が未導入の環境では導入され、導入済みの環境では導入を飛ばす。
- アプリの一覧とスタートメニューに登録され、両方のモードの画面が表示される。
- 導入後の差分が、インストール先、2 つのショートカット、`HKCU\Software\Classes\vocroz`、アンインストールの登録（と WebView2）だけである。`PATH`、`Run` キー、タスクスケジューラーに追加がない。

**残す証拠**: 導入前後の状態の差分、インストーラーのログ（`%TEMP%\VOCROZ*.log`）、`--version` の出力、両画面のキャプチャ。

### AT-A09 未実装ボタンの無害性

**確かめること**: Beta 以降で実装する機能のボタンを押しても、非モーダルの「開発中」の通知が出るだけで、ウィンドウが開かず、設定と音声が変わらないこと。

対象のボタンは次のとおりです（`ui/src/screens/mixer/MixerScreen.tsx`、`ChannelStripView.tsx`、`ui/src/screens/client/ClientScreen.tsx`）。

| 画面 | ボタン |
| --- | --- |
| 親機のツールバー | ルーティング、録音・再生、仮想オーディオデバイス、VST エフェクト、MIDI・VST 音源、映像 |
| 親機のチャンネルストリップ | FX（各ストリップ） |
| 子機 | 返送モニター |

**手順**

1. 親機と子機（同じ PC で可）を起動し、子機を承認してミュートを解除し、テスト音が出ている状態にする。出力の録音を始める。
2. `settings.json` のハッシュを記録する: `Get-FileHash $env:LOCALAPPDATA\VOCROZ\settings.json`
3. ウィンドウの一覧を記録する: `Get-Process | Where-Object MainWindowTitle | Select-Object Id, ProcessName, MainWindowTitle`
4. 上の表のボタンをすべて 1 回ずつ押す。続けて同じボタンを素早く 5 回押す。
5. 通知が出ている間に、フェーダーとミュートを操作できることを確かめる（モーダルでないこと）。
6. 手順 2 と 3 をもう一度行い、比べる。録音を止める。

**合否の基準**

- どのボタンでも「開発中」の通知だけが出る。通知は同時に 3 件までで、Master のストリップに重ならない。
- 通知が出ている間も他の操作ができる。
- ウィンドウの一覧と `settings.json` のハッシュが変わらない。
- 録音に、ボタン操作の時刻での音量の変化や途切れがない。

**残す証拠**: ウィンドウの一覧とハッシュの前後、操作中の画面の録画、出力の録音。

### AT-A04 フェーダー操作とミュートの独立性

**確かめること**: ドラッグ、数値入力、キーボードで音量が変わり、ホイールでは変わらないこと。子機側と親機側のミュートの理由が区別して表示され、−∞ dB とミュートが区別されること。ミュートと解除を繰り返しても `NO_SIGNAL` の誤判定や古い音の再生が起きないこと。

**手順**

1. 親機と子機 1 台を起動して承認し、両側のミュートを解除する。子機には 1 秒ごとに鳴るクリックか、数を読み上げる声を入れる。出力の録音を始める。
2. チャンネルのフェーダーで次を順に行い、表示の dB 値を記録する。
    - ドラッグ
    - `Ctrl` を押しながらドラッグ（ドラッグより細かく動く）
    - 数値をダブルクリックして `-12.5` を入力し `Enter`
    - フォーカスを当てて `↑` を 2 回（+1.0 dB）、`Shift + ↓` を 3 回（−0.3 dB）
    - フェーダーの上でマウスホイールを回す
3. フェーダーを一番下まで下げ、表示が −∞ dB になり、ミュートの表示（`MUTE`）とは別に見えることを確かめる。
4. 親機でチャンネルをミュートし、表示が `MUTE` になることを確かめる。続けて子機で送信をミュートし、親機のストリップに `子機MUTE` が別に表示されること、親機からは子機のミュートを解除できないことを確かめる。
5. 両方のミュートを解除し、親機側のミュートと解除を 1 秒間隔で 20 回、続けて子機側の送信ミュートと解除を 20 回繰り返す。
6. 録音を止める。親機のログで、手順 5 の時間帯の信号状態の遷移を確かめる。

**合否の基準**

- 手順 2 の操作で、ホイール以外はすべて値が変わり、ホイールでは変わらない。矢印キーは 0.5 dB、`Shift` 付きは 0.1 dB 刻みで変わる。
- −∞ dB とミュート、親機のミュートと子機のミュートが、それぞれ見分けられる。
- 手順 5 の間に `NO SIGNAL` の表示が出ない（子機の送信ミュート中はキープアライブが続くため）。
- 解除した直後の音が、その時点の音である。録音で、ミュート中にクリックや声が溜まって遅れて再生される箇所がない。

**残す証拠**: 手順 2 の値の記録、手順 3〜4 の画面のキャプチャ、出力の録音、手順 5 の時間帯の親機のログ。

### AT-A08 UI のクラッシュの隔離

**確かめること**: 音声の出力中に親機の UI のプロセスを強制終了しても音が止まらず、UI を起動し直すと元のミキサーの状態が正しく表示されること。

**手順**

1. 親機と子機 1 台で音を出す。チャンネルのフェーダーを −6.0 dB、Master を −3.0 dB にし、別のチャンネルがあればミュートにしておく。画面をキャプチャする。出力の録音を始める。
2. WebView のレンダラーだけを終了する。タスクマネージャーの「詳細」で、`remote-pa.exe` の子の `msedgewebview2.exe` を終了する。画面の状態を記録する。
3. `remote-pa.exe` を強制終了する: `taskkill /F /IM remote-pa.exe`。`pa-engine.exe` が残っていることを確かめる: `Get-Process pa-engine`
4. 30 秒待ってから、スタートメニューの「VOCROZ（親機）」で起動し直す。
5. 表示を手順 1 のキャプチャと比べる。フェーダーを 1 つ動かし、音量が変わることを確かめる。録音を止める。

**合否の基準**

- 手順 2〜4 の間、録音に途切れがない。
- 手順 4 で新しい `pa-engine` を起動せず、既存のエンジンにつながる（`pa-engine` のプロセス ID が変わらない）。
- 再表示した値が手順 1 と一致し、その後の操作が反映される。

**残す証拠**: 手順 1 と 5 のキャプチャ、`pa-engine` のプロセス ID の前後、出力の録音、親機のログ（UI の切断と再接続、スナップショットの送信）。

### AT-A07 出力デバイスの抜去

**確かめること**: 音声の出力中に親機の出力デバイスを抜いても、別のスピーカーに勝手に音が出ず、Master がミュートされて警告が出ること。

**手順**

1. 1.1 のとおり、Windows の既定の出力を内蔵スピーカーにし、音量を上げておく。VOCROZ の出力は USB インターフェースを選ぶ。
2. 子機のテスト音を出し、USB インターフェースから音が出ることを確かめる。
3. USB インターフェースのケーブルを抜く。抜いた時刻を記録する。
4. 30 秒待ち、内蔵スピーカーから音が出ないこと、画面の表示を確かめる。
5. USB インターフェースを挿し直す。挿しただけでは音が出ないことを確かめる。
6. 画面で出力先を選び直し、Master のミュートを解除して音が戻ることを確かめる。
7. 同じ手順を、手順 3 で「サウンドの設定」からデバイスを無効にする方法でも行う。

**合否の基準**

- 抜いた後、内蔵スピーカーを含め、どのデバイスからも音が出ない。
- Master が `SAFETY MUTE` になり、画面上部のデバイスの警告が出続ける。
- 挿し直しただけでは Master のミュートが解除されない。操作者が選び直して初めて音が出る。
- エンジンも UI も落ちない。

**残す証拠**: 抜いた時刻と画面の録画、親機のログ（デバイスの抜去の検知と Master の安全ミュート）、内蔵スピーカーの出力の録音（WASAPI ループバックで無音であること）。

### AT-A13 設定の破損と初期ミュートでの起動

**確かめること**: 設定の保存中に強制終了したり、壊れた設定ファイルを置いたりしても、バックアップか安全な初期状態（全ミュート）で起動し、前回音が出ていた状態でも、起動し直した直後にいきなり音が出ないこと。

**手順**

1. 親機と子機 1 台で音を出し、Master とチャンネルのミュートを解除した状態にする。
2. **保存中の強制終了**: フェーダーを動かし続けながら、別の PowerShell で次を実行する。保存のタイミングに当たるように、終了する時刻をずらしながら 20 回繰り返す。

    ```powershell
    1..20 | ForEach-Object {
      Start-Sleep -Milliseconds (Get-Random -Minimum 200 -Maximum 1500)
      taskkill /F /IM pa-engine.exe
      Read-Host "$_ 回目: 画面からエンジンを再起動し、無音と全ミュートを確かめてから Enter"
    }
    ```

    エンジンは自動では再起動しないので（X2）、毎回画面の操作で再起動する。起動直後に音が出ていないこと、画面が全ミュートであることを確かめ、手でミュートを解除してから次の回に進む。
3. **壊れた設定ファイル**: 親機を終了し、`settings.json` を退避してから、次の 4 通りで 1 回ずつ起動する。
    - 中身が空のファイル
    - 途中で切れた JSON（元のファイルの前半だけ）
    - JSON ではないバイト列（`[byte[]](1..255) | Set-Content -AsByteStream`）
    - `settings.json` を削除し、バックアップだけを残す
4. 各回で、起動直後の音、ミュートの状態、バックアップからの復元の案内を確かめる。
5. 退避した `settings.json` を戻す。

**合否の基準**

- どの回でも、起動直後に音が出ない。チャンネル、Master、子機の送信がすべてミュートで始まる。
- 壊れた設定ファイルでは、バックアップから読み込むか、初期状態で起動して復元を案内する。起動に失敗したり、エラーのダイアログで止まったりしない。
- 強制終了を 20 回繰り返しても、`settings.json` とバックアップの両方が壊れた状態にならない。

**残す証拠**: 各回の起動直後の出力の録音（無音）、画面のキャプチャ、親機のログ（設定の読み込みの結果）、壊したファイルそのもの。

### AT-A12 アンインストールと再導入

**確かめること**: 「設定を保持して削除」の後に再導入すると設定が引き継がれ、「データをすべて削除」の後に再導入すると初期状態に戻ること。レジストリや `PATH` にごみが残らないこと。

**手順**

1. VM-Clean を AT-A01 の導入後の状態にする。付録 A で状態を記録する（記録 1）。
2. 親機を起動し、出力デバイスの選択、ウィンドウの位置とサイズなど、保存される設定を変えて終了する。`settings.json` のハッシュを記録する。
3. アプリの一覧からアンインストールし、「設定とログを保持する」を選ぶ。
4. インストール先が残っていないこと、`%LOCALAPPDATA%\VOCROZ\` が残っていることを確かめる。付録 A で状態を記録する（記録 2）。
5. 再導入して起動し、手順 2 の設定が引き継がれていることを確かめる。
6. アンインストールし、「すべてのアプリデータを削除する」を選ぶ。確認の画面が出ることを確かめてから削除する。
7. インストール先と `%LOCALAPPDATA%\VOCROZ\` の両方がないことを確かめる。付録 A で状態を記録する（記録 3）。
8. 再導入して起動し、初期状態であることを確かめる。
9. 追加の確認: セッションの稼働中にアンインストールを始め、確認が出ることを確かめる（`docs/adr/0013-installer-and-updater.md`）。

**合否の基準**

- 手順 5 で設定が引き継がれ、手順 8 で初期状態になる。
- 記録 3 と、導入前の記録（AT-A01 の手順 3）との差分が、WebView2 Runtime だけである。`HKCU\Software\Classes\vocroz`、アンインストールの登録、ショートカット、`PATH`、`Run` キーが残らない。
- 記録 2 と導入前の記録の差分が、`%LOCALAPPDATA%\VOCROZ\` だけである。

**残す証拠**: 記録 1〜3 と導入前の記録の差分、`settings.json` のハッシュ、手順 6 と 9 の画面のキャプチャ。

### AT-A11 不正な更新の拒否とロールバック（署名を除く部分）

**確かめること**: 署名が違う、または破損した更新ファイルを与えると更新を拒否し、元のバージョンが壊れずに起動できること。
ここでは、Ed25519 のマニフェストの署名と SHA-256、起動確認によるロールバックを確かめます。Authenticode の検証は区分 D で行います。

**手順**

1. 1.5 の旧バージョン（0.1.0）を導入する。`current.txt` の内容と、`app-0.1.0\` のファイルのハッシュを記録する。
2. 次の不正なマニフェストとパッケージを 1 つずつ用意し、それぞれで `pa-updater.exe --check` を実行して終了コードを記録する。マニフェストの置き場所は 1.5 のとおり。
    | 番号 | 用意のしかた | 期待する結果 |
    | --- | --- | --- |
    | 2-1 | 別の鍵（`keygen` で作り直した鍵）で署名したマニフェスト | 拒否 |
    | 2-2 | 正しく署名したマニフェストの `version` を書き換えたもの | 拒否 |
    | 2-3 | 正しいマニフェストのまま、ZIP の途中の 1 バイトを書き換えたパッケージ | 21（検証に失敗してパッケージを破棄） |
    | 2-4 | 現在より古いバージョン（0.0.9）を正しく署名したマニフェスト | 拒否（ダウングレードの防止） |
    | 2-5 | `url` が `http://` のマニフェスト | 拒否 |
3. **起動確認のロールバック**: `--version` で別のバージョンを返す `remote-pa.exe`（例: 0.1.0 のファイル）を入れた 0.1.1 のパッケージを作り、正しく署名する。セッションのない状態で `pa-updater.exe --check`、続けて `pa-updater.exe --apply` を実行し、終了コードを記録する。
4. 各回の後で、`current.txt` と `app-0.1.0\` のハッシュが手順 1 と同じであること、`app-0.1.1\` が残っていないこと、`<data-dir>\updates\` に不正なパッケージが残っていないことを確かめる。
5. スタートメニューから起動し、0.1.0 が正常に動くことを確かめる。

**合否の基準**

- 2-1〜2-5 はすべて拒否され、何も適用されない。
- 手順 3 の `--apply` は終了コード 22 で終わり、`current.txt` が切り替わらず、設定がバックアップから戻っている。
- どの回の後でも 0.1.0 が起動する。

**残す証拠**: 各回の終了コードと `pa-updater` のログ、`current.txt` とハッシュの前後、用意した不正なマニフェスト。

### X1 セッション中のスリープの抑止（`docs/adr/0008-runtime-behavior.md` の追加項目）

**手順**

1. 電源の設定で、スリープまでの時間を 1 分にする。
2. セッションを作り、子機 1 台を接続して音を出したまま 5 分待つ。管理者の PowerShell で `powercfg /requests` を実行し、`SYSTEM` の欄に `pa-engine.exe` があることを記録する。
3. セッションを終了し、2 分以内にスリープに入ることを確かめる。`powercfg /requests` に `pa-engine.exe` が残っていないことを確かめる。
4. 電源の設定を元に戻す。

**合否の基準**: セッションの稼働中はスリープに入らず、終了後は抑止が解除される。画面のスリープは抑止しない。

**残す証拠**: 手順 2 と 3 の `powercfg /requests` の出力。

### X2 エンジンの異常終了と再起動（`docs/adr/0008-runtime-behavior.md` の追加項目）

**手順**

1. 親機と子機 1 台で音を出し、ミュートをすべて解除した状態にする。
2. `taskkill /F /IM pa-engine.exe` を実行する。
3. 親機の画面にエンジンの停止の通知が出ること、自動で再起動しないことを確かめる。
4. 画面の操作でエンジンを再起動し、全チャンネルと Master がミュートで始まることを確かめる。

**合否の基準**: 停止が通知され、自動では再起動しない。再起動後は全ミュートで始まり、操作するまで音が出ない。

**残す証拠**: 画面の録画、再起動直後の出力の録音、親機のログ。

## 4. 区分 B: LAN の 2 台で確かめる

この区分の構成は次のとおりです。

| PC | 動かすもの |
| --- | --- |
| PC-A | ランデブーサーバー（1.4）、親機、子機 C1（`--data-dir=...\c1`） |
| PC-B | 子機 C2、C3（AT-A15 では C2〜C8） |

### AT-A03 3 台の同時ミックス

**確かめること**: 子機 3 台を承認し、両側のミュートを解除すると、親機の各フェーダーとミュートが独立して働き、物理デバイスからミックスして出力されること。

**手順**

1. 親機でセッションを作り、招待コードを C1〜C3 に入れて参加を申請する。
2. 3 台を承認する。C1〜C3 にそれぞれ 440 Hz、660 Hz、880 Hz のテスト音を入れる。出力の録音を始める。
3. 子機側の送信ミュート、親機側のチャンネルのミュート、Master のミュートをすべて解除する。
4. C2 のフェーダーだけを −20 dB にし、続けて C3 だけをミュートする。各操作の時刻を記録する。
5. 録音を止め、スペクトルで 3 つの周波数の音量の変化を確かめる。

**合否の基準**

- 3 つのテスト音が同時に出力される。
- 手順 4 の操作は、対象のチャンネルの周波数だけを変える。他のチャンネルの音量は変わらない。
- 親機の各ストリップのメーターが、対応する子機の音に合わせて動く。

**残す証拠**: 出力の録音とスペクトルの画像、操作の時刻、親機のログ（3 台の承認と信号状態）。

### AT-A05 切断と同じチャンネルへの復帰

**確かめること**: 3 台のうち 1 台を切断しても残り 2 台の音が途切れず、120 秒以内に再接続するとチャンネルが増えずに元のストリップに戻ること。

**手順**

1. AT-A03 の手順 3 の状態にし、出力の録音を始める。ストリップの並びとチャンネル名を記録する。
2. **回線の切断**: PC-B のネットワークアダプターを無効にする（`Disable-NetAdapter -Name <名前>`、管理者権限）。C2 と C3 の両方が切れるので、C1 の音が途切れないことを確かめる。
3. 60 秒後にアダプターを有効に戻し、C2 と C3 が元のストリップに戻ることを確かめる。
4. **プロセスの終了**: `taskkill /F` で C3 だけを終了し、90 秒後に同じ `--data-dir` で起動し直す。
5. **猶予切れ**: C3 を終了し、130 秒待つ。ストリップが `LOST` になり、位置を保ったまま残ることを確かめる。そのあと C3 を起動し直したときの振る舞いを記録する。
6. 録音を止める。

**合否の基準**

- 手順 2〜5 の間、切断していない子機の音が途切れない。
- 切断した子機のストリップは、5 秒ほどで `RECONNECTING` になる。
- 120 秒以内の再接続では承認なしで元のストリップに戻り、ストリップの数が増えない。フェーダーとミュートの設定も元のまま。
- 120 秒を過ぎると `LOST` になり、ストリップは操作者が削除するまで残る。

**残す証拠**: 出力の録音、各手順の画面のキャプチャ（ストリップの数と並び）、親機のログ（`RECONNECTING`、`LOST` への遷移と、再接続した参加者の ID）。

### AT-A06 悪条件のネットワークへの耐性

**確かめること**: パケットの順序の入れ替え、重複、欠損、ジッターを人工的に入れてもクラッシュせず、500 ms 以上の途絶で `NO_SIGNAL`（無音）になり、古い音が遅れて再生され続けないこと。

障害は PC-B の clumsy で、子機から親機へ向かう UDP に入れます。
フィルターは `udp and outbound and ip.DstAddr == <PC-A のアドレス>` とします。ランデブーサーバーへの UDP も同じアドレスに向かうので、ポートで分ける場合は `Get-NetUDPEndpoint -OwningProcess (Get-Process pa-engine).Id` でエンジンのポートを調べます。

**手順**

1. 親機と C2 で音を出し、C2 には数を読み上げる声かクリックを入れる。出力の録音を始める。
2. 次の条件を 1 つずつ 2 分間入れ、各条件の間に 30 秒の正常な時間を挟む。
    | 番号 | clumsy の設定 |
    | --- | --- |
    | 2-1 | Out of order 10% |
    | 2-2 | Duplicate 10%（2 回） |
    | 2-3 | Drop 5%、続けて 20% |
    | 2-4 | Lag 0〜40 ms のゆらぎ（Lag 20 ms と Throttle 10 ms を組み合わせる） |
    | 2-5 | 上の 4 つを同時に |
3. **途絶**: Drop 100% を 0.3 秒、0.6 秒、3 秒、10 秒の 4 回入れる。
4. **遅れて届く**: Lag 2000 ms を 10 秒間入れてから外す。
5. 録音を止める。

**合否の基準**

- どの条件でも、エンジンと子機が落ちない。
- 2-1〜2-5 で音が続く（欠損や揺らぎによる音質の低下はあってよい）。
- 手順 3 の 0.6 秒以上の途絶で `NO SIGNAL` が表示され、出力が無音になる。0.3 秒では `NO SIGNAL` にならない。
- 途絶が明けた後、途絶中の音が遅れて再生されず、すぐにその時点の音に戻る。
- 手順 4 の後、遅延が溜まったままにならず、数秒で元の遅延に戻る。

**残す証拠**: 出力の録音、clumsy の設定と時刻の記録、親機のログ（信号状態の遷移、破棄したパケットの統計）。

### AT-A17 伝送の暗号化と改ざんの検出

**確かめること**: パケットキャプチャで、音声と制御のどちらも平文が流れていないこと。改ざんやリプレイしたパケットが復号の段階で破棄され、音声やセッションの状態に影響しないこと。

**手順**

1. C2 の表示名を、他に現れない文字列（例: `CANARY-7Q2X`）にする。
2. PC-A で、管理者の PowerShell からキャプチャを始める。

    ```powershell
    pktmon filter add -t UDP
    pktmon start --capture --pkt-size 0 -f captures\a17.etl
    ```

3. C2 の参加の申請、承認、ミュートの解除、30 秒の音出し、ミュート、切断を行う。
4. `pktmon stop` の後、`pktmon etl2pcap captures\a17.etl -o captures\a17.pcapng` で変換する。
5. Wireshark で開き、`frame contains "CANARY-7Q2X"` で検索する。ランデブーサーバーとの HTTP を除いた UDP のペイロードに、表示名、招待トークン、Opus として解釈できる平文がないことを確かめる。
6. **改ざん**: PC-B の clumsy で Tamper 10% を 1 分間入れる。
7. **リプレイ**: clumsy で Duplicate 50%（5 回）を 1 分間入れる。キャプチャから取り出した過去の数パケットを送り直せる道具（Q1 #23 の障害注入プロキシなど）があれば、5 分前のパケットも送り直す。

**合否の基準**

- 手順 5 で、UDP のペイロードに平文の表示名やトークンが見つからない。
- 手順 6 と 7 の間、改ざんや重複したパケットが破棄され、音は欠損として扱われる（雑音が出ない）。
- 手順 6 と 7 で、接続状態、承認状態、ミュートの状態が変わらない。

LAN の確認では、ランデブーサーバーとの通信が HTTP なので、招待 API の本文は平文で流れます。これは確認の構成によるもので、この項目の対象外とします。HTTPS の確認は区分 C で行います。

**残す証拠**: pcapng ファイル（区分 A、B の証拠と同じく、リポジトリには入れない）、手順 5 の検索結果のキャプチャ、親機のログ（認証に失敗して破棄したパケットの統計）。

### AT-A14 権限とセキュリティの検証

**確かめること**: 改ざんした子機から Master の音量を変えるコマンドを送っても、エンジンが拒否すること。期限切れや拒否済みの招待コードで、もう一度入れないこと。

**手順**

1. **改ざんした子機**: 承認済みの子機の立場で Master の音量を変える制御メッセージを送る。送る道具は Q1（#23）の結合テストの道具を使う。道具がなければ、この確認は保留とし、CI の結合テストの結果を参照先として書く。
2. **期限切れの招待**: 招待を発行し、有効期限（30 分）が過ぎてから子機で使う。
3. **取り消した招待**: 招待を発行して取り消し（または新しい招待で置き換え）、古いコードを子機で使う。
4. **拒否した参加者**: 子機の参加を拒否した後、同じ子機が同じ招待コードで申請し直したときの振る舞いを記録する。
5. **終了したセッション**: セッションを終了した後、そのセッションの招待コードを使う。
6. **名前付きパイプ**: 親機のユーザーで `[System.IO.Directory]::GetFiles('\\.\pipe\') | Select-String -SimpleMatch vocroz` を実行してパイプの名前を調べる。PC-A の別の Windows ユーザーで、そのパイプに接続を試みる。

    ```powershell
    $pipe = [System.IO.Pipes.NamedPipeClientStream]::new('.', '<パイプの名前>', 'InOut')
    $pipe.Connect(2000)   # UnauthorizedAccessException になることを確かめる
    ```

**合否の基準**

- 手順 1 で Master の音量が変わらず、エンジンのログに拒否が記録される。
- 手順 2、3、5 で参加できず、子機に原因（`招待の有効期限が切れています`、`招待は取り消されました` など）が表示される。
- 手順 4 で、操作者がもう一度承認しない限り音が届かない。
- 手順 6 で接続が拒否される。

**残す証拠**: 子機の画面のキャプチャ、親機のログ、ランデブーサーバーの出力。

### AT-A02 の予行（LAN での接続と承認前の遮断）

本番の確認は区分 C で行います。LAN では、承認前に音が届かないことを先に確かめます。

**手順**

1. 出力の録音を始める。C2 にテスト音を入れ、子機の送信ミュートを解除してから参加を申請する。
2. 親機の承認待ちの一覧に C2 が出たら、承認せずに 60 秒待つ。この間、親機のチャンネルのミュートと Master のミュートを解除できる範囲で解除しておく。
3. C2 を承認し、ミュートを解除して音が出ることを確かめる。

**合否の基準**: 手順 2 の間、出力は無音で、C2 に対応するメーターが動かない。承認した後で初めて音が出る。

**残す証拠**: 出力の録音、親機のログ（承認前に届いた音声パケットの扱い）。

### AT-A16 の予行（接続できないときの表示）

本番の確認は区分 C で行います。LAN では、ファイアウォールで UDP を止めて、接続できない状態を作ります。

**手順**

1. PC-A の管理者の PowerShell で、エンジンの UDP の受信を止める規則を一時的に追加する。

    ```powershell
    New-NetFirewallRule -DisplayName "VOCROZ-A16-test" -Direction Inbound -Protocol UDP `
      -Program "$env:LOCALAPPDATA\Programs\VOCROZ\app-<バージョン>\pa-engine.exe" -Action Block
    ```

2. C2 で参加を申請し、両側の表示を記録する。
3. 規則を削除する: `Remove-NetFirewallRule -DisplayName "VOCROZ-A16-test"`

**合否の基準**: 「接続済み」と表示されない。子機に原因別のエラー（`親機に接続できません…` など）と対処案が表示され、親機にも接続できなかったことが分かる。

**残す証拠**: 両側の画面のキャプチャ、両側のログ。

### AT-A15 長時間と負荷の試験

**確かめること**: 子機 8 台の同時接続で 30 分、子機 3 台以上で 4 時間の連続稼働を完走し、メモリリークやエンジンのデッドロックが起きないこと。

LAN の 2 台で行い、WAN の代わりに clumsy で揺らぎと欠損を入れます。別回線の子機がそろったら、区分 C でも同じ測定をします。

**手順**

1. **8 台・30 分**: C1（PC-A）と C2〜C8（PC-B）を接続し、すべて承認してミュートを解除する。PC-B の clumsy で Lag 20 ms、Drop 1% を入れる。
2. **4 時間**: C1〜C3 で 4 時間動かす。clumsy で Lag 0〜40 ms のゆらぎと Drop 2% を入れ、1 時間ごとに 10 秒間 Drop 100% を入れる。
3. どちらの試験でも、PC-A で次のスクリプトを動かし、1 分ごとにエンジンの状態を記録する。

    ```powershell
    $out = "metrics\a15-$(Get-Date -Format yyyyMMdd-HHmm).csv"
    while ($true) {
      Get-Process pa-engine, remote-pa -ErrorAction SilentlyContinue |
        Select-Object @{n='time';e={Get-Date -Format o}}, ProcessName, Id,
          @{n='private_mb';e={[math]::Round($_.PrivateMemorySize64/1MB,1)}},
          HandleCount, @{n='threads';e={$_.Threads.Count}},
          @{n='cpu_s';e={[math]::Round($_.CPU,1)}} |
        Export-Csv $out -Append -NoTypeInformation
      Start-Sleep 60
    }
    ```

4. 試験の間、出力の録音を続ける。15 分ごとに、任意のチャンネルのミュートと解除を 1 回行い、すぐに反映されることを確かめる。
5. 終了時に、全チャンネルの音が出ていること、画面の操作が反映されることを確かめる。

**合否の基準**

- 試験の間、エンジン、UI、子機のどれも落ちず、応答が止まらない。
- 15 分ごとの操作がすぐに反映される（デッドロックがない）。
- 開始から 10 分後と終了時を比べて、`private_mb` が 10% 以上増え続けていない。`HandleCount` と `threads` が増え続けていない。この数値は目安で、増え方が一定の傾きで続く場合は不合格とする。
- 終了時に、全チャンネルの音が出ている。

**残す証拠**: `metrics\` の CSV とそのグラフ、出力の録音（4 時間分は区切ってよい）、親機のログ、clumsy の設定。

## 5. 区分 C: WAN が要るテスト

ランデブーサーバーを VPS で動かし、HTTPS で公開してから行います。
子機は、親機と別の回線（別の家庭用回線、モバイル回線のテザリングなど）につなぎます。

### AT-A02 WAN での接続と承認前の遮断

**確かめること**: 親機でセッションを作り、別のネットワークの子機が招待コードで接続できること（親機への直結と UDP ホールパンチングの両方の経路で）。親機が承認するまで、音声がまったく届かないこと。

**手順**

1. **直結**: 親機のルーターで UPnP を有効にするか、ポートを手動で転送し、親機が外から届く状態にする。区分 B の「AT-A02 の予行」の手順を、別回線の子機で行う。
2. **ホールパンチング**: ルーターの UPnP とポート転送を無効にして、同じ手順を行う。
3. どちらの経路でつながったかを、親機と子機のログで確かめる。
4. 子機側と親機側でパケットキャプチャを取り、承認前に子機から音声パケットが送られていないか、送られていても親機で破棄されていることを確かめる。

**合否の基準**: 両方の経路で接続できる。どちらの経路でも、承認前は出力が無音で、承認した後で初めて音が出る。

**残す証拠**: 両経路のログ（経路の記録）、出力の録音、キャプチャ、両側の回線の種類（NAT の種類が分かればそれも）。

### AT-A16 NAT 越えが成立しないときの表示

**確かめること**: 対称型 NAT 同士など接続できない環境で、「接続済み」と誤って表示されず、原因別のエラーコードと対処案が表示されること。

**手順**

1. 親機と子機の両方を、対称型 NAT になりやすい回線（キャリアグレード NAT のモバイル回線など）につなぐ。親機の UPnP とポート転送は使わない。STUN でサーバーから見えるアドレスを 2 つの宛先で比べ、対称型であることを確かめておく。
2. 子機で参加を申請し、両側の表示を記録する。
3. 親機の回線を家庭用回線に戻し、ポートを転送して接続できることを確かめる（対処案どおりに解決できること）。

LAN では Q1（#23）が Linux のネットワーク名前空間で NAT の種類を模擬した結合テストを持つので、その結果も参照先として書きます。

**合否の基準**: 手順 2 で「接続済み」と表示されない。両側に原因別のエラーコードと対処案が表示される。手順 3 で対処案どおりにつながる。

**残す証拠**: 両側の画面のキャプチャ、ログ、各回線の STUN の結果。

### 区分 C で測り直すもの

- AT-A17 の手順 5 を、HTTPS のランデブーサーバーで行い、招待 API の本文も平文で流れないことを確かめる。
- AT-A15 を別回線の子機 3 台で行う（4 時間）。8 台の 30 分は、別回線の台数が足りなければ、LAN の結果と clumsy の設定を証拠とする。

## 6. 区分 D: 署名が要るテスト

更新マニフェストの `publisher` に証明書の名前を入れ、Authenticode の検証を有効にします（`docs/adr/0013-installer-and-updater.md`）。

### AT-A01 の最終確認

署名したインストーラーで AT-A01 を行い、SmartScreen の表示と、インストーラーと実行ファイルのデジタル署名（ファイルのプロパティの「デジタル署名」）を記録します。

### AT-A10 実際の更新と本番中の保護

**確かめること**: 署名した旧バージョンから新バージョンへ、アプリ内で更新できること。セッションの稼働中は、更新の通知が来ても音が止まらず、セッションの終了後にだけ更新が適用されること。

**手順**

1. 署名した旧バージョン（0.1.0）を導入する。`current.txt` を記録する。
2. 新バージョン（0.1.1）のマニフェストを公開する。
3. 親機でセッションを作り、子機 1 台で音を出す。出力の録音を始めてから、親機を `--no-update-check` なしで起動し直すか、更新の確認を待つ。
4. 「更新版 0.1.1 が利用可能です。セッションの終了後に適用できます」の表示を確かめる。更新のボタンを押しても、セッションの終了後に適用する旨の通知だけが出ることを確かめる。
5. セッションの稼働中に `pa-updater.exe --apply` を直接実行し、終了コードが 20 であること、何も変わらないことを確かめる。
6. セッションを終了し、更新して再起動する。
7. `remote-pa --version` が 0.1.1 を返すこと、`current.txt` が 0.1.1 と直前の 0.1.0 を指すこと、設定が引き継がれていることを確かめる。

**合否の基準**: 手順 3〜5 の間、録音に途切れがない。セッション中は更新が適用されず、終了後に適用される。更新後に 0.1.1 が起動し、設定が残っている。

**残す証拠**: 出力の録音、手順 4 の画面のキャプチャ、手順 5 の終了コード、`current.txt` の前後、`pa-updater` のログ。

### AT-A11 の Authenticode の部分

## 7. 参考の測定: 遅延と音切れ

受け入れテストの一覧にはありませんが、合奏の用途で必須の低遅延を確かめるため、区分 B の間に次の値を測ります。

- **端から端までの遅延**: PC-B の子機の入力に、PC-A の別の出力からクリックを入れる。クリックの元の信号と VOCROZ の出力を同じ録音機器の 2 チャンネルで録り、時間差を測る。LAN で 10 回測り、中央値と最大値を記録する。Q1（#23）の遅延の計測ツールができていれば、それを使う。
- **音切れ**: 正常な LAN で 30 分の出力を録音し、途切れの回数を数える。エンジンのログの XRUN の数も記録する。仕様書の目標は 30 分あたり 1 回以下。
- **操作の応答**: ミュートを 20 回押し、操作から ACK を受けて表示が変わるまでの時間を、UI のログか画面の録画で測る。仕様書の目標は p95 で 100 ms 以内。

## 付録 A. 導入前後の状態の記録

AT-A01 と A12 で、導入とアンインストールの前後に実行し、出力を比べます。次の内容を `state.ps1` として保存し、`.\state.ps1 -Out <ファイル名>` で実行します。

```powershell
param([string]$Out = "state-$(Get-Date -Format yyyyMMdd-HHmmss).txt")
& {
  "## インストール先とデータ"
  Get-ChildItem "$env:LOCALAPPDATA\Programs\VOCROZ", "$env:LOCALAPPDATA\VOCROZ" -Recurse -ErrorAction SilentlyContinue |
    Select-Object -ExpandProperty FullName
  "## スタートメニュー"
  Get-ChildItem "$env:APPDATA\Microsoft\Windows\Start Menu\Programs" -Recurse -Filter *VOCROZ* |
    Select-Object -ExpandProperty FullName
  "## URL スキーム"
  reg query HKCU\Software\Classes\vocroz /s 2>&1
  "## アンインストールの登録"
  Get-ChildItem HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall |
    Get-ItemProperty | Where-Object DisplayName -Match 'VOCROZ|WebView2' |
    Select-Object DisplayName, DisplayVersion, PSChildName
  "## PATH（ユーザー）"
  [Environment]::GetEnvironmentVariable('Path', 'User')
  "## Run キー"
  Get-ItemProperty HKCU:\Software\Microsoft\Windows\CurrentVersion\Run
  "## タスクスケジューラー"
  Get-ScheduledTask | Where-Object TaskName -Match 'VOCROZ' | Select-Object TaskName
  "## ファイアウォールの規則"
  Get-NetFirewallApplicationFilter -ErrorAction SilentlyContinue |
    Where-Object Program -Match 'VOCROZ' | Select-Object Program
} *>&1 | Out-File -Encoding utf8 $Out
```

2 つの記録の差分は `Compare-Object (Get-Content 前.txt) (Get-Content 後.txt)` で取ります。
