# SRTP 外部出力の相互接続試験の手順

この文書は、SRTP 外部出力（Issue #31、`docs/adr/0040-srtp-external-output.md`）を、外部の受信機と組み合わせて Windows の実機で確かめるための手順書です。
CI では、送ったパケットを libsrtp の受信側で復号する単体テストで、RTP と SRTP の形式を確かめています。
この手順書では、CI で確かめられない部分（実際の受信機での復号と再生、実回線、保存した鍵の復元、パケットが暗号化されていること）を対象にします。

仕様書の Beta2 の合格条件のうち、外部出力の項目はこの試験が終わるまで未達のままです。

## 1. 準備

### 1.1 機材

| 名前 | 役割 | 条件 |
| --- | --- | --- |
| PC-A | 親機（`remote-pa` の親機モードと `pa-engine`） | Windows 11 x64。ルーティングで USER のバスを 1 本以上作れる状態にする |
| RX | 受信機 | 次の 1.2 のどれか。PC-A と同じ LAN に置く（実回線の確認は 3.6） |

### 1.2 受信機

外部の放送機器やメディアサーバーを手配できるまでは、SRTP に対応したソフトウェアの受信機で代わりに確かめます。
どれも、SDP（RFC 4566）の `a=crypto` の行で鍵を受け取れます。

| 受信機 | 用途 |
| --- | --- |
| 手配した放送機器かメディアサーバー | 最終の合否の判定。機種、ファームウェアのバージョン、設定画面の値を記録する |
| FFmpeg の `ffplay`（SDP ファイルを開く） | 手配できるまでの代わり。耳で確かめ、ログに復号の失敗が出ないことを見る |
| GStreamer（`udpsrc ! srtpdec ! rtpopusdepay ! opusdec`） | 手配できるまでの代わり。認証の失敗の数をログで見られる |

受信機に設定する SDP の例を次に示します。`<鍵>` は 2.2 で作った鍵（`inline:` に続く Base64）、`111` は画面のペイロードタイプ、`opus/48000/2` はプロファイルがモノラルでも `/2` のままにします（RFC 7587 では、Opus の `rtpmap` は常に 48000 Hz、2 チャンネルと書く）。

```text
v=0
o=- 0 0 IN IP4 0.0.0.0
s=VOCROZ external output
c=IN IP4 0.0.0.0
t=0 0
m=audio 5004 RTP/SAVP 111
a=rtpmap:111 opus/48000/2
a=fmtp:111 stereo=1; sprop-stereo=1
a=ptime:5
a=crypto:1 AES_CM_128_HMAC_SHA1_80 inline:<鍵>
```

`ffplay` の場合は `ffplay -protocol_whitelist file,udp,rtp external.sdp` で開きます。

### 1.3 確認用の道具

| 道具 | 用途 |
| --- | --- |
| Wireshark か `pktmon`（Windows 標準） | パケットのキャプチャ。暗号化されていること、ペイロードタイプ、マーカービット、送信の間隔を見る |
| 受信機の出力の録音（Audacity など） | 試験音と本番の音を波形で残す |
| テスト音（Master かバスに流す正弦波。例: 440 Hz） | 接続テストの 1 kHz と区別する |

### 1.4 記録すること

- 確認する main のコミット（`git rev-parse --short HEAD`）。すべての証拠にこの値を付ける
- 受信機の種類、バージョン、設定（宛先のポート、ペイロードタイプ、暗号スイート）
- 試験ごとの画面の「状態」と「直前の結果」、受信機のログ、キャプチャのファイル、録音

鍵そのものは証拠に残しません。試験に使った鍵は試験の後に作り直します。

## 2. 設定

### 2.1 宛先と送り出すバス

1. ミキサー画面のツールバーの「外部出力」を押し、右側のパネルを開く。状態が「停止中」であることを確かめる。
2. 宛先に RX の IP アドレス、ポートに受信機のポート（既定 5004）を入れる。
3. 送り出すバス（Master か、ルーティングで適用したバス）、コーデック（Opus ステレオかモノラル）、ペイロードタイプ（既定 111）、暗号スイート（既定 `AES_CM_128_HMAC_SHA1_80`）を選ぶ。
4. 「設定を保存」を押す。

### 2.2 鍵

1. 「鍵を作る」を押す。入力欄に `inline:` で始まる鍵が表示される。
2. 「コピー」を押し、受信機の設定（1.2 の SDP の `a=crypto` の行）に貼り付ける。
3. 「鍵を設定」を押す。入力欄が空になり、「鍵は設定済みです」と表示される。

受信機の側で作った鍵を使う場合は、受信機の `inline:` の値を入力欄に貼り付けて「鍵を設定」を押します。
寿命（`|2^31` など）と MKI（`|1:4` など）の付いた鍵は受け付けません。受信機の設定でこれらを外してください。

## 3. 試験

### 3.1 初期状態と鍵なしでの送信の禁止

1. 鍵を設定する前に、「送信を開始」と「接続テスト」が押せないことを確かめる。
2. 2.1 と 2.2 を済ませてから `pa-engine` と `remote-pa` を終了し、起動し直す。
3. パネルを開き、設定が戻っていること、「鍵は設定済みです」と表示されること、状態が「停止中」であることを確かめる。
4. 起動し直してから「送信を開始」を押すまでの間、Wireshark で PC-A から RX へのパケットが 1 つもないことを確かめる。

合格: 1 で押せない。3 で設定と鍵が戻り、停止中から始まる。4 でパケットが 0 個。
証拠: 1 と 3 の画面のキャプチャ、4 のキャプチャのファイル（フィルター `ip.dst == <RX>`）。

### 3.2 接続テスト

1. 停止中に「接続テスト」を押す。
2. 状態が「接続テスト中」になり、約 3 秒後に「停止中」に戻ること、直前の結果が「送信できました」になることを確かめる。
3. RX で 1 kHz の試験音が約 3 秒聞こえることを確かめる。

合格: 2 のとおりに表示が変わり、3 で試験音が途切れずに聞こえ、受信機のログに復号や認証の失敗が出ない。
証拠: 受信機の出力の録音、受信機のログ、Wireshark のキャプチャ。

「送信できました」は、PC-A のソケットが送信に成功したことだけを表します。受信機で復号できたかどうかは、受信機の側で確かめます。

### 3.3 本番の送信

1. 送り出すバスにテスト音を流し、「送信を開始」を押す。状態が「送信中」になることを確かめる。
2. RX でテスト音が聞こえることを、ステレオとモノラルのプロファイルの両方で確かめる（プロファイルを変えるときは「送信を停止」してから変える）。
3. ステレオのプロファイルで、L と R に別の音を流し、RX で左右が入れ替わっていないことを確かめる。
4. 送り出すバスのフェーダーやミュートを操作し、RX の音がそれに従うことを確かめる。
5. 「送信を停止」を押し、RX へのパケットが止まることを確かめる。

合格: 2〜4 のとおりに聞こえ、5 でパケットが止まる。受信機のログに復号や認証の失敗が出ない。
証拠: 受信機の出力の録音（左右を分けて）、受信機のログ、Wireshark のキャプチャ。

### 3.4 暗号化されていること

1. 3.3 の送信中のキャプチャで、パケットを RTP として解釈する（Wireshark の「Decode As」で UDP のポートを RTP にする）。
2. ペイロードタイプが画面の値と同じこと、パケットの間隔が 5 ms であること、最初のパケットにマーカービットが立っていることを確かめる。
3. ペイロードの末尾に認証タグ（`AES_CM_128_HMAC_SHA1_80` では 10 バイト、`_32` では 4 バイト）があり、ペイロードの中身が Opus として読めないことを確かめる。
4. 受信機の鍵を 1 文字変えて受信し、音が出ないこと、受信機のログに認証の失敗が出ることを確かめる。
5. 暗号スイートを `AES_CM_128_HMAC_SHA1_32` に変えて、受信機の設定も合わせ、3.3 の 1 と 2 を繰り返す。

合格: 2〜5 のとおり。4 で、鍵が違うと再生されない。
証拠: キャプチャのファイル、4 の受信機のログ。

### 3.5 失敗と停止の扱い

1. 宛先に解決できない名前（例: `receiver.invalid`）を入れて保存し、「送信を開始」を押す。状態が「停止中」のままで、直前の結果が「宛先の名前を解決できませんでした」になり、通知が出ることを確かめる。
2. 送り出すバスをルーティングで消して適用する。送信が止まり、「外部出力で送っていたバスがなくなった」旨の通知が出ることを確かめる。別のバスや Master へ切り替わって送り続けないことを、RX で確かめる。
3. 送信中に RX の受信機を止め、PC-A の音声の出力（Master）に影響が出ないことを確かめる。

合格: 1〜3 のとおり。
証拠: 画面のキャプチャ、通知の履歴、受信機の出力の録音。

### 3.6 実回線と遅延

1. RX を別の回線（インターネット越し）に置き、ルーターのポートを開けて 3.3 を繰り返す。
2. 送り出すバスにクリック音を流し、PC-A の出力と RX の出力を同じ録音機に入れて、時間差を測る。

合格: 1 で途切れずに聞こえる。2 の時間差は、回線の片道の遅延と受信機のバッファの合計に近い（PC-A の側で足している遅延は、5 ms のフレームとエンコードの先読みだけ）。
証拠: 録音、受信機のバッファの設定、回線の往復時間（`ping`）。

### 3.7 鍵がログに出ないこと

1. 3.1〜3.5 を終えた後、`<data-dir>\logs` のログファイルと、診断レポートを書き出したファイルを、試験に使った鍵の Base64 の文字列で検索する。

合格: どのファイルにも鍵が見つからない。
証拠: 検索のコマンドと結果（鍵そのものは残さない）。

## 4. 結果の報告

試験ごとの合否と証拠のファイル名を Issue #31 にコメントで残します。
不合格の試験があれば、受信機の種類と設定、再現の手順を書いた不具合の Issue を立てます。
受信機が 5 ms のフレームに対応しないと分かったら、10 ms と 20 ms のプロファイルを足す（ADR-0040 のコーデックのプロファイル）ための Issue を立てます。
