## 1. 製品概要と基本原則

### 1.1 製品の目的と役割
**Remote PA Console**は、インターネット（WAN）経由で複数人の音声を集め、1台の親機でミキシングして出力するためのWindows向けデスクトップアプリケーションである。

*   **親機（PA / Operator）**: セッションの作成、参加者の承認、音声の受信・ミキシング・VST処理・最終出力を一元管理する操作卓。
*   **子機（Client / Performer）**: 出演者が使用する入力収集ツール。マイクの選択、自身の送信ミュート、送信レベルの調整のみを行う。子機側から親機のミキサーやルーティングを操作することは一切できない。

### 1.2 Alpha版の「完成」の定義
本プロジェクトにおけるAlpha版は「開発者向けの動く試作品」ではなく、**「最小限の実用品（MVP）」**と定義する。以下のすべてを満たさなければAlpha版の完了とは認めない。
1.  開発ツール等の入っていないクリーンなWindows環境に、署名済みインストーラーで導入できる。
2.  LAN内だけでなく、異なるインターネット回線（WAN）にいる複数の子機から音声を受信し、親機で個別にミックスして物理デバイスへ出力できる。
3.  アプリ内の通知から安全にアップデートでき、Windowsの標準機能からアンインストールできる。

### 1.3 設計の絶対原則（開発者が勝手に変えてはならない境界）
1.  **音声スレッドの完全独立**: UIの描画停止、ウィンドウ操作、またはUIプロセスのクラッシュによって音声処理を止めてはならない。WebView（UI側）で生の音声データを直接扱ってはならない。
2.  **初期ミュートの徹底（爆音防止）**: 初回起動時や再起動時、あるいは新規参加者の接続時、親機の各チャンネル・Master、および子機の送信状態はすべて**ミュート（Mute）から開始**する。オペレーターが明示的に解除するまで音を出してはならない。
3.  **状態の一元管理（エンジン主権）**: 音声・通信・セッションの正しい状態はすべてバックエンドのエンジン（`pa-engine.exe`）が保持する。UIはエンジンへ操作要求を送り、エンジン側で適用が完了したという応答（ACK）を受け取ってから初めて表示を更新する。ただしフェーダー等の連続値操作のドラッグ中に限り、操作者の手元の追従を優先する例外を設ける（3.2 連続値操作）。
4.  **操作を止めない通知（非モーダル原則）**: エラーや情報通知、承認要求などでモーダルダイアログ（画面をロックする窓）を出してはならない。モーダルが許されるのは「稼働中セッションの終了」や「データの完全削除」など、取り返しがつかない操作の確認時のみとする。
5.  **未実装機能の「開発中」表示**: Beta版以降で実装される機能（VST、ルーティング、録画など）のボタンはAlpha版から画面上に配置するが、クリック時は非モーダルなポップアップで「開発中」と知らせるのみとし、ダミーの空ウィンドウを開いたり内部状態を書き換えたりしてはならない。

## 3. システム構成とプロセス設計

### 3.1 技術スタックと動作環境
*   **対象OS**: Windows 11 x64（優先）、Windows 10 x64（必要なランタイムとセキュリティ更新が維持されている環境）。将来的なmacOS / Linux対応を見据え、Windows固有API（WASAPI等）は抽象化境界の内部に隔離する。
*   **使用技術**: C++20、JUCE（音声処理・グラフ管理）、WebView2 + TypeScript（UI）、独自UDPメディアプロトコル + libopus（ネットワーク音声伝送）、実績ある暗号ライブラリ（鍵交換・AEAD。暗号プリミティブの自作は禁止）、CMake（ビルド）、WiX Toolset等（署名済みWindowsインストーラー）。WebRTC（libwebrtc等）には依存しない。ランデブーサーバーは別途Go等で実装する。

### 3.2 プロセス分割と責務 (`RPC-ARCH`)
UIの不具合から音声処理を守るため、実行ファイル（プロセス）を以下のように分離する。

```text
[PA Desktop UI (remote-pa.exe)]  <--- 認証付きローカルIPC --->  [PA Engine (pa-engine.exe)]
  ・メインコンソール表示 (WebView2)                               ・セッション / 参加者の権限管理
  ・非モーダル通知 / トースト                                     ・独自UDPトランスポート / Opus 送受信 / ジッター吸収
  ・未実装機能の「開発中」ボタン                                  ・PCMミキサー / リミッター / WASAPI出力

[Performer Client (remote-pa.exe)]  === 暗号化UDP (P2P: 直結 / ホールパンチ) ===> [PA Engine]
                     ↑                                                          ↑
                     └──────── [Rendezvous Server]（招待解決・アドレス交換のみ。音声は通らない）┘
  ・マイク入力キャプチャ / 送信ミュート・ゲイン制御
  *(※子機は単一プロセス内でUIスレッドとリアルタイム音声スレッドを分離して動作させる)*

[Updater (pa-updater.exe)]
  ・セッション終了後のアイドル時のみ起動し、署名検証とトランザクション更新を実行する短命プロセス
```

*   **プロセス間通信（IPC）**: 親機のUIとエンジンは、現在のログインユーザーのみがアクセスできる名前付きパイプ（Named Pipe）等で通信する。認証なしのローカルHTTPサーバー等は使用しない。
*   **コマンドの冪等性**: UIからの操作要求には `request_id`、`entity_id`、`expected_revision` を含める。エンジンは適用後に新しい `applied_revision` を返す。重複したリクエストIDは無視し、古いリビジョンに基づく競合操作は拒否する。この厳密な扱いはミュート、ルーティング、承認などの**離散操作**に適用する。
*   **連続値操作（フェーダー、送信レベル等）**:
    *   音量はローカルの再生バランスを決める値であり、エンジン内（親機のフェーダーは親機エンジン、子機の送信レベルは子機エンジン）で完結する。ネットワークの相手へは送らない。
    *   ドラッグ中、UIはつまみをポインター位置に即座に描画する（ACKを待たない）。同時に最新値のみを送るコマンド（`set_gain`。同一entityの未送信分は上書きして間引く。上限60Hz `[設計値]`）をIPCで送り続け、エンジンは受け取るたびに5〜20msのランプで適用する。これにより、ドラッグ中も実際の音量がリアルタイムに追従する。
    *   連続値コマンドは `expected_revision` による競合拒否の対象外とし、entityごとのシーケンス番号による後勝ち（last-writer-wins）とする。
    *   ドラッグ終了時に確定値を1回送り、ACKで返る `applied_revision` と適用値をUIの正式表示とする。ドラッグ終了から一定時間（500ms `[設計値]`）ACKが返らない場合、UIはエンジンが最後に通知した値へつまみを戻し、非モーダル警告を出す。
    *   数値入力やキーボードによる操作は、1操作を1回の確定コマンドとして扱う。
*   **メーター描画の最適化**: エンジンからUIへ48kHzの生波形を送ってはならない。エンジン側でピーク値やRMSを計算し、10〜30Hzの間隔で統計値のみをUIへプッシュする。

## 4. UI・画面設計と操作仕様

### 4.1 ウィンドウ構成 (`RPC-UI-001`〜`006`, `017`〜`034`)
*   **デスクトップ専用設計**: 親機のメイン画面は「実機のデジタルミキシングコンソール」を模したデスクトップUIとする。Webのダッシュボードやスマホ用のカード型レイアウトは採用しない。
*   **画面サイズ**: 基準解像度は1920×1080（DPIスケーリング対応）。最小1280×720のサイズでも、Masterストリップやミュートボタン、セッション制御が隠れずに操作できること（入力チャンネルが収まらない場合は横スクロールを許可する）。
*   **画面レイアウト**:
    *   **上部ステータス帯（高さ44〜56px）**: セッション名、状態、接続人数、現在の出力デバイス、警告件数、更新通知アイコンを常時表示する。
    *   **中央チャンネル領域**: 幅80〜112pxの均一なチャンネルストリップを並べる。参加者の増減があっても、本番中に自動で並び順を変えてはならない。
    *   **右端Master領域**: 幅104〜144pxで右端に常時固定する。
*   **独立サブウィンドウ（Beta1以降で順次解禁）**: ルーティング画面（Beta1）、メディア・録音管理（Beta2）、チャンネル詳細・VST GUI（Beta4）、映像プロダクション（Beta6）などは、メイン画面とは独立した「移動・リサイズ・マルチモニター配置が可能な別ウィンドウ」として対象マイルストーン到達時に実装する。サブウィンドウを閉じても音声処理は継続する。未到達のマイルストーンではウィンドウを作らず、ボタンの配置のみとする。

### 4.2 ミキサーとフェーダーの操作仕様 (`RPC-MIX-001`〜`008`, `RPC-UI-015`〜`016`)
*   **チャンネル数の保証**: Alpha版では最低8本のモノラル入力チャンネルと1本のMasterチャンネルを同時に扱えることを保証する。
*   **ストリップの表示項目**: 参加者名、短い識別ID、接続状態・信号状態の主表示（5.5.8の優先順位に従う）、ミュート表示（`send_muted` / `channel_muted` を区別）、プリフェーダー・ピークメーター、フェーダー（dB）、Muteボタン、選択（SEL）ボタンを常時表示する（マウスホバーしないと見えない隠しコントロールは禁止）。
*   **フェーダーの操作**:
    *   調整範囲は $-\infty\text{ dB} \sim +10\text{ dB}$（$0\text{ dB}$ に吸着/目印あり）。
    *   **誤操作防止のため、フェーダー上でのマウスホイール回転では音量を変化させない。**
    *   ドラッグで通常調整、`Ctrl + ドラッグ`で微調整、数値のダブルクリックでdB値の直接キーボード入力、フォーカス時の矢印キーで $0.5\text{ dB}$ 刻み（`Shift + 矢印`で $0.1\text{ dB}$ 刻み）の調整を行う。
*   **ミュートの独立性**: 「子機側の送信ミュート」と「親機側のチャンネルミュート」は独立して機能する。どちらかがミュートであれば音は出ない。親機がミュートしているチャンネルを子機側から勝手に解除することはできない。UI上では「どちらの理由でミュートされているか」を色だけでなくラベルやアイコンで明確に区別する。
*   **ミュートと音量の区別（データフロー）**:
    *   **ミュート**は「データを受け取らない」状態を意味する。ミュート / ミュート解除は制御チャネルで相手へ通知し、送信側はそれに応じて送信を停止・再開してよい。ミュート中に届いたデータ（通知到達前のもの、改ざんクライアントが送り続けたものを含む）は受信側エンジンで破棄する。ミュートの解除権限はミュートした側にのみあり、相手側からは解除できない。
    *   **方向別のデータフロー規則**:
        | 方向 / ミュートの種類 | データ送信 | 理由 |
        | :--- | :--- | :--- |
        | 子機→親機 / **子機の送信ミュート** | **停止する** | 出演者のマイク音声をPC外へ出さない（プライバシー） |
        | 子機→親機 / **親機のチャンネルミュート** | **継続する**（親機エンジンがミキサー入力段で破棄） | ミュートしたままプリフェーダーメーターで入力を監視でき、解除時に往復遅延なしで即座に音を出せるため |
        | 親機→子機 / **返送モニターのミュート（Beta1）** | **停止する** | 子機側でメーター監視の必要がなく、不要な通信を削減するため |
    *   **音量（フェーダー、$-\infty\text{ dB}$ を含む）**は受信側でゲインを掛けるだけの操作であり、データは常に送受信される。$-\infty\text{ dB}$ はミュートとして扱わず、UI上もミュートと区別して表示する。
    *   ミュート通知によって停止したストリーム（`PAUSED`）は `NO_SIGNAL` と判定しない（死活はキープアライブで監視する）。
    *   制御メッセージ（信頼性あり）とメディアフレーム（信頼性なし）の到着順が逆転しても誤判定しないよう、ミュート状態に世代番号（epoch）を付け、メディアフレームにも送信時点のepochを載せる。
    *   ミュート解除後に送信が再開されたら、ジッターバッファを新しい区間として再初期化し（クロックドリフト推定値は保持してよい）、停止前の古いデータを再生しない。再開時は5〜20msでフェードインする。解除後 **1秒** `[設計値]` 以内に最初のフレームが届かない場合に初めて `NO_SIGNAL` 判定を開始する（`RESUMING` → `NO_SIGNAL`、5.5.4）。
*   **メーターの鮮度**: 500ms以上有効な音声サンプルが届かないチャンネルは、メーターの緑バーをフリーズさせたままにせず、即座に減衰させて `NO_SIGNAL`（表示ラベル: NO SIGNAL）とする。

### 4.3 子機（Client）のUI仕様 (`RPC-CLI-001`〜`006`)
*   **画面構成**: 「招待コード/URLの入力と承認待ち画面」および「マイク選択・送信設定画面」の最小構成とする。
*   **操作項目**: 入力デバイスの選択（デバイス固有の永続IDで管理し、「入力なし」も選択可能）、送信Muteボタン、送信レベル（$-60\text{ dB} \sim +12\text{ dB}$、初期値 $0\text{ dB}$）、入力レベルメーター、通信状態の表示のみ。
*   **安全設計**: マイクを選択しただけでは送信を開始せず、必ず初期状態は「送信ミュート」とする。また、自分の声をそのまま聴くローカルサイドトーン機能は設けない（Beta1で親機からのミックス返送モニターを実装する）。

### 4.4 通知・ポップアップとモーダルの使い分け (`RPC-UI-007`〜`014`)
ライブオペレーションを妨げないため、画面表示のルールを以下のように厳格に定める。

| 発生する事象 | 採用するUI形式 | 動作・表示仕様 |
| :--- | :--- | :--- |
| **未実装（開発中）機能をクリック** | **非モーダル通知 (Toast)** | 「『{機能名}』は現在開発中です。今後のアップデートで利用可能になる予定です。」と表示するのみ。 |
| **設定の保存完了 / 招待コピー** | **非モーダル通知 (Toast)** | 4秒間表示して自動で消える。 |
| **通信切断・再接続 / パケット欠損** | **非モーダル通知 + ストリップ表示** | 警告は8秒間表示。該当チャンネルのステータス表記を更新し、他の操作は止めない。 |
| **マイクや出力デバイスの抜去** | **非モーダル警告 + ステータス帯保持** | 解決するまで画面上部のステータス帯に警告を残す。 |
| **新規参加者の承認リクエスト** | **非モーダルなサイドパネル** | メイン画面の端やヘッダーにバッジを出し、ミキシングを続けながら承認/拒否できる。 |
| **アップデートの発見** | **非モーダル通知 (Toast)** | 「更新版 `<version>` が利用可能です」と通知。セッションを強制終了させない。 |
| **稼働中セッションを閉じて終了** | **モーダルダイアログ（許可）** | 参加者がいる、または音声処理中にアプリを閉じようとした場合のみ表示。既定フォーカスは「キャンセル」。 |
| **ドライバーの導入・削除（Beta3）** | **モーダルダイアログ（許可）** | OSのシステム構成を変更し、再起動等を伴う可能性があるため明示確認を行う。 |
| **アンインストール時のデータ全削除** | **モーダルダイアログ（許可）** | 取り消せないデータ削除の確認時のみ使用。 |

*   **トースト通知の配置**: 画面右下を基本とするが、右端のMasterフェーダーやMasterミュートボタンに被さって操作を邪魔してはならない。同時表示は最大3件とし、あふれた分は通知履歴パネルに格納する。

## 5. セッション管理・音声処理・ネットワーク仕様

### 5.1 セッションのライフサイクル (`RPC-SES-001`〜`006`)
*   **状態遷移**: セッション・参加者・信号・ミュート・出力デバイスの各状態の正規名と遷移条件は **5.5 状態モデルと正規名称** で一元定義する。本書の他の箇所で状態に言及する場合は5.5の正規名を用いる。
*   **招待と認証**: 親機が発行する招待URL/コードは、128bit以上のエントロピーを持つトークンに紐づく。有効期限は **30分間** `[設計値]` とし、いつでも手動で失効できる。招待コードは「参加承認をリクエストする権利」を与えるだけであり、親機が承認（Accept）するまで音声通信は一切開始されない。
*   **切断と再接続**: 承認済みの子機が通信切断した場合、**120秒以内** `[設計値]` であれば再接続トークンを用いて元の `participant_id` と同じチャンネルストリップに自動復帰する（新しいチャンネルを重複生成してはならない）。
*   **セッション終了**: 終了時は全招待を無効化してピアを切断し、出力を10msかけてフェードアウト（ポップノイズ防止）させ、設定を保存して待機状態に戻る。

### 5.2 音声信号処理とタイミング (`RPC-AUD-001`〜`010`)
*   **音声データの流れ（Alpha版）**:
    ```text
    [子機] WASAPI Capture -> モノラル変換 -> 入力ゲイン/Mute(5〜20msランプ) -> Opus Encoder -> メディアフレーム化 -> AEAD暗号化 -> UDP送信
       ===> (P2P: 直結 または ホールパンチング。中継なし) ===>
    [親機] UDP受信 -> 認証・復号/リプレイ排除 -> シーケンス順序整列/重複排除 -> Opus Decoder & PLC -> 適応型ジッターバッファ
           -> クロックドリフト補正(リサンプラー) -> Chゲイン/Mute -> Master加算 -> 安全リミッター -> WASAPI出力
    ```
*   **内部フォーマット**: サンプルレート $48,000\text{ Hz}$、32-bit浮動小数点（Float32 PCM）。物理デバイスが $44.1\text{ kHz}$ 等の場合はデバイス境界でリサンプリングを行う。
*   **バッファサイズ**: 内部の標準ブロックサイズは **128サンプル** `[設計値]` とするが、物理オーディオインターフェースのコールバック長（64〜512サンプル等）が可変であっても破綻なく処理できる構造にする。
*   **メディアタイムスタンプとジッター吸収**:
    *   メディアフレームのタイムスタンプは、入力デバイスのレートに関わらず常に $48\text{ kHz}$ 時計で進める（RFC 7587 のOpusタイムスタンプの考え方に準拠）。ネットワークの「到着時刻」ではなく、フレームの「シーケンス番号とタイムスタンプ」に基づいて再生順序を整える。
    *   ストリームごとに適応型ジッターバッファ（初期目標 **60ms**、変動範囲 **20〜250ms** `[設計値]`）を設ける。
    *   単発のパケットロスはOpusのPLC（パケットロス隠蔽）で補間し、**500ms以上**音声が届かない場合は古いバッファを無限ループ再生せず、無音化して信号状態を `NO_SIGNAL` に遷移させる（5.5）。
*   **クロックドリフト補正**: 子機と親機のオーディオクロックの微妙なズレ（ppm単位の誤差）によってバッファが徐々に溢れたり枯渇したりするのを防ぐため、Alpha版から適応型リサンプリングによるドリフト補正を必須とする。
*   **リアルタイムスレッドの制約**: 音声出力コールバック内でのヒープメモリ確保（`new`/`malloc`）、ロック待ち（Mutex）、ファイルI/O、ネットワーク送受信、プラグイン探索は厳禁とする。フェーダー操作等の反映にはロックフリーのキュー（SPSC等）を用い、音量変更時は5〜20msのランプ処理を行ってクリックノイズを防ぐ。

### 5.3 ネットワークとセキュリティ (`RPC-NET-001`〜`012`)
*   **方針（WebRTC非採用）**: 親機・子機はともに本製品のネイティブアプリであり、ブラウザとの相互接続を要しない。したがってWebRTC（SDP / ICE / DTLS-SRTP / SCTP）には依存せず、要件を「UDP上でOpusを運ぶ」「暗号化する」「NATを越える」の3点に限定した独自プロトコルで実装する。
*   **メディア伝送**: 音声はUDP上の独自メディアフレーム（ストリームID、シーケンス番号、$48\text{ kHz}$ タイムスタンプ、Opusペイロード）で送受信する。通常の音声伝送にTCPやWebSocketを代用してはならない。
*   **暗号化**: すべてのパケット（メディア・制御とも）を認証付き暗号（AEAD）で保護し、平文送信は一切行わない。セッション鍵は接続ごとの鍵交換で確立し、シーケンス番号によるリプレイ防止を行う。鍵交換方式（候補: Noiseプロトコル / DTLS 1.3）はADRで決定する。暗号プリミティブは実績ある既存ライブラリを使用し、自作してはならない。招待トークンに親機の公開鍵指紋を含め、中間者による親機なりすましを防止する。
*   **制御チャネル**: 参加承認、ミュート状態通知、キープアライブ等の制御メッセージは、同一UDPセッション上の再送付き信頼メッセージ層で送受信する（SCTP / DataChannelは使用しない）。
*   **NAT越え（中継なし）**: 接続は以下の順で試行する。いずれも失敗した場合は嘘の「接続済み」表示を出さず、原因別の明確なエラーコードと対処案（親機のポート開放 / IPv6 利用等）を表示する。
    1.  **直結**: 親機が外部から到達可能な場合（IPv6グローバルアドレス、手動ポート転送、UPnP-IGD / NAT-PMP / PCPによる自動ポート開放）。
    2.  **UDPホールパンチング**: ランデブーサーバーで双方の外部アドレス候補を交換し、同時送信によりNATマッピングを開通させる。
*   **ランデブーサーバー**: Go製の単一バイナリとし、以下を同居させる。いずれの機能も音声のミキシング・復号は行わず、メディア鍵も保持しない。
    *   **UDP（単一ポート）**: STUN Binding（RFC 8489準拠。外部アドレス通知）と、独自ランデブーメッセージ（候補アドレス交換・ホールパンチ開始の同期）を同一ポートで受け付ける。両者はパケット先頭（STUNのMagic Cookie `0x2112A442` 等）で判別する。
    *   **HTTPS**: 招待の解決API、製品フロントページ（静的サイト）。更新マニフェスト（6.3）の配信も同居可とする。
    *   ランデブーサーバーが停止しても、確立済みのP2Pセッションの音声は継続しなければならない（セッション確立後はサーバーに依存しない）。
*   **中継（将来実装）**: Alpha〜v1.0の範囲では中継を提供せず、対称型NAT / CGNAT環境同士など直結もホールパンチングも成立しない組み合わせは接続不可として明示する。将来、有料オプションとしてランデブーサーバーに中継機能を追加する。親機・子機間は独自プロトコルのため標準TURN（RFC 8656）互換は要件とせず、暗号化済みパケットを不透明に転送する独自リレーとする。後から差し込めるよう、トランスポートは経路非依存に設計する。中継は帯域コストが大きいため、ランデブー・サイトとは別ホストへ分離できる構成とする。
*   **キープアライブ**: NATマッピング維持および死活監視のため、音声が流れていない間（送信ミュート中を含む）も **1秒間隔** `[設計値]` で制御パケットを送信する。音声・制御を問わず受信が **5秒** `[設計値]` 途絶した場合に接続状態を `RECONNECTING` へ遷移させる（5.5）。
*   **再接続バックオフ**: 回線瞬断時は 1秒、2秒、4秒、8秒、15秒（ランダムなジッター付き）の間隔で自動再接続を試みる。
*   **権限チェックと機密保護**: 「子機からのMaster音量変更」のような不正なコマンドが送られてきた場合、UIで隠すだけでなく必ずエンジンおよびサーバー側で権限を検証して拒否する。トークンや認証情報はWindows資格情報マネージャーまたはDPAPIで暗号化して保持し、設定ファイルやログに平文で書き出してはならない。

### 5.4 物理デバイス出力 (`RPC-OUT-001`〜`005`)
*   **出力方式**: Alpha版ではWASAPI共有モード（Shared Mode）で物理デバイスへ出力する（ASIOや排他モードは将来対応とし、UIに出す場合は「開発中」とする）。
*   **デバイス抜去時の安全動作**: 使用中の出力デバイス（USBオーディオIF等）が抜かれた場合、**勝手にPC内蔵スピーカー等の別デバイスへ出力を切り替えてはならない**。即座にMasterをミュートして出力を止め、非モーダル警告を出してオペレーターの手動選択を待つ。

### 5.5 状態モデルと正規名称 (`RPC-STATE-001`〜`008`)
状態は互いに独立した複数の軸で管理し、1つの列挙に混在させない。特に**ミュートは状態（通信の様子）ではなく操作フラグ**であり、接続状態・信号状態とは別に保持する。

#### 5.5.1 命名規則
*   プロトコル・エンジン・ログ・テストで使う**正規名**は、状態が `UPPER_SNAKE_CASE`、フラグが `lower_snake_case` とする。
*   UIの表示ラベルは正規名とは別に定義し、ローカライズ可能とする。UIは正規名を直接表示しない。
*   状態の値はすべてエンジンが決定し、UIは受け取った値を表示するのみとする（1.3 エンジン主権）。

#### 5.5.2 親機セッション状態 `SessionState`
| 正規名 | 意味 | 遷移条件 | UI表示ラベル |
| :--- | :--- | :--- | :--- |
| `IDLE` | セッションなし | 起動直後 / 終了完了 / エラー回復後 | 待機 |
| `CREATING` | セッション作成中（ランデブー登録・鍵生成） | 作成操作 | 作成中 |
| `READY` | 作成済み・参加者なし | 作成完了 | 準備完了 |
| `ACTIVE` | 1人以上が `CONNECTED` / `RECONNECTING` | 最初の参加者が接続 | 本番中 |
| `ENDING` | 終了処理中（招待失効・切断・フェードアウト・保存） | 終了操作 | 終了中 |
| `ERROR` | 致命的エラー。原因コード付き | 作成失敗 / エンジン異常 | エラー (E-xxx) |

遷移: `IDLE` → `CREATING` → `READY` ⇄ `ACTIVE` → `ENDING` → `IDLE`。`CREATING` / `READY` / `ACTIVE` から `ERROR` へ遷移でき、`ERROR` からは `IDLE` へ戻る。

#### 5.5.3 参加者接続状態 `ConnectionState`（親機側・参加者ごと）
| 正規名 | 意味 | 遷移条件 | UI表示ラベル |
| :--- | :--- | :--- | :--- |
| `PENDING` | 承認待ち。ストリップは生成せず承認パネルにのみ表示 | 招待による参加要求を受信 | 承認待ち |
| `CONNECTING` | 承認済み。経路確立（直結 / ホールパンチ）と鍵交換の実行中 | 承認（Accept）/ 再接続開始 | 接続中 |
| `CONNECTED` | 暗号化セッションと制御チャネルが確立済み | 経路・鍵交換の完了 | （信号状態を表示） |
| `RECONNECTING` | 受信途絶。再接続猶予（120秒）内 | 受信が5秒途絶（5.3） | 再接続中 |
| `LOST` | 再接続猶予切れ。ストリップは位置を保持したまま残し、オペレーターの削除操作を待つ | `RECONNECTING` が120秒経過 | 切断 |
| `FAILED` | 経路確立不能（NAT越え不成立等）。原因コード付き | `CONNECTING` の全経路失敗 | 接続不可 (E-xxx) |

*   ストリップは `PENDING` からの承認時に生成し、以後 `participant_id` に固定する。`LOST` からの再接続（再接続トークン有効時）は同じストリップへ復帰する。
*   承認拒否された参加者には `ConnectionState` を割り当てず、ストリップも生成しない。

#### 5.5.4 信号状態 `SignalState`（`CONNECTED` のときのみ有効）
| 正規名 | 意味 | 遷移条件 | UI表示ラベル |
| :--- | :--- | :--- | :--- |
| `RECEIVING` | 有効な音声フレームを受信中（親機の `channel_muted` 中も含む） | フレーム到着 | （メーターのみ。ラベルなし） |
| `PAUSED` | 子機の送信ミュートにより意図的に停止中 | `send_muted` = true の通知受信 | （ミュート表示で代替） |
| `RESUMING` | 送信ミュート解除通知後、最初のフレーム待ち | `send_muted` = false の通知受信 | （ラベルなし） |
| `NO_SIGNAL` | 送信中のはずが500ms以上フレーム未着。無音化済み | `RECEIVING` で500ms未着 / `RESUMING` で1秒未着 | NO SIGNAL |

*   `PAUSED` 中のフレーム不着は `NO_SIGNAL` としない。判定にはミュートのepoch（4.2）を用いる。
*   `CONNECTED` 以外の接続状態では `SignalState` は未定義とし、UIは接続状態のラベルを表示する。

#### 5.5.5 ミュートフラグ
| 正規名 | 対象 | 設定・解除できる主体 | 初期値 | データ送信（4.2） | UI表示ラベル |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `send_muted` | 子機の送信 | 子機のみ | true | 停止 | 子機MUTE |
| `channel_muted` | 親機の各入力チャンネル | 親機のみ | true | 継続（ミキサー入力段で破棄） | MUTE |
| `master_muted` | 親機のMaster | 親機（オペレーター）/ エンジン（安全動作） | true | — | MUTE / SAFETY MUTE |
| `return_muted` | 親機→子機の返送モニター（Beta1） | 親機のみ | true | 停止 | 返送MUTE |

*   `master_muted` には理由 `master_mute_reason`（`OPERATOR` / `SAFETY`）を付ける。`SAFETY` は出力デバイス抜去やエンジン異常時にエンジンが設定するもので、UIでは `SAFETY MUTE` と区別して表示する。解除はオペレーターの明示操作のみとする。
*   フェーダーの $-\infty\text{ dB}$ はミュートフラグではなく音量値である。

#### 5.5.6 出力デバイス状態 `OutputDeviceState`
| 正規名 | 意味 | UI表示ラベル |
| :--- | :--- | :--- |
| `NONE` | 出力デバイス未選択 | 出力未選択 |
| `OPEN` | 選択したデバイスへ出力中 | （デバイス名を表示） |
| `LOST` | 使用中のデバイスが抜去・消失。`master_muted` = true（`SAFETY`）。他デバイスへ自動切替しない | 出力デバイス消失 |

#### 5.5.7 子機クライアント状態 `ClientState`
| 正規名 | 意味 | UI表示ラベル |
| :--- | :--- | :--- |
| `DISCONNECTED` | 未接続。直前の終了理由（`SESSION_ENDED` 等）を保持できる | 未接続 |
| `RESOLVING` | 招待コードをランデブーサーバーで解決中 | 招待を確認中 |
| `AUTHENTICATING` | 参加要求の送信と認証 | 認証中 |
| `WAITING_APPROVAL` | 親機の承認待ち | 承認待ち |
| `CONNECTING` | 承認後、経路確立と鍵交換の実行中 | 接続中 |
| `CONNECTED` | 接続済み | 接続済み |
| `RECONNECTING` | 受信途絶。再接続を試行中（5.3 バックオフ） | 再接続中 |
| `FAILED` | 終端的な失敗。自動リトライしない。原因コード付き | 接続できません (E-xxx) |

*   `FAILED` の原因コード: `REJECTED`（承認拒否）、`INVITE_EXPIRED`、`INVITE_REVOKED`、`UNREACHABLE`（NAT越え不成立）、`RECONNECT_TIMEOUT`（再接続猶予切れ）。

#### 5.5.8 ストリップの主表示の優先順位
チャンネルストリップの状態欄には次の優先順位で1つだけ表示する。ミュート表示はこれとは独立したバッジ・ボタンで常時表示する（4.2）。
`FAILED` > `LOST` > `RECONNECTING` > `CONNECTING` > `NO_SIGNAL` > （ラベルなし: `RECEIVING` / `PAUSED` / `RESUMING`）

#### 5.5.9 旧名称との対応（v1.1以前）
| 旧名称 | 正規名 |
| :--- | :--- |
| `waiting` | `PENDING`（承認パネルのみ） |
| `live` | `RECEIVING` |
| `reconnecting` / `Reconnecting` | `RECONNECTING` |
| `lost` / `Lost` | `LOST` |

## 6. データ保存・インストーラー・更新・削除（Alpha版必須要件）

### 6.1 設定とログの永続化 (`RPC-DATA-001`〜`005`)
*   **保存先**: プログラムのインストールフォルダには書き込まず、すべて `%LOCALAPPDATA%/RemotePAConsole/` 配下の固定フォルダ（`settings.json`, `sessions/`, `logs/`, `cache/`, `updates/`）に保存する。
*   **破損対策（アトミック保存）**: 設定保存時は一時ファイルに書き出してフラッシュ（fsync）した後にリネーム置換し、直前の正常なバックアップを1世代残す。万一設定ファイルが破損していた場合は、安全な初期状態（全ミュート）で起動し、バックアップからの復元ボタンを提示する。
*   **ログと診断出力**: ログはローテーション（例: 10MB×5ファイル）を行い、生の音声データや招待トークンを一切含めない。ユーザーがサポートへ送るための「マスキング済み診断レポート出力機能」を備える。

### 6.2 インストーラー仕様 (`RPC-LIFE-001`〜`008`)
*   **パッケージ形態**: コード署名（Authenticode）された単一のWindowsインストーラー（WiX等）を提供する。1つのインストーラーで「Remote PA Console（親機）」と「Remote PA Client（子機）」の両方のショートカットを導入できる。
*   **クリーン環境での動作**: Visual C++ ランタイムやJUCE・Opus・暗号関連ライブラリはすべて同梱し、一般ユーザーに開発ツールやSDKの手動導入を一切求めない。WebView2 Evergreen Runtimeが未導入の環境では、公式の配布手段を用いてセットアップ中に自動導入する。
*   **OS環境を汚さない原則**: 原則として一般ユーザー権限（Per-User）で導入可能とする（カスタム仮想ドライバーを導入するBeta3までは管理者権限を要求しない）。システムのグローバルな `PATH` 環境変数の書き換え、レジストリへの独自設定保存、シェル拡張、PC起動時の自動常駐タスク登録は一切行わない。

### 6.3 アップデート仕様 (`RPC-LIFE-009`〜`018`)
*   **更新チェック**: アプリ起動時および最大24時間ごとにHTTPS経由で更新マニフェストを確認する（手動確認も可能）。
*   **署名とハッシュの検証**: マニフェスト（バージョン、URL、SHA-256、発行者、署名を含む）の信頼チェーンと、ダウンロードしたインストーラー自体の電子署名・ハッシュ値を厳密に検証する。改ざんや署名不一致があれば即座に破棄し、旧版を維持する。
*   **本番中の更新ブロック**: セッション稼働中にバックグラウンドで更新ファイルをダウンロード・検証することは許可するが、**バイナリの書き換えと再起動は、すべてのセッションが終了し、ユーザーが明示的に「更新して再起動」を押した時のみ**実行する。
*   **ロールバック保証**: 更新適用前に現在の設定データをバックアップする。もし更新途中でディスク不足やエラーが発生した場合、または新バージョンの起動確認に失敗した場合は、直前の動作していたバージョンと設定へ安全にロールバックする。
*   **実証テストの義務**: Alpha版の完了判定には、単なるダミー通知ではなく、実際に署名された2つの異なるビルド（例: `0.1.0-alpha.1` → `0.1.0-alpha.2`）を用いた実アップデート試験の合格を必須とする。

### 6.4 アンインストーラー仕様 (`RPC-LIFE-019`〜`025`)
*   Windowsの「インストールされているアプリ」から標準手順で削除できる。セッション稼働中にアンインストールが呼ばれた場合のみ、モーダルダイアログで終了確認を行う。
*   **ユーザーデータの扱い**: アンインストール時に「設定とログを保持する（既定）」か「すべてのアプリデータを完全に削除する」かを選択できる。完全削除を選んだ場合でも、ユーザーが任意に指定した外部の録音保存先フォルダや、他アプリも共有するWebView2ランタイム自体は削除してはならない。

## 7. Beta版以降の機能仕様（Beta1〜Beta6 事前契約）

Alpha版では以下の機能はすべて「開発中（PLANNED）」として入口のみ表示し、各マイルストーンで順次実装する。

### 7.1 Beta1：高度なルーティング・バス・返送モニター (`RPC-B1-001`〜`006`)
*   **入力ソースの拡張**: 子機ごとのステレオ入力、複数マイク入力、およびPC内アプリケーション音声のループバック収集に対応する。
*   **ルーティング画面（マトリクス / ノードグラフ）**: 入力ソース、ユーザー作成バス、Masterバス、物理出力先を自由に結線できる。設定変更はステージング（仮状態）で検証し、意図しないフィードバックループ（発振経路）が検出された場合は適用をブロックする（明示的なディレイノードとオペレーターの承認がある場合を除く）。
*   **センドとバス制御**: プリフェーダー / ポストフェーダーの選択、任意のセンドレベル調整、キュー（Cue）/ モニターバスの作成に対応する。
*   **手動同期オフセット**: 入力ソースごとの手動ディレイオフセット調整、およびシステム全体の目標レイテンシー設定・実測ジッター表示を提供する。
*   **子機への返送モニター（Minus-Me）**: 親機のミックス音声を子機へ送り返す機能（初期値はOFF）。返送をミュートまたはOFFにしている間は、親機から子機への音声送信自体を停止する（4.2 方向別のデータフロー規則）。ハウリングやエコーを防ぐため、子機自身のマイク音声を除外したミックス（Minus-Me）を生成して返送し、万一子機側で返送音をそのまま送信ソースに選んだ場合はルートガードで遮断する。

### 7.2 Beta2：録音・ファイル再生・SRTP外部出力 (`RPC-B2-001`〜`004`)
*   **マルチトラック録音（WAV / FLAC）**: 任意のチャンネルやバスの音声を録音する。ディスクの書き込み遅延や容量不足が起きてもリアルタイム音声スレッドを絶対にブロックしないよう、非同期バッファリングで完全に隔離する。
*   **音源ファイル再生**: ローカルの音声ファイルを読み込み、任意のバスへルーティングして再生できるメディアプレイヤー機能。
*   **SRTP外部ストリーム出力**: 外部の放送機器やサーバーへ向けて、指定したバスの音声をSRTPで暗号化送信する（平文での誤送信は禁止）。外部機器との相互接続のため、本機能のみ標準RTP/SRTPを用いる（親機・子機間の独自トランスポートとは独立）。接続テスト機能とコーデックプロファイル設定を備える。

### 7.3 Beta3：Windows独自仮想音声デバイス (`RPC-B3-001`〜`003`)
*   **カスタム仮想音声ドライバー**: 外部アプリからPAへ音を入れる仮想再生デバイス（Render-to-PA）と、PAのミックス音を外部アプリ（配信ソフトや通話アプリ等）へ渡す仮想録音デバイス（Capture-from-PA）を提供する（MicrosoftのSysVADサンプル等を参考にしつつ、製品品質で実装する）。
*   **署名と品質保証**: ドライバーは必ず正規のコード署名（WHQL / Attestation Signing等、Windowsが通常モードで読み込める署名）を施し、テストモードを要求する未署名ドライバーでの出荷は認めない。
*   **ライフサイクル統合**: インストーラーおよびアンインストーラーから安全に導入・更新・完全削除でき、デバイスの永続ID維持、クロック精度・遅延テスト、HLK互換性検証をクリアすることをBeta3のリリース条件とする。

### 7.4 Beta4：VST3エフェクト (`RPC-B4-001`〜`007`)
*   **プラグイン探索と隔離スキャン**: インストール済みのVST3プラグインを別プロセス（ヘルパー）でスキャンし、不良プラグインによる本体の起動クラッシュを防ぐ。
*   **グラフ統合と遅延補正（PDC）**: JUCEの `AudioProcessorGraph` 等を用いてVST3エフェクトをホストし、プラグインが報告する処理遅延を並列パス間で自動補正する。
*   **独立GUIとクラッシュ耐性**: VSTの独自エディターは独立したネイティブウィンドウとして開き、閉じても音声処理は継続する。実行モードは「信頼済みインプロセス（低遅延）」と「アウトオブプロセス（完全クラッシュ隔離）」を選択可能とし、プラグインがハングアップまたはクラッシュした際は該当パスのみを安全にバイパスまたはミュートしてセッションを継続する。

### 7.5 Beta5：MIDI・VSTi音源 (`RPC-B5-001`〜`006`)
*   **MIDI入力とルーティング**: MIDIデバイスの列挙（永続ID管理）、承認済みクライアントからのMIDIイベント受信、PCM音声とは独立したMIDIルーティングを提供する。
*   **VST3インストゥルメント（VSTi）**: Beta4のホスト基盤を拡張し、MIDIイベントでVSTi音源を駆動して音声バスへ出力する。
*   **タイミング精度と音残り防止**: MIDIタイムスタンプをDSPブロック内の正確なサンプルオフセットへ変換し、Note On / Off の順序を保証する。通信切断時や異常時には即座に All Notes Off（Panic）を発行し、音が鳴りっぱなしになる現象（Stuck Note）を防ぐ。

### 7.6 Beta6：映像キャプチャ・合成・動画記録 (`RPC-B6-001`〜`008`)
*   **映像キャプチャとレイヤー合成**: Windows Graphics Capture等を用い、静止画・ウィンドウ・ディスプレイ画面をキャプチャする。位置、サイズ、クロップ、不透明度、重なり順（Z-order）の基本的なレイヤー合成とシーン切り替えを、独立した「Production Editor」ウィンドウで操作する。
*   **音声最優先の原則**: GPU合成や映像エンコードは音声スレッドから完全に切り離す。システム高負荷時には映像フレームをドロップ（間引き）させ、**いかなる場合も音声処理を止めてはならない**。
*   **A/V同期と録画**: 映像のプレゼンテーションタイムスタンプを音声セッションのタイムラインに同期させ、外部出力およびコンテナファイルへの録画を行う。録画中の異常終了時にもファイルが破損せず再生可能にするリカバリー機構を備える。

## 8. 非機能要件・障害時動作・受け入れテスト

### 8.1 パフォーマンス・設計目標値 `[設計値]`
以下の数値は開発の基準および受け入れテストのベースラインである（地球の裏側とのWAN通信で無条件に20ms以下を保証するような非現実的な宣言は行わない）。

| 指標 | 目標基準 | 測定・検証方法 |
| :--- | :--- | :--- |
| **同時接続子機数** | モノラル 8台以上 | 30分間のWANシミュレーションで全チャンネルが破綻なく聴こえること |
| **連続稼働耐性（Soak）** | 4時間クラッシュなし | 子機3台以上、パケットロスやジッターを注入しながら4時間連続稼働 |
| **音声途切れ（Glitch）** | 30分あたり1回以下 | 正常なLAN環境でのループバック録音とXRUN（バッファアンダーラン）計測 |
| **UI操作の応答速度** | p95 が 100ms 以内 | Mute等の離散操作、およびフェーダーのドラッグ終了から、エンジンの適用完了ACKが返るまでのローカル時間 |
| **ドラッグ中の音量追従** | p95 が 30ms 以内 `[設計値]` | フェーダードラッグ中のポインター移動から、出力音量に反映されるまでの時間（ランプ開始時点で計測） |
| **メーター更新周期** | 10〜30 Hz（500msで失効） | UIレンダリング統計と通信遮断時の `NO_SIGNAL` 遷移確認 |

### 8.2 障害・異常時の規範動作まとめ

| 発生した異常・障害 | オーディオエンジンの動作 | UIの表示・動作 | 復旧方法 |
| :--- | :--- | :--- | :--- |
| **子機1台の回線切断** | 該当ChのみPLC後に無音化。他Chは継続 | 該当ストリップに `RECONNECTING` → （猶予切れで）`LOST` を表示 | 120秒以内の再接続で同じChへ自動復帰 |
| **パケット欠損・順序逆転** | シーケンス番号・タイムスタンプに基づき整列・PLC補間。500ms超過で無音 | ジッター/ロス警告を非モーダル表示 | 回線回復で自動復帰（古い音の再生は破棄） |
| **子機のマイク抜去** | 無音を送信 | 子機画面に警告表示。Mute状態は維持 | マイク再接続または別デバイスの手動選択 |
| **親機の出力デバイス抜去** | **別デバイスへ勝手に流さず** Masterを安全Mute | 画面上部にデバイス警告を継続表示 | オペレーターが新しい出力先を手動で選択 |
| **親機UIプロセスの強制終了** | **エンジンは生き残り、ミキシングと出力を継続** | UI再起動後にIPC再接続し、現在の状態を復元 | 自動で再アタッチ完了 |
| **親機エンジンのクラッシュ** | 安全に出力を停止 | 再起動後にエラー通知 | 再起動時は必ず**全Ch・Masterミュート**から開始 |
| **NAT越え不成立（直結・ホールパンチとも失敗）** | 該当子機の接続を確立しない | 子機・親機双方に原因別エラーコードと対処案を表示（「接続済み」と誤表示しない） | 親機のポート開放 / IPv6 / 別回線で再試行 |
| **更新パッケージの署名不一致** | 稼働中なら影響なし | 更新失敗を通知し、パッケージを破棄 | 旧バージョンのまま通常利用を継続 |

### 8.3 Alpha版 受け入れテスト一覧（Release-Blocking Tests）
Alpha版のリリースには、以下のテストすべてに合格し、ログや測定結果の証拠（Evidence）を揃える必要がある（単なる画面キャプチャや「動きました」という口頭報告は不可）。

*   **`AT-A01` [クリーン導入]**: 開発ツールのないクリーンなWindows x64仮想マシンにインストーラーで導入し、WebView2がセットアップされ、アプリ一覧に登録されて起動すること。
*   **`AT-A02` [WAN接続・承認前遮断]**: 親機でセッションを作成し、別ネットワークの子機が招待コードで接続（親機直結とUDPホールパンチングの両経路で確認）。親機が承認するまでは音声が一切届かないこと。
*   **`AT-A03` [3台同時ミックス]**: 子機3台を承認し、双方のMuteを解除。親機の各フェーダーとMuteが独立して機能し、物理デバイスから混音出力されること。
*   **`AT-A04` [フェーダー操作とMute独立性]**: ドラッグ、数値入力、キーボードで音量が変わり、ホイールでは変わらないこと。また、子機側Muteと親機側Muteの理由が区別して表示され、$-\infty\text{ dB}$ とMuteが区別されること。Mute / 解除を繰り返しても `NO_SIGNAL` の誤判定や古い音の再生が起きないこと。
*   **`AT-A05` [切断と同一Ch復帰]**: 3台のうち1台を切断しても残り2台の音が途切れず、120秒以内に再接続した際、チャンネルが増殖せず元のストリップに復帰すること。
*   **`AT-A06` [悪条件ネットワーク耐性]**: パケットの順序逆転、重複、欠損、ジッターを人工的に注入してもクラッシュせず、500ms以上の途絶で `NO_SIGNAL`（無音）になり、古い音が遅れて再生され続けないこと。
*   **`AT-A07` [出力デバイス抜去の安全性]**: 音声出力中に親機のオーディオデバイスを抜いた際、別のスピーカーへ勝手に音が出ず、MasterがMuteされて警告が出ること。
*   **`AT-A08` [UIクラッシュ隔離]**: 音声出力中に親機のUIプロセス（WebView側）をタスクマネージャー等で強制終了しても音が止まらず、UI再起動後に元のミキサー状態が正しく再表示されること。
*   **`AT-A09` [未実装ボタンの無害性]**: Beta1〜Beta6で実装予定の「開発中」ボタンをすべてクリックし、非モーダル通知が出るだけで、空ウィンドウの生成や設定・音声の変化が一切起きないこと。
*   **`AT-A10` [実アップデートと本番保護]**: 署名済みの旧版から新版へアプリ内更新できること。また、セッション稼働中は更新通知が来ても音が止まらず、セッション終了後にのみ更新が適用されること。
*   **`AT-A11` [不正更新の拒否とロールバック]**: 署名が異なる、または破損した更新ファイルを与えた際に更新を拒否し、元のバージョンが壊れずに起動できること。
*   **`AT-A12` [アンインストールと再導入]**: 「設定を保持して削除」→「再インストール」で設定が引き継がれ、「データをすべて削除」→「再インストール」で初期状態に戻ること。レジストリやPATHにゴミが残らないこと。
*   **`AT-A13` [設定破損と初期ミュート復帰]**: 設定保存中の強制終了や破損ファイルを置いた状態で起動しても、バックアップまたは安全な初期状態（全ミュート）で起動し、前回音が出ていた状態でも再起動直後にいきなり音が出ないこと。
*   **`AT-A14` [権限とセキュリティ検証]**: 改ざんしたクライアントからMaster音量変更コマンドを送ってもエンジン側で拒否されること。また、期限切れ・拒否済みの招待コードで再侵入できないこと。
*   **`AT-A15` [長時間・負荷試験]**: 8クライアント同時接続（30分）および3クライアント以上での連続稼働（4時間）を完走し、メモリリークやエンジンのデッドロックが起きないこと。
*   **`AT-A16` [NAT越え不成立時の表示]**: 対称型NAT同士など接続不能な環境を模擬し、「接続済み」と誤表示されず、原因別エラーコードと対処案が表示されること。
*   **`AT-A17` [伝送の暗号化・改ざん検出]**: パケットキャプチャで音声・制御とも平文が流れていないこと。改ざん・リプレイしたパケットが復号段階で破棄され、音声やセッション状態に影響しないこと。
