# 0012. ランデブーサーバーのプロトコルと状態の持ち方

- 状態: 採用（2026-11-07）

## コンテキスト

仕様書は、ランデブーサーバーを Go の単一バイナリとし、UDP の単一ポートで STUN Binding と独自のランデブーメッセージ（候補アドレスの交換、ホールパンチ開始の同期）を、HTTPS で招待の解決 API と製品サイトを提供するよう求めている。
サーバーは音声もメディア鍵も扱わず、止まっても確立済みのセッションは続かなければならない。
招待は 128 bit 以上のエントロピーを持つトークンに紐づき、30 分で失効し、いつでも手動で失効できる。
ホスティング先は決まっていない（候補は Google、Cloudflare、さくらインターネット）。

## 決定

### 招待

- 親機が招待トークン（16〜64 バイト）、静的公開鍵（32 バイト）、ランデブー ID（16 バイト）を `POST /v1/invites` で登録し、サーバーが招待コードと失効用の鍵を返す。招待トークンと鍵は親機が作り、サーバーは預かって渡すだけにする。
- 招待コードは Crockford Base32 の 10 文字（50 bit）で、`XXXXX-XXXXX` と表示する。入力時は大文字小文字、ハイフン、空白、`O` と `0`、`I`・`L` と `1` の違いを吸収する。
- 子機は `POST /v1/invites/resolve`、親機は `POST /v1/invites/revoke` を使う。招待コードや鍵を URL に入れず、すべて本文で渡す。
- 有効期限の上限は 30 分。期限切れと失効の記録は 24 時間残し、その間は `INVITE_EXPIRED` と `INVITE_REVOKED` を区別して返す。
- 失効用の鍵は 256 bit の乱数で、サーバーはハッシュだけを保持し、定数時間で照合する。

### UDP

- 1 つのポートで受け、先頭で振り分ける。STUN は先頭 2 bit が 0 で 4 バイト目から Magic Cookie（`0x2112A442`）があるもの、ランデブーメッセージは `VRZ` で始まるもの。どちらでもないパケットと不正なパケットには応答しない。
- STUN は RFC 8489 の Binding だけを実装し、認証はしない。応答には XOR-MAPPED-ADDRESS、SOFTWARE、FINGERPRINT を付ける。
- ランデブーメッセージは REGISTER、REGISTERED、PUNCH の 3 種類（形式は `infra/rendezvous/internal/udpapi/wire.go`）。親機と子機は同じランデブー ID で REGISTER を送り、両者がそろうとサーバーが双方に PUNCH（相手のピア ID と候補アドレス）を同時に送る。受け取った双方が同時に相手へ送信して NAT のマッピングを開く。
- ランデブー ID は招待ではなくセッションに紐づける。招待の期限（30 分）を過ぎても、再接続のためにホールパンチをやり直せるようにするため。
- 登録はソフトステートで、30 秒更新がなければ消える。親機は 10 秒程度の間隔で REGISTER を送り直し、子機は接続できるまで再送する。

### 状態とホスティング

- 招待と登録はメモリにだけ置く（単一ノード）。SQLite などの永続化はしない。
- 設定はコマンドライン引数だけで受け取り、クラウド固有の SDK やサービスに依存しない。TLS はバイナリ自身が終端するか（`-tls-cert`、`-tls-key`）、前段のリバースプロキシやロードバランサーに任せる。

## 理由

- 招待の寿命は 30 分なので、再起動で招待が消えても、親機が招待を作り直せば済む。メモリだけにすると、外部ライブラリ（SQLite のドライバー）もディスクも要らず、単一バイナリのまま動かせる。
- 招待コードは参加を申請する権利しか与えず、音声は親機が承認するまで流れない。50 bit と 30 分の寿命があれば、総当たりで有効なコードを引き当てる確率は実用上無視できる。そのうえで、読み上げや手入力がしやすい長さにした。
- 招待コードを本文で渡すと、前段のプロキシやホスティングのアクセスログに招待コードが残らない（ADR-0006 で招待コードをフラグメントに入れたのと同じ理由）。
- PUNCH を双方に同時に送れば、別途の時刻同期なしでホールパンチの開始をそろえられる。子機が REGISTER を再送するたびに PUNCH も再送されるので、パケットが失われても再試行になる。
- 不正なパケットに応答しないのは、送信元を偽装した反射攻撃の踏み台にならないようにするため。候補アドレスから未指定アドレス、マルチキャスト、ポート 0 を除くのも、相手を無意味な宛先へ誘導させないため。
- コマンドライン引数だけで動く単一バイナリなら、VPS でもコンテナ基盤でも同じ形で動かせる。

## 結果

- UDP を受けられるホスティングが必要になる。VPS や仮想マシン（さくらの VPS、Google Compute Engine など）では動くが、UDP を受けられないサーバーレス基盤（Cloud Run、Cloudflare Workers など）では HTTP 側しか動かない。HTTP 側だけを別のホストに分けることはできる。
- 招待の登録に認証はないので、上限（10 万件）まで招待を作られると新しい招待を作れなくなる。運用で問題になったら、前段でのレート制限か、登録 API の認証を追加する。
- 親機と子機のクライアント実装（`session`、`network`）は、HTTP は `internal/httpapi/invites.go`、UDP は `internal/udpapi/wire.go` の定義に合わせる。
- 複数ノードへの拡張や将来の中継は、このプロトコルを変えずに別のホストへ追加できるよう、状態を持つ部分を `invite` と `signaling` に閉じ込めておく。
