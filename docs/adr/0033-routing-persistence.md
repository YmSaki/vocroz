# 0033. ルーティングの構成の保存と復元、ルーティング画面の開き方

- 状態: 採用（2026-11-09）

## コンテキスト

ADR-0026 で、ルーティングの構成は「ステージング → 検証 → 承認 → 適用」の順にだけ変わり、新しいバスとセンドはミュートで作ると決めた。
バスと追加の出力は、セッションを終えても残す（`HostContext::teardown()`）。
残っているのは、アプリを終了して起動し直したときに構成をどこまで戻すかと、ルーティング画面をどう開くかである。

構成を保存するにあたっての制約は次のとおり。

- チャンネルストリップの `entity_id`（`ch1` など）は、セッションごとに参加の順で振り直す。前回の `ch1` と今回の `ch1` は別の参加者である。
- 起動時、再起動時は、チャンネル、Master、子機の送信をすべてミュートで始める（初期ミュート）。保存した値で音が出る状態に戻ってはならない。
- ループの承認は適用 1 回ごとに求める（ADR-0026）。
- 設定ファイルは外部入力で、壊れていることも、古いバージョンが書いたものであることもある。

ルーティング画面は、ADR-0009 で `webui` が独立したサブウィンドウとしてホストすると決めている。
ただし、親機モードの `remote-pa` は `webui` の `MessageChannel` 1 本を `pa-engine` への名前付きパイプ 1 本に中継している（ADR-0020）。
サブウィンドウにするには、2 つ目の WebView と 2 本目の接続（か、1 本の接続の多重化）が要る。

## 決定

### 保存するもの

- 親機の設定（`HostSettings`）に、適用中の構成のうちストリップを参照しない部分（`routing`）と、そのバスとセンドのフェーダーの値（`route_gains`）を足す。
  - 保存するのは、バス、追加の出力、遅延ノードと、Master とそれらの間のセンドである。ストリップを端点とするセンドと、入力の手動ディレイは保存しない（`without_strip_references()`）。ストリップの ID が次の起動では別の参加者を指すためである。
  - ストリップの判定は「構成の中で定義されていない端点」とする。ストリップの ID には決まった接頭辞がないため。
  - ミュートは保存しない。ステージング中の構成と、ループの承認も保存しない。
- 保存するのは、適用したとき（`commit_routing` の成功）とセッションの終了時（既存の `teardown()`）である。本番中にアプリが落ちても、最後に適用したバスと出力の構成に戻れるようにするため。
- 設定ファイルの形式のバージョン（`schema_version`）は 1 のまま上げない。`routing` と `route_gains` がないファイルは、ルーティングを保存する前のファイルとして既定の結線で読み、ほかの設定は引き継ぐ。どちらか一方だけがある、形が合わない、という場合は、ほかの欄と同じく壊れたファイルとして扱う（ADR-0027 のバックアップからの復元に回る）。
- 列挙型の名前（`user`、`cue`、`post_fader`、`pre_fader`）は、設定ファイルの形式として `persistence` で別に持つ。UI との形式（`control-protocol`）とは変更の理由が違い、UI との形式を変えても保存済みのファイルは読めなければならないため。
- 診断レポートでは、セッション名と同じく、バスと出力の名前を伏せる。オペレーターが自由に付ける名前で、人名が入りうるため。

### 起動時の復元

`HostSession::start()` で、Master をミュートにしたあとに `HostContext::restore_routing()` を呼ぶ。

1. 保存した構成からストリップへの参照を取り除き（念のため読み込み時にも行う）、ストリップがない状態でステージングして検証する。
2. 問題（`RoutingIssue`）があれば、ステージングを捨てて既定の結線（構成なし）で起動し、警告をログに残す。上限の変更などで前回の構成が通らなくなった場合も、音を出さない側に倒す（フェイルセーフ）。
3. 遅延ノードを通るループがあれば、ステージングに置いたまま起動する。承認は適用 1 回ごとなので、起動のたびにオペレーターがルーティング画面で承認して適用する。
4. それ以外は、そのままミキサーに適用する。ミキサーが受け付けなければ、ステージングを捨てて既定の結線で起動する。
5. 適用したバスとセンドは、保存したフェーダーの値（+10 dB に丸める）とミュートで始める。

### ルーティング画面の開き方

- ルーティング画面（`ui/src/screens/routing/`）は、当面はミキサー画面と同じウィンドウで切り替えて開く。ミキサー画面のツールバーの「ルーティング」で開き、「ミキサーに戻る」で戻る。切り替えは `main.ts` が行い、ストアは 2 つの画面で共有する。
- 独立したサブウィンドウ（ADR-0009）は、`webui` が 2 つ目の WebView と接続を扱えるようになってから移す。画面はストアとクライアントを props で受け取る Container にしてあり、サブウィンドウでも同じ画面をそのままマウントできる。
- 編集はすべて `stage_routing` で構成全体をエンジンへ送り、表示はエンジンから戻ったステージング中の構成と検証の結果で行う。画面は編集中の構成を持たない（エンジン主権）。文字と数値の欄は確定したときにだけ送る。
- ループの承認は、モーダルダイアログではなく画面の上部のチェックボックスで行う。モーダルダイアログは不可逆操作の確認だけに使う規則（AGENTS.md 第 12 節）に従うためで、承認はステージングの revision ごとに外れる。
- 新しい項目の `entity_id` は、適用中の構成とレベルで使っている ID を避けて振る。消したバスと同じ ID で新しいバスを作ると、エンジンが前のバスのフェーダーとミュートの解除を引き継ぎ、新しいバスがミュートで始まらなくなるため。

### フェイクエンジン

開発用のフェイクエンジン（`ui/src/ipc/fake-engine/fake-routing.ts`）で、ステージング、検証、承認、適用、レベル、ストリップの削除の反映を再現する。
規則の正本は `session` の `routing_validator` で、フェイクエンジンは画面の開発のための写しとする。件数の上限など、画面で再現する必要のない規則は省く。

## 理由

- ストリップを参照する結線まで保存するには、参加者を ID 以外（表示名など）で突き合わせる規則が要る。表示名は参加者が自由に変えられ、同じ名前の参加者もいるので、別の参加者の音を返しやキューに送る事故の元になる。バスと出力の骨組みだけを戻し、ストリップからの送りはセッションごとに作り直すほうが安全である。
- 保存したループを自動で適用すると、起動の直後に発振しうる経路が、オペレーターが確かめないまま組まれる。ステージングに置いて承認を待てば、画面でループのノードを確かめてから適用できる。
- 設定のバージョンを上げると、P1 で保存した既存のファイルが壊れたものとして扱われ、セッション名や出力デバイスの選択まで失われる。欄を足すだけなので、ない場合を既定値として読むほうが利用者の負担が少ない。
- サブウィンドウは `webui` と `remote-pa` の接続の構成を変える作業で、ルーティングの機能とは独立に進められる。同じウィンドウでの切り替えなら、今の 1 本の接続のままで画面を使い始められる。

## 結果

- 起動し直しても、バス、追加の出力、遅延ノードと、その間のセンドとフェーダーが戻る。バスとセンドはミュートで始まるので、オペレーターがミュートを解除するまで新しい経路から音は出ない。
- ストリップからの送りと入力の手動ディレイは、セッションごとにルーティング画面で作り直す必要がある。
- ループを含む構成は、起動のたびに承認して適用する必要がある。
- ルーティング画面を開いている間はミキサー画面が見えない。サブウィンドウへの移行は `webui` の作業として残る。
