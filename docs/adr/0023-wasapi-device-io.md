# 0023. オーディオデバイスの入出力は WASAPI を直接呼び、抜去は通知だけにする

- 状態: 採用（2026-11-08）

## コンテキスト

audio-core は `AudioOutput` と `AudioInput` のポートを定め、48kHz Float32 でコールバックを呼ぶこと、デバイスのレートが違えば実装側で変換すること、抜去を `AudioDeviceListener::on_device_lost()` で通知し、別のデバイスへフォールバックしないことを契約にしている。
仕様書は、出力デバイスを OS の既定のデバイスではなく永続的な ID で指定すること、抜去したら Master を `SAFETY MUTE` にして警告を出し、既定のデバイスに音を流さないこと、低遅延の共有モードを使えるなら使うことを求めている。
実装手段の候補は、WASAPI を直接呼ぶ方法と、JUCE の `AudioIODevice`（`AudioDeviceManager`）を使う方法の 2 つである。

## 決定

- **実装手段**: `device` のアダプターは WASAPI（MMDevice API と `IAudioClient`）を直接呼ぶ。JUCE の `AudioIODevice` は使わない。
- **デバイスの指定**: エンドポイント ID（`IMMDevice::GetId()`）で指定し、`IMMDeviceEnumerator::GetDevice()` でそのデバイスだけを開く。ID が解決できない、有効でない、向きが違う場合は `kDeviceNotFound` で失敗し、既定のデバイスを開かない。空の ID も「その ID のデバイスはない」として扱う。
- **ストリームの開き方**: 共有モードのイベント駆動で開く。デバイスのミックスフォーマットがすでに 48kHz Float32 で、`IAudioClient3` がエンジンの周期を返したら、低遅延共有モード（`InitializeSharedAudioStream`、エンジンの最小周期）で開く。それ以外のデバイスと、低遅延共有モードを断るドライバーでは、通常の共有モードで 48kHz Float32 を指定し、`AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM | SRC_DEFAULT_QUALITY` でレートとサンプル形式の変換を OS に任せる。排他モードは Alpha では使わない。
- **抜去の検知**: オーディオスレッドのループで、WASAPI の呼び出しが失敗したら（抜去と無効化は `AUDCLNT_E_DEVICE_INVALIDATED`）、ストリームを止めて `on_device_lost()` を 1 回呼ぶ。抜去でイベントが届かなくなった場合に備え、100ms イベントが届かなければバッファの状態を問い合わせて失敗を拾う。抜去以外の失敗も、フェイルセーフのため同じく止めて通知する。Master のミュートと警告は通知を受けた側（session と `Mixer::engage_safety_mute()`）が行う。挿し直しても自動では開き直さない。
- **スレッド**: ストリームごとに専用のオーディオスレッドを作り、MMCSS の「Pro Audio」に登録する（ADR-0008）。ストリームの COM オブジェクトはそのスレッドの中だけで作って使う。
- **子機のマイク入力**: `device` の `AudioInput`（`make_wasapi_audio_input()`）を、子機のマイク入力と親機のローカル入力の両方に使う。`capture` には Beta の WASAPI ループバック（アプリ音声の収集）だけを置く。「入力なし」は `AudioInput` を作らない選択として子機のロジックが持ち、`device` は関与しない。
- **デバイスの一覧**: 選択画面と、保存した ID がまだあるかの確認のため、audio-core に `AudioDeviceCatalog` ポートを置き、`device` が実装する。一覧は有効なデバイスだけを返し、既定のデバイスには表示用の印だけを付ける。

## 理由

- **WASAPI を直接呼ぶ理由**: JUCE の WASAPI 実装はデバイスを表示名で指定し、エンドポイント ID を公開 API で扱えない。同じ機種を 2 台つないだときや、利用者が名前を変えたときに、保存したデバイスを確実に開き直せない。また、JUCE の `AudioDeviceManager` は入力と出力を 1 つの組として開き、デバイスの変化に応じて開き直す振る舞いを持つため、「抜去したら止めて通知するだけ」という契約を守るには、その振る舞いを抑える工夫が別に要る。必要な WASAPI の範囲（ID での指定、共有モード、イベント駆動、`IAudioClient3`）は狭く、直接呼んだほうがコードが短く、振る舞いを把握しやすい。JUCE は WebView と VST3 のために引き続き使う。
- **リサンプリングを OS に任せる理由**: 低遅延共有モードはフォーマットの変換をしないため、48kHz でないデバイスでは通常の共有モードになる。そのとき OS の変換を使えば、自前のリサンプラーと、レート変換のためのバッファリングを持たずに済む。合奏で使うデバイスは 48kHz に設定するよう案内し、48kHz のデバイスでは変換のない低遅延の経路を通す。
- **ID で開けば自動で切り替わらない理由**: Windows のストリームの自動切り替えは、既定のデバイスとして開いたストリームにだけ働く。特定の ID で開いたストリームは、抜去されると無効になるだけで、別のデバイスへは移らない。
- **マイク入力を `device` に置く理由**: 入力と出力で、ID の解決、ストリームの開き方、抜去の検知、MMCSS への登録は同じ知識である。アダプター同士は依存できない（AGENTS.md 4.1）ので、`capture` に別に書くと同じ知識が 2 か所にできる。

## 結果

- `modules/device` を追加する。OS に依存しない判断（ストリームの開き方）は `src/detail/stream_plan` に置き、Linux の CI でも単体テストする。WASAPI を呼ぶ部分は `src/win/` に置き、Windows の CI で、デバイスがない環境でも通るテスト（ID の解決の失敗など）を実行する。
- 48kHz でないデバイスでは、OS の変換のぶんだけ遅延が増える。受け入れテストでは、デバイスを 48kHz に設定した状態で測る。
- 抜去の検知から Master の安全ミュートまでの接続（session）は、S1（#13）と E1（#21）で行う。
- AGENTS.md 3.3 の `device` の行にこの決定を追記し、`capture` の行の「子機のマイク入力」を「持たない責務」の列に移す。
- WASAPI のループバック（Beta）を実装するときに、`device` のストリームの知識との重複を見て、置き場所（`capture` か `device` か）を決め直す。
