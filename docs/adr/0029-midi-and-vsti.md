# 0029. MIDI のタイミング、順序、Panic、ルーティングと、子機からの MIDI の形式

- 状態: 採用（2026-11-09）

## コンテキスト

Beta5 では、MIDI で VST3 インストゥルメント（VSTi）を鳴らせるようにする（B5、Issue #30）。
仕様書の合格条件は、発音タイミング、Note Off の確実な処理、通信切断時の音残り（Stuck Note）を防ぐ試験に合格すること。

置き場所と大枠はすでに決まっている。

- ADR-0009: MIDI の値型、タイムスタンプからサンプルオフセットへの変換、MIDI のルーティング、発音中のノートの追跡と Panic は `audio-core`。MIDI デバイスの入力は `device`、VSTi は `plugin-host`、承認済みの子機だけを受け付ける判断と切断時の Panic の指示は `session`。子機からの MIDI は信頼制御層の上の MIDI 専用チャンネルで送る。
- ADR-0019: 信頼制御層のレーン 1 を MIDI に使う。レーンごとに連番と再送が独立で、制御メッセージの再送待ちで MIDI を止めない。
- ADR-0024: プラグインノードの `process()` は、ブロック内の `MidiEvent` の範囲を受け取る。入力 0 のプラグインノードが VSTi。

この ADR では、残っていた次の点を決める。

- タイムスタンプ（実時間）をブロック内のサンプル位置にどう写すか。遅延とタイミングの揺れのどちらを優先するか
- Note On と Note Off の順序をどう保証するか
- MIDI の経路を、PCM の結線とは独立にどう記述するか
- どんなときに Panic を出し、何を送るか
- 子機から送る MIDI のメッセージの形式と、子機の時計の扱い

低レイテンシは必須要件で、オーディオスレッドでは第 9 節のリアルタイム制約に従う。

## 決定

### タイムスタンプからサンプル位置への変換

- MIDI の入力 1 系統（MIDI デバイス 1 台、子機 1 台）ごとに、`audio-core` の `MidiInputQueue` を 1 つ置く。生産者のスレッド（MIDI デバイスのコールバック、ネットワーク受信スレッド）がタイムスタンプ付きのメッセージを SPSC キューに積み、オーディオスレッドがブロックごとに取り出す。
- タイムスタンプは `common::Clock` と同じ基準（`steady_clock`）の時刻にする。`Mixer` に時計を注入すると、デバイスのコールバックの先頭で時刻を読み、その時刻と、そのコールバックの先頭のサンプル位置（出力した累計サンプル数）を対応づける（`MidiBlockClock`）。コールバックを `kBlockSize` に分けた各ブロックは、同じ対応を使う。
- イベントを鳴らすサンプル位置は「コールバックの先頭のサンプル位置 + タイムスタンプからコールバックの先頭までの経過（負）+ `schedule_ahead_samples`」とする。
  - ブロックより前に当たるイベント（遅れて届いた）は、捨てずにブロックの先頭に置く。Note Off を捨てると音残りになるため。
  - ブロックより後に当たるイベントは、次のブロックへ持ち越す。持ち越したイベントより後に届いたものも一緒に持ち越す。
  - コールバックの先頭より後のタイムスタンプは、先頭の時刻とみなす。時計のずれたイベントを未来の時刻のまま信じると、いつまでも鳴らず後続も詰まるため。持ち越しは最大でも `schedule_ahead_samples` に収まる。
- `schedule_ahead_samples` は入力ごとに `session` が決める。既定は 0 で、届いたブロックの先頭で鳴らす（遅延が最小、タイミングはブロック長ぶん揺れる）。デバイスのコールバック長にすると、タイミングの揺れがなくなる代わりに、遅延がその長さだけ増える（128 サンプルなら 2.7ms）。
- 時計を注入しない `Mixer` では、すべてのイベントをブロックの先頭に置く（既存の構成と結合テストはそのまま動く）。

### 順序の保証

- 1 つの入力の中では、届いた順を変えない。タイムスタンプが前後していても、前のイベントより前のサンプル位置には置かない（位置を単調非減少にする）。タイムスタンプの順に並べ替えると、同じノートの Note Off が Note On より先に処理され、音が止まらなくなることがあるため。
- 1 ブロックに取り出す数には上限（`kMaxMidiEventsPerBlock`、256 件）がある。超えたぶんは捨てずにキューに残し、次のブロックの先頭で送る。
- 複数の入力を 1 つのプラグインへつないだときは、サンプル位置の順に合わせる。同じ位置は、経路を記述した順（`midi_connections` の順）にする。

### MIDI の経路

- MIDI の経路は PCM の結線とは独立に、`GraphDescription` の `midi_sources`（`MidiSourceId` と `MidiSource`）と `midi_connections`（ソースからプラグインノードへ）で記述する。MIDI ソースはノードではない。音声のチャンネル数、処理順、ループの検出、PDC に関わらないので、ノードにすると検証規則に例外が増えるため。
- 送り先はプラグインノードだけ。1 つのソースを複数のプラグインへ、複数のソースを 1 つのプラグインへつないでよい。同じ経路の重複、存在しないソースやノード、プラグインでない送り先は `kInvalidMidiConnection`。重複を受け付けると、同じイベントが 2 回届き、1 回目の Note Off で止まった音を 2 回目の Note On で鳴らし直すことがあるため。
- グラフは 1 ブロックに 1 回だけ、各ソースから取り出す。
- MIDI のチャンネルによる振り分け（チャンネル 1 だけをこの音源へ、など）は、この ADR では扱わない。必要になったら経路にフィルターを加える。
- MIDI の経路の追加と変更は、PCM の結線と同じくグラフの記述し直しと差し替えで行う。ルーティングのステージング（ADR-0018）にそのまま乗る。

### 発音中のノートの追跡と Panic

- 経路（ソース → プラグイン）ごとに、送った Note On のうちまだ Note Off を送っていないノートと、踏まれたサステインペダルを追跡する（`ActiveNotes`）。ベロシティ 0 の Note On は Note Off とみなす。All Sound Off と All Notes Off はそのチャンネルのノートを止めたとみなす（ペダルの状態は変えない）。
- Panic では、追跡しているノートすべてに Note Off を送り、続けて踏まれているペダルにサステインのオフ（CC 64 = 0）を送る。CC 123（All Notes Off）を送るだけにしないのは、VST3 では MIDI の CC がプラグインのパラメーターへ写されるだけで、All Notes Off を解釈しないプラグインがあるため。Note Off はそのブロックの先頭に置き、同じブロックの新しいイベントより前に送る。
- Panic を出す場面は次のとおり。
  - `session` が `MidiInputQueue::request_panic()` を呼ぶ: 子機の `LOST`、MIDI デバイスの抜去、オペレーターの Panic の操作。未送信のメッセージは捨てる。残すと、Note Off の後に古い Note On が届いて音が戻るため。
  - キューがあふれて、止める側のメッセージ（Note Off、ペダルのオフ、All Sound Off、All Notes Off）を落としたとき。自動で Panic にする（フェイルセーフ、AGENTS.md 1.2）。Note On を落としても音が鳴らないだけで残らないので、Panic にしない。
  - グラフの差し替えで経路が外れたとき。外れた経路で発音中だったノートに、差し替え後の最初のブロックで Note Off を送る。同じソースと同じプラグインの経路が残るなら状態を引き継ぎ、Note Off は送らない（ルーティングの別の変更で演奏中の音を切らないため）。引き継ぎは、オーディオスレッドが新しいグラフを取り込み、古いグラフを退役させる直前に行う。退役後はコントロールスレッドがいつ破棄してもよいため。
- プラグインごとグラフから外した場合は、そのプラグインを処理しないので Note Off を送れない。同じプラグインを再び挿す前に、`session` がプラグインをリセットする。

### 子機からの MIDI

- 子機は MIDI を信頼制御層のレーン 1（ADR-0019）で送る。順序と到達は信頼制御層が保証する。メッセージの形式は、制御メッセージと同じく `session/src/wire/` に置く（ADR-0022、AGENTS.md 4.4）。
- 1 つのメッセージは、先頭 1 バイトの種別（MIDI イベント）に続けて、イベントを 1 件以上並べる。各イベントは、子機の時計での時刻（マイクロ秒、32 ビット、ビッグエンディアン、桁あふれで一周する）と、チャンネルメッセージ（1〜3 バイト、長さはステータスバイトで決まる）。ランニングステータス、SysEx、システムメッセージは送らない。余分なバイトや不正なメッセージを含むメッセージは全体を捨てる（信頼境界、AGENTS.md 6.3）。
- 子機は打鍵ごとにすぐ送る。まとめて送ると、まとめる時間だけ遅延が増えるため。
- 親機は、子機の時刻を親機の時計に写してから `MidiInputQueue` に積む。写し方は「受信時刻 − 子機の時刻」の直近の最小値（片道の遅延の最小値）を差として使う。最小値を使うと、写した時刻は受信時刻より後にならず、ネットワークの揺れで生じた間隔のずれを、`schedule_ahead_samples` の範囲で元の間隔に戻せる。子機の時計の進み方のずれ（クロックドリフト）は、直近の窓の中で最小値を取り直すことで追う。
- 子機の MIDI の `schedule_ahead_samples` の既定は 0 とし、到着したブロックの先頭で鳴らす（遅延を最小にする）。揺れの吸収を優先する演目では、`session` が入力ごとに増やせる。
- 承認済みの子機のメッセージだけを `MidiInputQueue` に積む判断は `session` が持つ（ADR-0009）。

## 理由

- **一定の遅延を足すか、揺れを許すかを入力ごとに選べるようにした**: 合奏では低遅延が必須で、既定は遅延を足さない側にした。一方で、一定の遅延は演奏者が慣れられるが、揺れは慣れられない。MIDI デバイスの直結のように遅延の小さい入力では、コールバック長の遅延を足してでも揺れをなくしたい場面がある。規則は 1 つにして、数値だけを `session` が選ぶ。
- **時刻の対応はコールバックの先頭で 1 回だけ読む**: `Mixer` はコールバックを `kBlockSize` に分けて連続で処理するので、ブロックごとに時刻を読むと、2 つ目以降のブロックがほぼ同じ時刻になり、サンプル位置の対応が崩れる。デバイスのポート（`AudioRenderCallback`）に時刻を足す方法は、`device` と結合テストの実装を変えることになるので採らなかった。
- **ソースをノードにしない**: MIDI は音声のチャンネル数、処理順、PDC、ループの規則と関わらない。ノードにすると、それぞれの検証に「MIDI ソースは除く」という例外が要る。
- **追跡を経路ごとにした**: ソースごとに追跡すると、経路を外したときに、どのプラグインへどのノートを送ったかが分からない。プラグインごとに追跡すると、1 つのソースの Panic で別のソースのノートまで止めてしまう。経路ごとなら、Panic も差し替えも、そのノートを受け取ったプラグインにだけ Note Off を送れる。1 経路の状態は 272 バイトで、全ノートの Note Off（2048 件）とペダルのオフ（16 件）が必ず入る領域を構築時に確保する。
- **子機の MIDI に専用ストリームを作らない**: ADR-0009 のとおり、到達の保証を優先する。冗長化（同じイベントを複数回送る）の専用方式は、信頼制御層の再送より速く届く場面がある一方、重複の除去と順序の保証を別に作ることになる。再送が起きたときの遅れは、音の欠落や音残りより影響が小さい。
- **子機の時刻を最小の片道遅延で写す**: 子機と親機の時計の差は直接は分からないが、最小の片道遅延を差とみなせば、写した時刻が受信時刻を追い越さない。追い越さないので、持ち越しが `schedule_ahead_samples` を超えることもない。

## 結果

- `audio-core` に、`MidiSource` ポート、`MidiInputQueue`、MIDI メッセージの判定と組み立て（`midi_message.h`）、`GraphDescription` の MIDI の経路と、`GraphError` の `kDuplicateMidiSource`、`kMissingMidiSource`、`kInvalidMidiConnection` を加える。`Mixer` に時計を受け取るコンストラクターを加える。既存の構成と API の振る舞いは変えない。
- MIDI デバイスの入力（`device`、JUCE の `MidiInput`）、子機の MIDI のメッセージ（`session/src/wire/`）と時刻の写し方、承認と `LOST` の Panic（`session`）、VSTi のホスト（`plugin-host` の `JucePluginProcessor` が `MidiEvent` を JUCE の `MidiBuffer` に写す）は、この ADR に従って続く PR で加える。
- ADR-0009 の `MidiInput` ポート（MIDI デバイスの列挙、開閉、抜去の通知）は、`device` の PR で `audio-core` に定義する。デバイスから届いたメッセージは、そのデバイスの `MidiInputQueue` に積む。グラフが取り出す側のポートは `MidiSource` で、`MidiInput` とは役割が違う。
- MIDI のチャンネルによる振り分けと、MIDI のクロックや SysEx は扱わない。必要になったら ADR を追加する。
- `plugin-host` の `JucePluginProcessor` は、`MidiEvent` を JUCE の `MidiBuffer` の内部形式（int32 のサンプル位置、uint16 の長さ、本体）で末尾に直接書き足し、`MidiBuffer` の内部形式に依存する。`MidiBuffer::addEvent()` は挿入位置を先頭から線形に探すので件数の 2 乗の時間がかかり、Panic の 2,064 件で約 4.5 ms と、1 ブロック（128 サンプル、約 2.7 ms）を超えるためである。JUCE を更新するときは、`plugin-host` の読み戻しのテスト（`JucePluginProcessorTest.PluginReadsBackTheSameMidiEventsInOrder`）が通ることを確かめる。
