# 0019. 信頼制御層（制御メッセージの再送、キープアライブ、死活監視、再接続のバックオフ）

- 状態: 採用（2026-11-08）

## コンテキスト

仕様書は、参加承認、ミュート状態の通知、キープアライブなどの制御メッセージを、メディアと同じ UDP セッションの上の再送付き信頼メッセージ層で送るよう求めている（SCTP と DataChannel は使わない）。
キープアライブは音声が流れていない間も 1 秒間隔で送り、音声と制御のどちらも 5 秒届かなければ接続状態を `RECONNECTING` に移す。
回線の瞬断時は 1、2、4、8、15 秒（ジッター付き）の間隔で再接続を試みる。
ADR-0009 は、子機からの MIDI をこの層の上の専用チャンネルで送り、他の制御メッセージとは順序を共有しないと決めている。
ADR-0014 は、制御パケットの暗号文側を、この層が決める不透明なバイト列とした（空ならキープアライブ）。

## 決定

### 制御パケットの平文

フレームを隙間なく並べる。整数はビッグエンディアン。空の平文はキープアライブで、フレームを持たない。

| フレーム | 内容 |
| --- | --- |
| ACK（種別 1、14 バイト） | 種別（1）、レーン（1）、累積 ACK（4、次に受け取りたい連番）、選択 ACK（8、ビット i が連番「累積 ACK + 1 + i」の受信済みを表す） |
| データ（種別 2、8 バイト + 本文） | 種別（1）、レーン（1）、連番（4）、本文の長さ（2）、本文（制御メッセージ 1 つ） |

- レーンは 0（制御）と 1（MIDI）。連番、窓、ACK はレーンごとに独立で、あるレーンの再送待ちで別のレーンを止めない。
- 未知のフレーム種別、未知のレーン、途中で切れたフレーム、送っていない連番を受信済みとする ACK を含むパケットは、全体を不正として捨て、どのフレームも適用しない。
- メッセージ 1 つの最大長は 1166 バイトで、全レーンの ACK と一緒に 1 つのパケット（平文 1202 バイト）に必ず収まる。メッセージの分割と再構成は持たない。
- 連番は 0 から始め、2^32 - 1 は使わない（累積 ACK で「すべて受信済み」を表せなくなるため）。使い切ったら接続を張り直す。

### 送信と再送

- 送信要求とデータの受信のたびに、その場でパケットを送る（ACK を遅らせない）。ACK は送るべきメッセージに相乗りさせる。ACK だけのパケットには ACK を返さない。
- レーンごとに、ACK を待たずに送るのは最も古い未 ACK のメッセージから 64 個まで（選択 ACK で伝えきれる幅）。送信待ちはレーンごとに 256 個までで、超えたら送信をエラーで拒む。
- 再送タイムアウトは RFC 6298 の平滑化 RTT と変動から求め、下限 50ms、上限 1 秒、測定値がないときは 250ms にする。再送したメッセージの ACK からは RTT を測らない（Karn のアルゴリズム）。再送のたびにそのメッセージのタイムアウトを倍にする（上限 1 秒）。
- 輻輳制御は持たない。

### キープアライブと死活監視

- 制御パケットを 1 秒送らなければ、空の制御パケット（キープアライブ）を送る。
- 受信側は、認証に成功したパケット（メディアと制御）を受けるたびに最後の受信時刻を更新し、5 秒更新がなければ途絶をリスナーで外側に知らせる。途絶の後に同じ接続のパケットがまた届けば、再開を知らせる。
- 最後の受信時刻はネットワーク受信スレッドが原子変数に書き、コントロールスレッドが読んで判定する。

### 再接続のバックオフ

- 試行の間隔は 1、2、4、8、15 秒で、以降は 15 秒を繰り返す。各間隔に 80〜120% の一様なジッターを掛ける。乱数はポート（`RandomSource`）から得る。
- 再接続を始める時期、再接続猶予（120 秒）、成功の判断は `session` が行う。

### スレッドと暗号化の受け持ち

- 信頼制御層はコントロールスレッドで動き、制御パケットの平文までを作る。平文はポート（`ControlPacketSink`）に渡す。
- `PacketSealer` はメディアと制御でシーケンス番号を共有し、1 つのスレッドからしか使えない。そのため、どのスレッドで暗号化して送るかはコンポジションルートが決める。制御だけを送る方向では、暗号化してソケットのポート（`DatagramSocket`）で送る `SecureControlPacketSink` をそのまま使える。

## 理由

- 選択 ACK と再送タイマーだけの最小の構成は、QUIC や SCTP の信頼性の部分と同じ考え方で、TCP のような先頭の欠落による全体の停止を、レーンの分離で MIDI と制御の間に持ち込まない。
- 制御メッセージは操作 1 回に 1 つ程度で帯域をほとんど使わないので、輻輳制御を持たなくても回線を圧迫しない。窓とキューの上限で送りすぎを防ぐ。
- ACK を遅らせず、再送タイムアウトの下限を TCP の 1 秒より大きく下げるのは、ミュート通知や承認の遅れが合奏の本番に直接響くため。上限を 1 秒にしたので、途絶の判定（5 秒）までに数回は再送できる。
- 不正なパケットを全体で捨てるのは、一部だけを適用して送受信の状態が食い違うのを防ぐため。相手は認証済みなので、不正なパケットが届くのは不具合か改変の場合だけになる。
- 平文までを信頼制御層の責務にすると、送信側のスレッド構成（制御スレッドで暗号化するか、オーディオスレッドに渡すか）を E1 と子機の組み立てで選べ、`PacketSealer` を複数のスレッドで共有する事故を避けられる。

## 結果

- 制御メッセージの中身（承認、ミュート通知の `(send_muted, epoch)`、入力なし通知など）の形式は、使う側（`session`）が決める。
- `pa-engine` と子機の組み立て（E1 と子機のコンポジションルート）は、ネットワーク受信スレッドで復号した制御パケットの平文をコントロールスレッドに渡し、`ReliableControlChannel::on_control_packet()` を呼ぶ。`LivenessMonitor::note_packet_received()` は受信スレッドで直接呼ぶ。`next_deadline()` で次に `tick()` と `poll()` を呼ぶ時刻を得る。
- 制御パケットの平文の形式を変えるときは、ADR-0014 のプロトコルバージョンを上げる。
