# 0026. ルーティングのステージングと適用、ループの承認、UI とのメッセージ

- 状態: 採用（2026-11-08）

## コンテキスト

ADR-0018 で、ルーティングのグラフ（センド、遅延ノード、手動ディレイ、複数の物理出力）と、ループの検出（`analyze_feedback()`）を `audio-core` に用意した。
ADR-0009 では、ステージングと承認の判断を `session` が持つと決めている。
残っているのは、ルーティング画面（B1a の UI）とエンジンの間で、構成をどの形でやり取りし、どの順で検証して適用するかである。

ルーティングの変更は、本番中に音の経路を一度に変える操作である。
編集の途中の構成がそのまま鳴ったり、意図しないループで発振したり、新しく作ったキューに参加者の音が勝手に出たりしてはならない（フェイルセーフと初期ミュート）。

## 決定

### 構成と entity

- ルーティング全体を 1 つの entity（`entity_id` は `routing`）として扱う。中身は、適用中の構成（`applied`）、ステージング中の構成と検証の結果（`staged`）、バスとセンドのレベル（`levels`）。
- 構成（`RoutingConfig`）は、バス、追加の出力、センド、遅延ノード、手動ディレイの 5 つの一覧で表す。UI は構成全体を送り、差分は送らない。構成は最大でもスナップショットに収まる大きさに制限するので（センド 128 本など）、差分の形を作るより単純で、検証も構成全体に対して 1 回で済む。
- ストリップから Master と、Master からメインの出力（デバイスのチャンネル 0 と 1）への結線は暗黙にあるものとし、構成には書かない。Alpha までの音の経路はルーティングを触らなくてもそのまま鳴り、ルーティングは「足す」操作だけになる。
- バス、出力、センド、遅延ノードの `entity_id` は UI が振り、種類ごとの接頭辞（`bus-`、`out-`、`send-`、`delay-`）で始める。ステージングの段階で新しいバスを参照するセンドを書けるよう UI に振らせ、エンジンが振る ID（`ch1`、`pending1`、`master` など）とは接頭辞で衝突を避ける。
- 遅延は UI に合わせて ms で表し、ミキサーへ渡すときに `session::delay_samples()` でサンプル数に換算する（最も近い整数に丸める）。検証と適用で丸め方を食い違わせないよう、換算はこの関数だけで行う。
- 追加の出力はステレオで、`device_channel` から 2 チャンネルに書く。メインの出力のチャンネルと、ほかの出力のチャンネルとは重ねられない。

### ステージング、検証、適用

1. `stage_routing`: UI が構成を送る。エンジンは検証して、構成と結果を `staged` に置く。問題があってもステージングは受け付け、理由（`RoutingIssue`）と原因の `entity_id` を返す。ルーティング画面が「どこが悪いか」を示せるようにするためで、ミキサーには何も渡さない。
2. `commit_routing`: エンジンはステージング中の構成を検証し直し（ステージングのあとにストリップが削除されていることがある）、問題がなければミキサーへ適用する。
3. `discard_routing`: ステージング中の構成を捨てる。

検証は「件数 → ID → 出力のチャンネル → 遅延 → センド → ループ」の順で、最初の問題だけを返す。
つなげない組み合わせは、ストリップへの入力、出力からの送り、自分自身への送り、暗黙の結線との重複、同じ組の重複である。
プリフェーダーの送り元はストリップとバスに限り、Master は認めない（Master のミュートを迂回する経路になるため）。

フェーダーの容量などミキサーのグラフの細部は、コンポジションルートが `Mixer::validate_graph()` と `apply_graph()` で確かめる。
ミキサーが受け付けなければ `ENGINE_ERROR` で拒否し、今のグラフで鳴らし続け、ステージングも残す。

### ループの承認

- 遅延ノードを通らないループがあれば `UNDELAYED_LOOP` とし、承認しても適用しない。
- 遅延ノードを通るループだけがあれば `needs_approval` を立て、ループのノードを `looped_entity_ids` で示す。`commit_routing` の `approve_feedback` が `true` のときだけ適用する。承認は適用 1 回ごとで、ステージングし直したら改めて承認が要る。
- 承認の有無で拒否するときのエラーコードは、ほかの「今の状態では適用できない」と同じ `INVALID_STATE` にする。理由は `staged.check` に出ているので、新しいエラーコードは作らない。

### revision とレベル

- `routing` の revision は、ステージング、適用、破棄と、ストリップの削除で適用中の構成から参照を取り除いたときに進める。検証のやり直しで結果だけが変わっても進めない（観測値のため。ADR-0015）。
- バスとセンドのフェーダーとミュートは、それぞれの `entity_id` の別の entity（`RouteLevel`）にする。フェーダーやミュートの操作で `routing` の revision を進めると、ステージング中の編集が REVISION_CONFLICT で弾かれるためである。ミュートは `set_route_mute`（revision を進める）、フェーダーは `set_gain`（seq で後勝ち、revision は進めない）で操作する。
- 新しいバスとセンドはミュートで 0 dB から始める（初期ミュート）。プリフェーダーのセンドは送り元のミュートで止まらないので、これがないと新規参加者の音がキューに出てしまう（ADR-0018）。同じ `entity_id` が残るものは、適用し直しても値を引き継ぐ。

### ストリップの削除とセッションの終了

ストリップを削除したら、それを参照するセンドと手動ディレイを適用中の構成から取り除いて適用し直す。
バス、出力、遅延ノードはセッションをまたいで残す。
ステージング中の構成は検証し直すだけで、中身は変えない（オペレーターの編集を勝手に書き換えないため）。

### ミキサーのポート

`MixerControl` に `apply_routing()`、`set_route_muted()`、`set_route_gain()` を足す。
構成から `GraphDescription` への変換（ノードと結線、フェーダーとメーターの割り当て、暗黙の結線）は、E1（`pa-engine` の組み立て）で実装する。

## 理由

- ステージングと適用を分けると、編集の途中の構成が鳴らず、適用の直前に必ず検証と承認を通せる。
- 検証を `session` に置くと、UI に返す理由と原因の `entity_id` を、ミキサーの内部の識別子（`NodeId`、`FaderId`）を持ち出さずに作れる。ループの判定は `audio-core` の `analyze_feedback()` を使い、規則を二重に持たない。
- 構成全体を送ると、UI の「元に戻す」やプリセットの読み込みも、同じ 1 つのコマンドで表せる。

## 結果

- ルーティング画面（`ui/src/screens/routing/`）は E1 のあとに作る。それまでフェイクエンジンはルーティングのコマンドを `INVALID_STATE` で拒否する。
- 構成の永続化（設定ファイルへの保存と起動時の復元）はこの ADR の範囲外で、次の PR で決める。復元するときもバスとセンドはミュートで始める。
- 目標レイテンシーと実測ジッターの表示は、`transport` と `session` の統計の側で扱う。
