# 0025. 結合テストの試験基盤（障害注入、NAT の模擬、遅延計測）

- 状態: 採用（2026-11-08）

## コンテキスト

実機に触る前に、子機と親機の組み合わせを Linux の CI で繰り返し試したい（Issue #23）。
仕様書の受け入れテストのうち、AT-A02（承認前の遮断、直結とホールパンチの両経路）、AT-A03（3 台のミックス）、AT-A05（切断と同じストリップへの復帰）、AT-A06（悪条件の回線）、AT-A16（NAT 越え不成立の表示）、AT-A17（暗号化と改ざんの検出）は、回線の条件を人工的に作れれば CI で大部分を確かめられる。
合奏用途では低遅延が必須なので、端から端までの遅延が構成から見積もった範囲に収まることも、回線の条件ごとに確かめたい。

一方で、2026-11-08 の時点では transport（T1〜T3）とランデブーサーバー（R1）はあるが、session（S1）、network、子機とエンジンの組み立てはまだない。
AGENTS.md には、モジュールをまたぐ結合テストの置き場所がない（単体テストは各モジュールの `tests/`）。

## 決定

### 置き場所

トップレベルに `tests/` を作り、モジュールをまたぐ結合テストと、その試験基盤と試験ツールを置く。
`apps/` と同じく、すべてのモジュールに依存してよい。製品のターゲットからはリンクせず、インストーラーにも入れない。

```text
tests/
  netsim/       障害の設定と判定、プロセス内のネットワーク（ライブラリ vocroz_netsim）
  harness/      transport の部品を製品と同じ順序で組み立てる送信側と受信側、仮想時刻の駆動、遅延計測
  integration/  結合テスト（GoogleTest。ctest に登録する）
  tools/        試験ツール（vocroz-latency、vocroz-udp-fault-proxy）
  nat/          ネットワーク名前空間で NAT を模す試験のスクリプト
```

### 障害の模型は 1 つにする

遅延、ジッター、欠損、重複、順序の入れ替え、改ざん（1 ビットの反転）を、方向ごとの `FaultProfile` で表す。
1 パケットの扱いを決める `FaultInjector` は時刻もソケットも持たない純粋な判定にし、プロセス内のネットワーク（`SimulatedNetwork`）と実ソケットのプロキシ（`vocroz-udp-fault-proxy`）の両方が同じものを使う。
設定の文字列表現（`delay=20ms,jitter=5ms,loss=0.02,seed=7`）も 1 か所で定義し、テスト、ツール、手順書で同じ書き方を使う。

乱数は SplitMix64 と [0, 1) への変換を自前で固定する。
`std::uniform_real_distribution` は標準ライブラリごとに実装が違い、同じシードでも MSVC と libstdc++ で結果が変わるためである。
1 パケットで消費する乱数の数も固定し、欠損率だけを変えたときに揺らぎの列がずれないようにする。

### 結合テストは仮想時刻のプロセス内で動かす

結合テストは、`SimulatedNetwork` と `FakeClock` の上で、キャプチャのコールバック、ネットワークの配送、出力のコールバックをサンプル単位の仮想時刻で順に進める。
実時間を待たず、スレッドもソケットも使わないので、決定的に、短時間で、OS なしに何秒分の通信でも再現できる。
transport の `DatagramSocket` ポートは `SimulatedDatagramSocket` で実装し、製品で network（Winsock）が入る位置に差し込む。

S1 がマージされるまでは、ハンドシェイクはプロセス内で済ませ（`establish_secure_link()`）、送信ミュートの解除は受信側に直接渡す。
S1 のあとは、「エンジン + 子機 3 台」の結合テスト（承認前に音が届かない、3 台のミックス、1 台の切断で残りが途切れない、同じストリップへの復帰）を同じネットワークの上に足し、`harness/` の送信側と受信側は製品の組み立てに置き換える。

### 実ソケットのプロキシ

`vocroz-udp-fault-proxy` は子機と上流（親機かランデブーサーバー）の間に置く UDP のプロキシで、子機の送信元ごとに上流側のソケットを分ける（上流からは NAT と同じに見える）。
POSIX のソケットで書き、Linux だけでビルドする。Windows の実機確認では、WSL か、経路の途中に置いた Linux の機械で使う。

### NAT の模擬

Linux のネットワーク名前空間と iptables で、フルコーン、ポート制限、対称型の NAT を模す（`tests/nat/run-nat-matrix.sh`）。
NAT の組み合わせごとに名前空間を作り直し、ランデブーサーバーの実バイナリと、試験用のピア `punchprobe` を親機側と子機側で動かす。

`punchprobe`（`infra/rendezvous/cmd/punchprobe`、`internal/punchprobe`）は、親機と子機のクライアント実装ができるまでの代わりで、`internal/udpapi` のワイヤーフォーマットをそのまま使う（スキーマを 2 か所に書かない）。
結果は次の 4 つに分ける。

| 結果 | 意味 |
| --- | --- |
| `CONNECTED` | 相手との間で双方向に届いた |
| `UNREACHABLE` | サーバーから相手の候補を受け取ったが、双方向に届かなかった（製品の原因コード `UNREACHABLE`） |
| `RENDEZVOUS_UNREACHABLE` | サーバーから REGISTERED が返らなかった |
| `PEER_NOT_FOUND` | 登録はできたが、相手が同じランデブー ID で現れなかった |

`UNREACHABLE` 以外の 2 つは試験での原因の切り分けに使う区分で、製品の原因コードとして採用するかは session と network の実装（S1、N1）で決める。
`punchprobe` は相手から届いた送信元（ピア再帰アドレス）へも送り返す。片側だけが対称型の組み合わせでも通信を成立させるためで、製品のクライアントにも同じ振る舞いを求める。

この試験は root 権限が要るので、CI では専用のジョブ（`sudo` が使える ubuntu のランナー）で動かす。

### 遅延の計り方

無音の間に 1kHz のバーストを約 400ms ごとに送り、出力でバーストの立ち上がりを検出して、入力での立ち上がりとの差を遅延とする。
実際の伝送の部品（Opus、暗号化、ジッターバッファ、ドリフト補正）を通るので、部品のどこかに想定外のバッファが入れば計測値に表れる。
構成から内訳（キャプチャのブロック、フレーム、Opus の先読み、片道の遅延と揺らぎ、ジッターバッファの目標、出力のブロック）を計算し、計測値がその範囲に収まることを CI で確かめる。
デバイスの入出力の遅延はシミュレーションの外なので、指定した値を足して「口から耳まで」の見積もりにする。

## 理由

- 仮想時刻のプロセス内のテストは、スレッドの競合や CI の負荷による揺らぎがないので、CI を厳しくしすぎずに済む。障害の列もシードで固定でき、失敗したときに同じ条件を手元で再現できる。
- 障害の模型を C++ の 1 か所に置けば、結合テストとプロキシで規則がずれない。Go でプロキシを書けば Windows でもそのまま動くが、模型が C++ と Go の 2 か所に分かれ、同じシードで同じ障害にならなくなる。
- NAT の振る舞いは OS の実装そのものを使わないと確かめられない。名前空間と iptables なら、追加のソフトウェアなしで、ubuntu のランナーの上で組み合わせを作り直せる。
- 新しく conntrack に入る前の mangle の段階で外からの新しい接続を捨てるのは、相手の先着のパケットが conntrack に残ると、こちらの送信の外側ポートが変わり、ポート制限の NAT 同士でもホールパンチが成立しなくなるため。
- 遅延の内訳と計測値を並べれば、合奏に間に合わないときに、どの設定（フレーム長、ジッターバッファ、デバイスのブロック）を変えればよいかが分かる。

## 結果

- AGENTS.md の第 3.2 節（トップレベルのディレクトリ）、第 4.2 節（GoogleTest の使用範囲）、第 5.1 節（配置表）、第 17 節（コマンド）に `tests/` を追記する。
- Linux の CI に、NAT の模擬のジョブを足す。結合テストは既存の Linux と Windows のジョブの ctest で動く（`vocroz-udp-fault-proxy` は Linux だけ）。
- S1 のあと、「エンジン + 子機 3 台」の結合テストを `tests/integration/` に足す。session と network のクライアントができたら、NAT の模擬の `punchprobe` を製品のクライアントに置き換え、製品の原因コードとエラー表示を確かめる。
- 実際の回線での遅延（デバイスのバッファを含む）は、引き続き実機の手順書（`docs/testing/alpha-acceptance.md` の「参考の測定」）で、クリックの元の信号と出力を同じ録音機器で録って確かめる。
