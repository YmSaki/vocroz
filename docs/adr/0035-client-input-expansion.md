# 0035. 子機の入力拡張（ステレオ、複数の入力、アプリ音声）

- 状態: 採用（2026-11-09）

## コンテキスト

Alpha までの子機は、マイク 1 本をモノラルで送るだけだった。親機では 1 台の子機が 1 本のチャンネルストリップになる。
Beta では次の 3 つを送れるようにする。

- ステレオの入力（キーボードやオーディオインターフェースのライン入力）。
- 1 台の子機からの複数の入力（ボーカルのマイクとギターのライン入力など）。親機では入力ごとに別のストリップにして、オペレーターが別々にフェーダーとミュートを掛けられるようにする。
- WASAPI のループバックで集めたアプリ音声（伴奏の再生アプリなど）。

メディアパケットにはすでにストリーム ID（`transport` の `MediaPayload::stream_id`）がある。
一方で、どの ID がどの入力で、何チャンネルかを親機に伝える手段はなく、`session` の参加者は 1 台に 1 本のストリップを前提にしていた。
返送モニター（`docs/adr/0036-return-monitor.md`）が同じ時期に親機から子機への下りストリームを追加するので、ストリーム ID の扱いをそろえる必要もあった。

## 決定

### ステレオ

- 1 ストリームはモノラルかステレオ（`transport::kMaxStreamChannels = 2`）。サラウンドは扱わない。
- Opus はステレオでも 1 つのエンコーダーとデコーダーで符号化する（`OpusEncoderConfig::channels`、`OpusFrameDecoder::create(channels)`）。PCM はインターリーブで渡す。フレーム長（5ms）とアプリケーション（`RESTRICTED_LOWDELAY`）はモノラルと同じなので、ステレオにしても遅延は増えない。
- ステレオの目標ビットレートの目安は 192kbps（モノラルの 1.5 倍）。最終値はモノラルと同じく実測で決める。
- `PlayoutStream` はジッターバッファを 1 つ、クロックドリフト補正の `DriftResampler` をチャンネルごとに持ち、左右に同じ比率を掛ける。左右で比率がずれると定位が揺れるため。
- `audio-core` の `AudioSource` ポートはチャンネル数（`channel_count()`）を返し、チャンネルごとのバッファへ書き出す（`pull(float* const* channels, frames)`）。ストリップのチャンネル数（`NodeSpec::channels`）はソースのチャンネル数にそろえる（`pa-engine` の `MixerGraphBuilder`）。モノラルのストリップからステレオのバスへは、これまでどおり左右に同じ信号を送る。

### 複数の入力とストリーム ID

- 1 台の子機は最大 4 つの入力（`control_protocol::kMaxInputStreams`）を送れる。入力ごとにストリーム ID を子機が振る。ストリーム ID の空間は向きごとに別で、子機から親機への ID と、親機から子機への返送の ID は重ならない。
- 子機は入力の一覧を制御メッセージの `StreamsReport`（種別 0x06）で申告する。参加の申請と再接続の後と、入力の構成を変えたときに、一覧のすべてを送る。親機は前回の一覧と置き換える。差分を送らないのは、制御メッセージの順序や再送で一覧が食い違わないようにするため。
- 本文は `u8 個数（1〜4）`、続いて入力ごとに `u16 ストリーム ID（ビッグエンディアン）`、`u8 種類（1: マイク、2: アプリ音声）`、`u8 チャンネル数（1 か 2）`。ストリーム ID の重複を含め、信頼境界（`session/src/wire/`）で検証する。
- 申告を受け取る前の子機は、ストリーム 0 のモノラルのマイク 1 本とみなす。申告を送らない子機（Alpha の子機）も、これまでどおり 1 本のストリップで動く。

### 親機のストリップ

- `session` の参加者の登録簿は、これまでどおり 1 エントリーを 1 本のストリップにする。同じ子機のストリップは `participant_id`、接続、再接続トークン、接続状態を共有する。参加者の下にストリップの配列を持たせる形にしなかったのは、ミキサー、UI、ルーティングがストリップの `entity_id` だけで動いており、それらを変えずに済むため。
- 接続状態、信号状態、送信ミュートは子機ごとの値なので、同じ子機のストリップにそろえて写す（`HostContext::advance_participant`）。
- 申告が変わったら、ストリーム ID、種類、チャンネル数が同じ入力のストリップは残し、フェーダー、ミュート、ルーティングを保つ。種類かチャンネル数が変わった入力は、別の入力としてストリップを作り直す。チャンネル数の違うストリップは、ルーティングとミキサーでの扱いが変わるため。
- 新しいストリップはチャンネルミュートで始める（初期ミュート）。新しいストリップは同じ子機のストリップの後ろに足し、既存のストリップの並びを変えない。
- 承認の前に届いた申告は覚えておき、承認のときに入力の数だけストリップを作る。ストリップの上限（`kMaxChannelStrips`）に収まらなければ、承認を拒否する。承認後の申告で上限を超える入力は受け付けず、その入力のパケットは対応がないので受信側で捨てる（音の経路を増やさない側に倒す）。
- ストリップの表示用に、`ChannelStrip` に入力の種類（`source_kind`: `MICROPHONE`、`APP_AUDIO`）、チャンネル数（`channel_count`）、同じ種類の入力の通し番号（`source_number`、ストリーム ID の順で 1 から）を加える。UI はこれから「マイク 2」「アプリ音声」「ステレオ」などのラベルを作る。マイク 1 本だけのモノラルの子機ではラベルを出さず、これまでの表示を変えない。
- 切断した子機のストリップを削除するときは、その子機のストリップをすべて削除する。再接続トークンは子機ごとの値で、一部のストリップだけを残すと、戻ってきた子機の入力と食い違うため。
- `PeerLink::admit` は、接続とストリップ 1 本の組ではなく、ストリームごとの流し込み先（`StreamRoute`: ストリーム ID、チャンネル数、ストリップ）の一覧を受け取る。承認、再接続、申告の変更のたびに呼び、一覧を置き換える。

### 子機の入力の選び方

- 子機の画面で選べる入力は、マイク（モノラルかステレオ）とアプリ音声（常にステレオ）の 2 つにする。マイクは常に 1 本で、ストリーム ID は 0、アプリ音声は 1 に固定する（`session` の `kMicrophoneStreamId`、`kAppAudioStreamId`）。ID を固定すると、アプリ音声を足し引きしてもマイクの ID が変わらず、親機のマイクのストリップが保たれる。2 本目のマイクを送る構成は、子機に 2 本目の入力デバイスの選択が要るので、この ADR の範囲では扱わない（ワイヤーフォーマットと親機は 4 入力まで受けられる）。
- マイクのチャンネル数は子機の設定（`ClientSettings::input_channels`）に保存し、次の起動でも同じ構成で申告する。アプリ音声を送るかどうかは保存せず、起動のたびに送らない状態から始める。再生中の音が意図せず配信されないようにするため。
- 子機は入力の構成（`session::InputStream` の一覧）を `CaptureControl::set_streams` で受け取り、入力ごとにエンコーダーと `CaptureProcessor` を持つ（`client-desktop` の `ClientCapture`）。オーディオスレッドは入力のデバイスごとに別なので、エンコード済みのフレームは入力ごとの SPSC キューで送信スレッドへ渡す（プロデューサーを 1 つに保つため）。変わらない入力のキャプチャは止めない。

### アプリ音声

- WASAPI のループバックによるアプリ音声の収集は、`capture` モジュールの `AudioInput` の実装にする（AGENTS.md 3.3）。子機のマイク入力（`device`）と同じポートを実装するので、`CaptureProcessor` から先は入力の種類を区別しない。
- アプリ音声は既定で送らない。子機の画面で入力として加えたときだけ送る（送信は送信ミュートで始まる）。

## 理由

- ストリーム ID はすでにメディアパケットにあるので、ワイヤーフォーマット（`transport/src/wire/`）は変えずに済む。対応の申告だけを制御メッセージに足せばよい。
- Opus のステレオは 1 つのエンコーダーで符号化でき、左右を別のストリームで送るより、ビットレートと計算量が少なく、左右の同期もずれない。
- 1 エントリー 1 ストリップの形を保つと、ミキサー、ルーティング、UI の既存のコードと保存した構成を変えずに、子機の入力を増やせる。

## 結果

- 子機の画面で入力を足したり、ステレオに切り替えたりすると、親機のミキサーに新しいストリップがミュートで現れる。既存のストリップのフェーダーとルーティングは保たれる。
- `PeerLink` と `AudioSource` のポートのシグネチャが変わる。実装（`pa-engine` の受信、試験基盤の `SimulatedHost`）は流し込み先の一覧とチャンネル数を扱う。
- 保存したルーティングの構成は、これまでどおりストリップの `entity_id` で参照する。子機の入力を作り直したストリップは別の `entity_id` になるので、そのストリップを参照するルーティングは片付けられる。
- 子機側の申告、入力ごとの `CaptureProcessor`、子機の画面でのステレオの切り替えは、親機側の受け口の後に続けて実装した。ループバックの収集（`capture` モジュール）ができるまで、子機の画面のアプリ音声は開発中の表示にする。
