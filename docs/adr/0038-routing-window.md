# 0038. ルーティング画面を別の窓で開く

- 状態: 採用（2026-11-09）

## コンテキスト

ADR-0009 では、ルーティング画面などの独立したサブウィンドウを `webui` がホストすると決めた。
ADR-0033 では、まずはミキサーと同じ窓で画面を切り替えて開くことにし、別の窓にするのは後回しにした。
別の窓にするには、次の制約を満たす必要がある。

- `pa-engine` の名前付きパイプは、同時につながる UI を 1 つに限っている（ADR-0020）。窓ごとに接続を増やすことはできない。
- エンジンの応答（`ack`、`reject`、`gain_ack`）は接続に対して返る。エンジンからは、窓がいくつあっても UI は 1 つに見える。
- 後から開いた窓は、接続したときのスナップショットを受け取っていない。
- ルーティングの窓が閉じたりハングしたりしても、ミキサーの窓とエンジンへの経路は止めてはならない。
- 中継の経路では、メッセージをデコードしない（ADR-0020）。検証はエンジンで 1 回だけ行い、中継の遅れとコピーを最小にするため。

## 決定

### 窓のホスト

- ルーティングの窓は、ミキサーの窓と同じ `webui::WebUiHost` をもう 1 つ作って開く。新しい部品は作らず、ADR-0009 の「`webui` がサブウィンドウをホストする」をこの形で実現する。
- 窓に表示する画面は、初期化データの `screen`（`main` か `routing`）で UI に渡す。モードと同じく、窓ごとに起動時に固定する。
- UI は、窓を開く求めと閉じる求めを、ネイティブイベント `vocroz.window` で送る。値は `open_routing` か `close` の 2 つだけで、ほかの値は捨てる。
  - `webui` は求めをメッセージスレッドに積み直してから、コンポジションルートに渡す。WebView のイベントの中で、その WebView の窓を破棄しないためである。
- 窓を開く、前面に出す、閉じるの判断は、コンポジションルート（`remote-pa` の `HostMode`）が行う。ルーティングの窓は 1 つだけ開く。開いているときにもう一度求められたら、最小化から戻して前面に出す。
- ルーティングの窓の閉じるボタンと「閉じる」ボタンは、その窓だけを閉じる。アプリは終了しない。ミキサーの窓を閉じたら、従来どおりアプリを終える（ルーティングの窓も一緒に閉じる）。
- ブラウザでの開発時（フェイクエンジン）は窓を開けないので、従来どおり同じ窓で画面を切り替える。

### 1 本のパイプの多重化

- `control-protocol` に `ChannelGroup` を加える。複数の UI の経路を、1 本の `MessageChannel` に見せる部品である。`HostMode` は、`ChannelRelay` で `ChannelGroup` とエンジンへの経路をつなぐ。
- 配る規則は次のとおり。どちらの方向でも、メッセージはデコードしない。
  - エンジンからのメッセージは、`ack` と `reject` と `gain_ack` も含めて、すべての窓に送る。
  - どの窓からのメッセージも、そのままエンジンへ渡す。
- 応答の振り分けは UI が行う。
  - 窓ごとに違う request_id の接頭辞を、初期化データの `request_prefix` で渡す。ミキサーの窓は `m`、ルーティングの窓は `rt` である（`apps/pa-desktop/src/app_constants.h`）。
  - `EngineClient` は、自分が送っていない request_id の応答を無視する。これは従来からの振る舞いである。
  - 接頭辞を決めるのはコンポジションルートだけで、UI は渡された値を使うだけにする。窓が増えたときも、決まりはコンポジションルートの 1 か所で済む。
- 連続値のコマンド（`set_gain`）の `gain_ack` も、すべての窓に届く。
  - ミキサーの窓が操作するのはストリップと Master だけである。ルーティングの窓が操作するのはバスとセンドのレベルだけである。entity が重ならないので、ほかの窓の `gain_ack` が自分の送信と取り違えられることはない。
  - 同じ entity を 2 つの窓で操作する画面を作るときは、この決定を見直す。
- エンジンからの通知（`notice`）も両方の窓に届き、それぞれの窓がトーストで示す。

### 後から開いた窓の初期状態

- 後から開いた窓は、読み込みが終わったら従来どおり `hello` を送り、スナップショットを受け取る。エンジンは `hello` のたびに全状態を送る。
- そのスナップショットは、すでに開いている窓にも届く。ストアは全体を置き換えるだけなので、表示は変わらない。
- `ChannelGroup` は、スナップショットやイベントを覚えて渡すことはしない。覚えるにはデコードが要り、状態の正本がエンジン以外にもう 1 つできてしまうためである。
- エンジンにつながる前に開いた窓の `hello` は、どこにも届かない。つながったときに `HostMode` がすべての窓を読み込み直し、`hello` からやり直させる（ADR-0030 と同じ）。

### 閉じた窓、ハングした窓

- `ChannelGroup` は、窓の経路の 1 つが閉じても、まとめた経路全体を閉じたことにしない。ミキサーの窓とエンジンへの経路は続く。
- 窓を閉じるときは、先に `ChannelGroup` から外してから破棄する。外した後は、パイプの受信スレッドからその窓へ送ることはない。
- 窓への送信は、どの窓でもメッセージスレッドへの依頼を積むだけで、ブロックしない。
  - WebView2 のページはブラウザープロセスで動くので、ページがハングしても、パイプの受信スレッドとメッセージスレッドは止まらない。
  - 止まった窓に届かなかったメッセージは、その窓で失われるだけである。ほかの窓への配送には影響しない。

## 理由

- 応答をエンジンで送り元の窓にだけ返すには、エンジンが窓を区別する必要がある。そのためにはパイプを窓ごとに分けるか、プロトコルに窓の識別子を足すことになる。どちらも、1 つの UI だけをつなぐ前提（ADR-0020）を変えてしまう。
- `ChannelGroup` が request_id を付け替えて振り分ける方法もあるが、これには中継の経路で JSON をデコードし、書き換えて、エンコードし直す必要がある。中継で検証しないという方針（ADR-0020）と、中継の遅れを最小にする方針に反する。
- UI はもともと、自分が送っていない応答を無視する作りになっている。接頭辞を窓ごとに分けるだけで、すべての窓に配っても取り違えは起きない。

## 結果

- `control-protocol` に `ChannelGroup` が増える。
- `webui` の `WebUiLaunchData` に `screen` と `request_id_prefix` が増える。`WebUiHostOptions` に `on_open_routing` が、`WebUiHost` に `bring_to_front()` が増える。
- `remote-pa` の親機モードは、ルーティングの窓を開いたり閉じたりする。ADR-0033 の「同じウィンドウで切り替えて開く」は、ブラウザでの開発時だけの動作になる。
- UI は、初期化データの `screen` と `request_prefix` を読む。ルーティングの窓では、閉じるボタンの文言が「閉じる」になる。
