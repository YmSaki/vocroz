# 0045. グラフの差し替えで音声の履歴を引き継ぐ

- 状態: 採用（2026-11-15）

## コンテキスト

ADR-0018 で、ストリップの手動ディレイと遅延ノードを `DelayLine` で実装した。
ADR-0024 で、プラグイン遅延補正（PDC）を結線ごとの `DelayLine` で実装した。
グラフの変更は、オーディオスレッド外で新しい `RenderGraph` を作り、ポインターの交換で差し替える（AGENTS.md 6.1）。

`pa-engine` は、参加者の追加や退出、受信ストリームや返送の付け替え、ルーティングの編集のたびに、グラフ全体を組み立て直す。
新しいグラフの `DelayLine` は無音で始まるので、変更していないストリップでも、遅延の長さぶん音が途切れていた。
500 ms の入力ディレイでは、別の子機を承認しただけで 500 ms の音が抜けた（Issue #103）。

差し替えで引き継いでいたのは、MIDI の発音中のノートだけだった（ADR-0029）。
フェーダーの状態はグラフの外（`Mixer`）にあるので、もともと途切れない。

決めることは次のとおり。

- 差し替え前と後のノードを、何で対応づけるか
- いつ、どのスレッドで引き継ぐか
- 遅延の長さを変えたときにどうするか

## 決定

### ノードの対応は HistoryKey で決める

- `NodeSpec` に任意の `history_key`（`HistoryKey`、64 ビットの値）を足す。
- 差し替え前のグラフに、同じ種類で同じキーのノードがあれば、次のものを引き継ぐ。
    - `kStrip` の手動ディレイと `kDelay` の遅延（チャンネル数と遅延の長さが同じとき）
    - そのノードへの結線の遅延補正（送り元にもキーがあり、取り出す位置と補正の長さが同じとき）
- キーを付けないノードは引き継がず、これまでどおり無音から始める。
- 同じグラフの中で同じキーを複数のノードに付けたら、そのキーのノードは引き継がない。
- `MinusMeReturn` にも任意の `history_key` を足し、返送のミックスの安全リミッターに付ける。

### pa-engine は役割と entity_id からキーを作る

- `build_mixer_graph()` が、役割（`strip`、`bus`、`delay`、`output`、`insert`、`return`）と entity_id の FNV-1a（64 ビット）をキーにする。
- Master は役割 `bus` と Master の entity_id、返送は役割 `return` と返送のキー（接続）を使う。

### 引き継ぎはオーディオスレッドで、バッファの交換だけで行う

- `GraphExchange::acquire()` が、新しいグラフを取り込むときに `RenderGraph::adopt_audio_history()` を呼ぶ。MIDI の引き継ぎと同じ場所。
- `DelayLine::adopt()` は、`std::vector` の `swap()` と読み書きの位置の交換だけを行う。確保、解放、サンプルのコピーはしない。
- 差し替え前のグラフには無音のバッファが残り、コントロールスレッドが破棄するときに解放される。
- キーの検索は、構築時にキーの昇順に並べた索引の二分探索で行う。

### 遅延の長さを変えたら無音から始める

- 長さが違う `DelayLine` は引き継がない。
- 長さを変えるのはオペレーターの操作で、前の長さで遅らせていた音を新しい長さの途中から出すと、意図しない時刻の音になるため。

## 理由

- `NodeId` は組み立てのたびに振り直す（`pa-engine` は通し番号、`add_minus_me_returns()` は最大値の次）。`NodeId` で対応づけると、別の経路の音が新しい経路から出る。
- `FaderId` は ID のプールから使い回すので、別の参加者のストリップに同じ値が付きうる。遅延ノードにはフェーダーがない。
- 経路の同一性は、それを組み立てる側（`pa-engine` の entity_id）だけが知っている。そのため、明示的なキーを任意で渡す形にした。キーを付けない呼び出し元（固定ミキサーなど）の振る舞いは変わらない。
- 履歴は、古いグラフが最後のブロックまで処理した時点のものが要る。オーディオスレッド外で写すと、写した後に古いグラフが処理したブロックが抜けるので、取り込みの瞬間にオーディオスレッドで行う。
- 交換だけなら処理時間は遅延の長さによらず、AGENTS.md 第 9 節の制約（確保、ロック、上限のない処理をしない）を満たす。
- 64 ビットのハッシュは衝突しうるが、数千の entity でも確率は 1e-12 未満で、さらに種類、チャンネル数、遅延の長さが一致したときにしか影響しない。番号を払い出す表を持つより単純なので、こちらを選んだ。

## 結果

- 参加者の追加と退出、受信ストリームと返送の付け替え、関係のないルーティングの編集で、既存の入力ディレイ、遅延ノード、遅延補正の音が途切れない。
- 遅延の長さを変えたときは、これまでどおり新しい長さぶん無音になる。長さの変更を途切れなくつなぐ（古いバッファの末尾を写すなど）のは範囲外で、必要になったら別に決める。
- ストリップのチャンネル数が変わったとき（受信ストリームがモノラルからステレオになったときなど）は引き継がない。
- `MinusMeReturn` を集成体初期化している既存のテストでは、`-Wmissing-field-initializers` の警告が増える（CI は警告で失敗しない）。
