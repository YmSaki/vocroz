# 0014. 子機と親機の間の UDP パケットの形式と、ハンドシェイク後の暗号化

- 状態: 採用（2026-11-08）

## コンテキスト

ADR-0001 で、鍵交換を `Noise_IK_25519_ChaChaPoly_BLAKE2s` にし、ハンドシェイク後は独自の UDP フレームのヘッダー（バージョン、接続 ID、種別、シーケンス番号）を AEAD の関連データにしてシーケンス番号でリプレイを排除すると決めた。
ヘッダーのバイト配置、暗号文側に載せるもの、リプレイ排除の窓の幅、パケットの最大長は決まっていなかった。

また、Noise の CipherState は nonce を内部で 1 ずつ数える前提で、noise-c の `noise_cipherstate_set_nonce()` は nonce を巻き戻せない。
UDP ではパケットが欠落したり順序が入れ替わったりするので、CipherState のままでは、遅れて届いた正規のパケットを復号できない。
認証の前に nonce を進めると、偽造パケット 1 つで以降の正規のパケットをすべて捨てさせられる。
noise-c には CipherState の鍵を取り出す API もない。

## 決定

### 固定ヘッダー（14 バイト、ビッグエンディアン、暗号化しない）

| 位置 | 長さ | 内容 |
| --- | --- | --- |
| 0 | 1 | バージョン（1）。違う値のパケットは捨てる |
| 1 | 1 | 種別。1: ハンドシェイク開始、2: ハンドシェイク応答、3: メディア、4: 制御 |
| 2 | 4 | 接続 ID。開始側（子機）がハンドシェイクの前に乱数で決め、両方向で使う |
| 6 | 8 | シーケンス番号。送信方向ごとに 0 から 1 ずつ進め、メディアと制御で共有する。ハンドシェイクでは 0 |

- 接続はアドレスではなく接続 ID で識別する。NAT のマッピングが変わったときや、将来の不透明中継（仕様の「中継（将来実装）」）を経由したときも、パケットの形式を変えずに同じ接続として扱える。
- メディアと制御のパケットは、ヘッダー全体を AEAD の関連データにする。種別、接続 ID、シーケンス番号の書き換えは認証の失敗になる。
- ハンドシェイクのパケットは、Noise のプロローグに「ラベル、バージョン、接続 ID」を入れる。ヘッダーの接続 ID を書き換えるとハンドシェイクが失敗する。

### 暗号文側

- メディア: ストリーム ID（2）、タイムスタンプ（8、48kHz のサンプル数）、ミュート epoch（4）、Opus のペイロード（1 フレーム、空は不正）。どのストリームのどの時刻の音声かも経路上からは見えない。
- 制御: 信頼制御層が決める不透明なバイト列。空でもよい（キープアライブ）。
- ハンドシェイク: Noise のメッセージ。任意のペイロード（招待トークンなど）を Noise が暗号化して運ぶ。

### パケットの最大長

UDP ペイロードで 1232 バイト（IPv6 の最小 MTU 1280 から IPv6 と UDP のヘッダーを引いた値）にする。どの経路でも IP フラグメンテーションを起こさないためで、フラグメントを 1 つ失うとパケット全体が失われる。メディアの固定部とヘッダーと認証タグを除いた Opus のペイロードは 1188 バイトまでで、低遅延モード（ADR-0002）のフレームには十分に大きい。

### ハンドシェイク後の暗号化

- Noise の `Split()` で得た送信用と受信用の CipherState から、それぞれ 1 回だけ、nonce 0 で 32 バイトのゼロを暗号化し（関連データは用途のラベル）、暗号文を新しい鍵にする。導出に使った CipherState はその場で破棄する。Noise 仕様の `REKEY()` と同じく、ChaCha20 を鍵に対する擬似乱数関数として使う考え方で、新しいプリミティブは作らない。
- 導出した鍵で、libsodium の `crypto_aead_chacha20poly1305_ietf` を使う。nonce はシーケンス番号から Noise の ChaChaPoly と同じ形（4 バイトのゼロ + 8 バイトのリトルエンディアン）で作る。
- 送信側はシーケンス番号を二度使わない。2^64 - 1 は Noise と同じく予約値として使わない。

### リプレイ排除

- 受信側は 1024 パケット幅のスライディングウィンドウを持つ。5ms フレームで毎秒 200 パケットのとき約 5 秒分で、経路上の順序の入れ替わりより十分に長い。
- 窓より古いシーケンス番号と、受信済みのシーケンス番号は捨てる。窓の判定は復号の前に行い、窓への記録は認証に成功してから行う。偽造パケットでは窓が進まない。
- ハンドシェイク開始メッセージのリプレイは transport では検出しない。応答しても攻撃者は鍵を得られず、古い参加申請の再送を拒むのはペイロードを検証する session の責務とする。

## 理由

- 接続 ID で識別する形は WireGuard や QUIC と同じで、経路に依存しない設計（仕様のトランスポートの要件）をパケットの形式だけで満たせる。
- 明示的な nonce とスライディングウィンドウは、UDP 上の AEAD で広く使われている方式（IPsec の RFC 4303、DTLS、WireGuard）で、欠落と入れ替わりがあっても遅延を増やさずに復号できる。
- noise-c を改変したり、内部の構造体から鍵を読んだりすると、ライブラリの更新で静かに壊れる。公開 API だけで鍵を導出すれば、ADR-0010 で固定した noise-c をそのまま使える。
- 鍵の導出を自作の KDF にせず、Noise 仕様の `REKEY()` と同じ構成にとどめることで、暗号プリミティブを自作しない方針（ADR-0001）を守る。

## 結果

- 鍵の導出の構成は、ADR-0001 の「RC1 前の外部のセキュリティレビュー」の対象に含める。
- 制御メッセージの形式、再送、キープアライブは信頼制御層（T3）が、この形式の制御パケットの上に作る。
- 接続 ID が既存の接続と重なったときの扱いと、承認の判断は session が決める。
- 形式を変えるときはバージョンを上げる。古いバージョンのパケットは受信側で捨てる。
