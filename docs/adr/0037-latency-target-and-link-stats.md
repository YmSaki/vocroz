# 0037. 全体の目標レイテンシーと、受信の実測値（ジッター）の表示

- 状態: 採用（2026-11-09）

## コンテキスト

仕様では、入力ごとの手動ディレイのほかに「全体の目標レイテンシーの設定」と「実測ジッターの表示」を求めている。
ADR-0026 では、この 2 つを `transport` と `session` の統計の側で扱うとして先送りした。

受信の遅延の大半はジッターバッファ（`PlayoutStream`）の深さで決まる。
`PlayoutStream` は、最小の深さ（`min_delay`）と上限（`max_delay`）の間で、回線の揺れに合わせて目標の深さを自動で調整する（ADR-0002 の低遅延プロファイルでは、最小 10 ms、上限 20 ms）。
上限を超えて溜まったフレームは、古い方から捨てて遅延を戻す。

オペレーターが選べるべきなのは、このうちの上限である。
上限を短くすると遅延は小さくなるが、回線が揺れたときに捨てるフレームと PLC で補う区間が増え、音が途切れやすくなる。
この兼ね合いを判断するには、回線の実際の揺れが画面で見えている必要がある。

## 決定

### 目標レイテンシー

- 目標レイテンシーは、全チャンネルに共通のジッターバッファの上限（`max_delay`）とする。最小の深さと、自動調整の仕組みは変えない。
- 範囲は 10〜250 ms、既定は 20 ms とする（`control_protocol::kMinLatencyTargetMs`、`kMaxLatencyTargetMs`）。
  - 下限の 10 ms は、ジッターバッファの最小の深さと同じ値である。これより短い上限は自動調整と矛盾する。
  - 上限の 250 ms は、ADR-0002 で決めたジッターバッファの範囲の上限である。合奏には向かないが、回線が悪いときに聞き取りの確認だけに使えるよう残す。
  - 既定の 20 ms は ADR-0002 の低遅延プロファイルの上限である。低遅延が必須要件なので、既定は短い側に置き、回線が揺れたときにオペレーターが実測値を見て伸ばす運用にする。
- 設定はセッションの entity（`session`）への離散コマンド `set_latency_target { target_ms }` で行う。
  - エンジンが範囲を検証し、適用したら `SessionInfo.latency_target_ms` を変えて revision を進め、ACK を返す（エンジン主権）。UI は ACK の後に届いた状態で表示を変える。
  - 範囲の外の値は `control-protocol` の信頼境界で拒否する。
- `session` は値を `PlayoutControl` ポート（`set_latency_target()`）で反映する。`pa-engine` がこのポートを実装し、すべての受信ストリームの `PlayoutStream::set_max_delay()` に配る。
- 値は親機の設定（`HostSettings.latency_target_ms`）に保存し、起動時に戻す。
  - この値がない古い設定ファイルは既定値で読む。型が違えば、設定ファイル全体を壊れたものとして扱う（ADR-0027 と同じ）。
  - 保存した値が範囲の外か有限でなければ、起動時に既定値に戻す。

### 再生中の反映

- `set_max_delay()` は値を 1 つの atomic に置くだけで、ブロックしない。最後に置いた値が勝つ。オーディオスレッドが次の `render()` の始めに読み、そのときに反映する。
- 上限を広げても、その場では何も起きない。目標の深さは自動調整で徐々に深くなるので、音は途切れない。
- 上限を狭めると、目標の深さを新しい上限まで浅くし、溜まりすぎた古いフレームを 1 回だけ捨てる。
  - このときは一瞬だけ音が不連続になる。回線の停滞のあとに遅延を戻す既存の処理と同じ動作である。
  - 本番中に上限を狭めるのはオペレーターの明示的な操作だけなので、クロスフェードなどの追加の処理はしない。オーディオパスに処理とバッファを足さないためである。

### 受信の実測値

- ジッターは、RFC 3550 の interarrival jitter と同じ式で推定する（`transport::JitterEstimator`）。
  - 連続する 2 フレームについて、到着の間隔とメディアタイムスタンプの間隔の差の絶対値をとり、1/16 の重みで平滑化する。
  - 送信ミュートの世代が変わったらタイムスタンプが連続しないので、次のフレームを新しい起点にする。それまでの推定値は残す。
  - 推定はネットワーク受信スレッドで、受け付けたフレームごとに行う。ヒープ確保はしない。
  - 再生の制御（自動調整）には使わず、表示のためだけに使う。
- エンジンは、ストリップの `entity_id` ごとのジッターとバッファの深さを、`link_stats` イベントで約 1 Hz で送る。
  - 値は観測値なので revision を持たず、スナップショットにも含めない（ADR-0015）。
  - 受信していないストリップは省いてよい。値がまだない項目は null にする。
  - UI は届いた一覧で置き換え、一覧にないストリップの古い値は残さない。
- UI では、目標遅延をステータス帯で選び、ジッターとバッファの長さをチャンネルストリップに常に表示する。

## 理由

- 上限だけを選ばせると、自動調整の仕組みを変えずに済む。最小の深さまで選ばせると、オペレーターが回線より短い深さに固定して音を途切れさせる操作ができてしまう。
- チャンネルごとではなく全体で 1 つにしたのは、合奏では全員の遅延をそろえる方が演奏しやすく、操作も少ないためである。
- 実測値を 1 Hz にしたのは、オペレーターが値を読んで判断するには十分な速さで、メーター（10〜30 Hz）ほど IPC と再描画の負荷をかけないためである。

## 結果

- `control-protocol` に `set_latency_target`、`link_stats`、`SessionInfo.latency_target_ms` が増える。
- `session` に `PlayoutControl` ポートが増える。
- `transport` に `JitterEstimator` と `PlayoutStream::set_max_delay()` が増える。ジッターバッファの容量は、上限の最大の 250 ms 分を最初から確保する。
- 受信ストリームへの配布、ジッターの推定の実行、`link_stats` の送信は、`pa-engine` の子機の受信の組み立て（E1）で接続する。それまでの `pa-engine` は、何もしない `PlayoutControl`（`UnconnectedPlayoutControl`）を注入する。
