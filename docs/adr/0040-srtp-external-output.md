# 0040. SRTP 外部出力（libsrtp の採用、鍵、RTP の形式、平文の禁止）

- 状態: 採用（2026-11-09）

## コンテキスト

Beta2 では、指定したバスの音声を、外部の放送機器やサーバーへ SRTP で暗号化して送る（B2b、Issue #31）。
仕様は次のことを求めている。

- 外部機器と相互接続するため、この機能だけは標準の RTP / SRTP を使う。親機と子機の間の独自トランスポート（ADR-0014）とは独立させる
- 平文での誤送信は禁止
- 接続テストの機能と、コーデックのプロファイルの設定を持つ

ADR-0009 では、ライブラリを採用するときに ADR を書き、アダプターのモジュールを新設するかを決めるとした。
ここでは、ライブラリ、置き場所、鍵の扱い、RTP の形式、スレッドの分け方、平文を送らない仕組みを決める。

前提は次のとおり。

- 相手は SIP や WebRTC のシグナリングを持たない放送機器やメディアサーバーで、宛先、ペイロード形式、鍵を手で設定する運用が一般的である。
- 外部出力は合奏の経路（出演者のモニター）に入らないが、低遅延の方針（AGENTS.md 1.2）は同じく守る。
- 相互接続試験の相手機器は今週は手配できない。

## 決定

### ライブラリ

- SRTP の処理には libsrtp 2.7.0（Cisco、BSD-3-Clause）を使う。BSD-3-Clause は AGPL-3.0 と互換である。
- 取得は `cmake/libsrtp.cmake` で、タグ v2.7.0 のコミット（`ee1a77c`）で固定する（ADR-0010 の Git でしか取得できないものの固定の方法）。ターゲットは `libSRTP::srtp2`。
- 暗号のバックエンドは libsrtp の内蔵の実装を使い、OpenSSL などには依存しない。暗号スイートは内蔵の実装で使える `AES_CM_128_HMAC_SHA1_80`（既定）と `AES_CM_128_HMAC_SHA1_32` だけにする。`AES_CM_128_HMAC_SHA1_80` は SDES（RFC 4568）で実装が必須とされる組み合わせで、ほぼすべての受信機が対応している。AES-GCM は OpenSSL のバックエンドが要るので、相互接続試験で必要と分かってから追加する。
- 使ってよい範囲は `transport` だけにする（AGENTS.md 4.2）。libsrtp の型は公開ヘッダーに出さない。

### 置き場所

- モジュールは新設せず、`transport` に置く。RTP のヘッダーの組み立て、SRTP の暗号化、Opus のエンコードは、どれも OS に依存しないワイヤーフォーマットと暗号の処理で、`transport` の責務（ワイヤーフォーマット、暗号、Opus）に収まる。ソケットの実装を持たない点も同じである。
- 独自トランスポートとの独立は、クラスと経路を分けることで保つ。外部出力の部品（`SrtpProtector`、`ExternalStreamSender`、`src/wire/rtp_header_codec`）は、Noise のハンドシェイク、`SecureChannel`、独自のパケットヘッダー（`PacketHeader`）を使わず、それらからも使われない。ソケットも子機との接続とは別に持つ（宛先ごとに 1 つ）。
- 宛先へ送る UDP ソケットは `transport::DatagramSocket` ポートで受け取り、実装は `network` が持つ（2 本目の PR）。

### 鍵

- 鍵は SDES（RFC 4568）の `a=crypto` 属性と同じ形式で扱う。マスターキー 16 バイトとマスターソルト 14 バイトを連結した 30 バイトを Base64 にした文字列で、`inline:` の接頭辞は付けても付けなくてもよい。受信機の設定画面からそのまま貼り付けられ、こちらで作った鍵を受信機に貼り付けることもできる。
- 鍵の寿命（lifetime）と MKI の指定（`|` で続く部分）は受け付けない。1 本のストリームを 1 つの鍵で送り、鍵の切り替えは出力を止めて設定し直す運用にする。
- すべて 0 の鍵は受け付けない。未設定の入力欄の初期値をそのまま送り出す誤りを防ぐため。
- パースは信頼境界の 1 か所（`parse_srtp_master_key()`）で行い、内側には検証済みの `SrtpMasterKey` だけを渡す（AGENTS.md 6.3）。鍵を作るときは libsodium の乱数を使う（`generate_srtp_master_key()`）。
- 鍵は秘密情報として扱う。ログに出さず、`control-protocol` のスナップショットとイベントには「設定済みかどうか」だけを載せる。保存は `persistence` の DPAPI で保護する（2 本目の PR）。

### 平文を送らない仕組み

- RTP のパケットを送る部品は `ExternalStreamSender` だけで、`ExternalStreamSender` は libsrtp のセッション（`SrtpProtector`）を作れないと作れない。`SrtpProtector` は検証済みの鍵からしか作れず、libsrtp の NULL 暗号や NULL 認証のポリシーは使わない。鍵がなければ送信の部品そのものが組み立てられないので、送信は起きない。
- 暗号化に失敗したパケットは送らずに捨てて数える。平文に戻して送る経路は持たない。
- 暗号化はパケットのバッファの中で行い（in place）、暗号化の前のバイト列をソケットに渡す変数は持たない。

### RTP の形式

- RTP（RFC 3550）と Opus のペイロード形式（RFC 7587）に従う。1 パケットに Opus の 1 フレームを入れ、RTP のタイムスタンプの時計は 48kHz にする（RFC 7587 ではチャンネル数やサンプルレートに関わらず 48kHz）。
- ペイロードタイプは動的な範囲（96〜127）から選び、既定は 111 にする。受信機の SDP と合わせるため、設定で変えられるようにする（2 本目の PR）。
- SSRC、シーケンス番号の初期値、タイムスタンプの初期値は乱数で決める（RFC 3550 の推奨。SRTP の既知平文の攻撃を難しくする）。
- マーカービットは、最初のパケットと、送信が途切れた後（タイムスタンプが 1 フレームより先へ飛んだとき）の最初のパケットに立てる（RFC 3551 の音声の規則）。受信機はこれを再生の区切りとして扱える。
- CSRC とヘッダー拡張は使わない。SRTP のトレイラーを含めてもパケットの最大長（`kMaxPacketBytes`、1232 バイト）を超えない。

### コーデックのプロファイル

- 最初のプロファイルは Opus のステレオ（`kStereoBitrateBps`）とモノラル（128 kbps）の 2 つにする。フレーム長は低遅延の方針に合わせて 5 ms にする。RFC 7587 は 2.5〜120 ms を認めており、受信機が短いフレームに対応しないと分かったら、10 ms と 20 ms のプロファイルを足す。
- 非圧縮の L16（AES67 など）は、PTP の時刻同期と平文のマルチキャストが前提の方式が多く、この機能の要件（暗号化）と合わないので、今は持たない。

### スレッド

- オーディオスレッドは、送り出すバスの音声を取り出して Opus でエンコードし、エンコード済みのフレームを SPSC キューで送信スレッドへ渡す。返送モニター（ADR-0036）と同じ分け方で、オーディオパスに追加のバッファリングを入れない。
- 送信スレッドが RTP のヘッダーを付け、SRTP で暗号化して UDP で送る。libsrtp とソケットの呼び出しはオーディオスレッドで行わない（AGENTS.md 第 9 節）。
- 送り出すバスは、ルーティング（ADR-0018）のバスか Master のポストフェーダーの出力から選ぶ。バスからの取り出しは、返送タップと同じく出力を持たないタップのノードで行う（2 本目の PR で `audio-core` に足す）。

### 初期状態と接続テスト

- 外部出力は、起動時と再起動時に停止の状態から始める（初期ミュートの製品要件）。設定（宛先、バス、プロファイル、鍵）は保存して戻すが、送信の開始はオペレーターの操作でだけ行う。
- 接続テストは、出力を止めている間だけ行える。同じ SRTP の経路で 1 kHz、-20 dBFS の試験音を数秒（3 秒）送り、宛先の解決とソケットの送信の失敗を結果として返す。試験音も暗号化して送る。
- ICMP の到達不能の通知は、今は結果に含めない。`network` の Winsock のソケットは、子機との接続で ICMP のエラーに受信を止められないよう `SIO_UDP_CONNRESET` を切っており（`modules/network/src/win/winsock_udp_endpoint.cpp`）、同じ実装を使う外部出力のソケットでも通知が届かない。外部出力のソケットだけ設定を変えるかは、相互接続試験で受信機が止まっているときの振る舞いを見てから決める。
- 受信機に届いて復号できたことまでは、受信機が返す SRTCP の受信レポートがないと確かめられない。受信レポートによる確認は、相互接続試験で受信機の振る舞いを確かめてから足す。

### UI とエンジンの間の制御

- 外部出力は entity `external_output` 1 つで表す。スナップショットとイベント（`external_output_updated`）には、設定（宛先、ポート、送り出すバス、プロファイル、ペイロードタイプ、暗号スイート）、鍵が設定済みかどうか、状態（`STOPPED`、`RUNNING`、`TESTING`）、直前の結果（`OK`、`RESOLVE_FAILED`、`SEND_FAILED`）を載せる。鍵は載せない。
- コマンドは、設定の変更（`set_external_output_config`）、鍵の設定（`set_external_output_key`）、開始と停止（`set_external_output_running`）、接続テスト（`test_external_output`）の 4 つにする。設定と鍵は、止めている間だけ変えられる。送信中の宛先や鍵の差し替えは、受信機から見ると別のストリームになるため、止めてから変える運用にそろえる。
- revision はコマンドで変えた値（設定、鍵、状態）で進め、接続テストが終わって結果が出たことでは進めない（`docs/adr/0015-control-protocol-messages.md` の観測値の規則）。開始に失敗したときはコマンドを受け付けたうえで、状態を `STOPPED` のまま結果を載せ、通知（`external_output_failed`）を出す。
- 送り出すバスがルーティングの適用でなくなったら、送信を止めて通知（`external_output_source_removed`）を出す。別のバスへ暗黙に切り替えない（AGENTS.md 1.2 のフェイルセーフ）。
- 鍵は UI の画面で作る（Web Crypto の `crypto.getRandomValues()`）。作った鍵を受信機に貼るための写しは画面の入力欄にだけ置き、エンジンへ送ったら入力欄から消す。エンジンは鍵を UI へ返さないので、一度設定した鍵を画面で見返すことはできない。受信機の鍵を失ったら作り直す。
- 鍵は、受信機に貼るのと同じ `inline:` 形式の文字列にして DPAPI で保存し、起動時の読み込みでも `parse_srtp_master_key()` で検証する。

### 組み立て

- `pa-engine` は、外部出力の開始のたびに、宛先の解決、ソケット、`ExternalStreamSender`、Opus のエンコーダー、SPSC キューを組み立ててから、ミキサーのグラフにタップのノードを足す。停止ではタップを外してから送信スレッドを止める。グラフとキューの寿命は、タップとエンコーダーが共有するパイプの共有ポインターでそろえる。
- タップの前には、Master と同じリミッターを置く。受信機の側でクリップさせないため。

## 理由

- libsrtp は SRTP の参照実装として、多くの SIP 電話、メディアサーバー、ブラウザが使っている。相互接続試験の相手機器がない今週でも、テストの受信側に libsrtp 自身を使えば、パケットの形式と暗号化が標準どおりであることを単体テストで確かめられる。
- 暗号のバックエンドを内蔵にすれば、OpenSSL のビルドと配布（Windows で数 MB の DLL と、脆弱性の追従）を抱えずに済む。
- モジュールを新設しないのは、責務が `transport` に収まり、新しい依存（`session` → 新モジュール）と許可リストの変更を増やさずに済むため。独自トランスポートからの独立は、モジュールではなく部品と経路の分離で保てる。
- 送信の部品を鍵なしに作れない形にすれば、平文で送らないことを実行時の確認ではなく型で保証できる。確認の分岐で守る方式は、分岐を足すたびに漏れうる。
- DTLS-SRTP は鍵交換を自動化できるが、相手機器との間にハンドシェイクの経路とシグナリングが要り、受信専用の放送機器の多くは対応していない。手で設定する SDES 形式の鍵なら、ほぼすべての機器と相互接続できる。

## 結果

- `transport` の公開 API に `SrtpMasterKey`、`SrtpCryptoSuite`、`RtpStreamParams`、`ExternalStreamSender`、`parse_srtp_master_key()`、`format_srtp_master_key()`、`generate_srtp_master_key()`、`make_rtp_stream_params()` が加わる。libsrtp を包む `SrtpProtector` と、RTP のヘッダーの組み立て（`src/wire/rtp_header_codec`）は `src/` に置き、公開しない。単体テストでは、送ったパケットを libsrtp の受信側で復号し、RTP のヘッダーとペイロードが元どおりであることを確かめる。
- libsrtp の内蔵の AES はテーブル参照の実装で、定数時間ではない。外部出力の暗号化は送信側だけで行い、鍵に依存する処理時間を相手が細かく測れる状況は考えにくいが、RC1 の前の外部のセキュリティレビューでこの判断を確かめる。必要なら OpenSSL のバックエンドに切り替える。
- 実装は 3 本の PR に分けた。1 本目は libsrtp と送信の部品、2 本目はバスから取り出すタップのノードとステレオのエンコード（`audio-core`、`transport`）、3 本目は設定と鍵の保存と出力の開始と停止（`session`、`persistence`）、`control-protocol` のコマンドとイベント、`pa-engine` の送信スレッドと宛先へのソケットの組み立て、外部出力と接続テストの画面（`ui/`）。
- 外部の受信機との相互接続試験は、相手機器を手配してから `docs/testing/srtp-external-output.md` の手順で行う。それまでは仕様書の Beta2 の合格条件のうち、この項目は未達のままになる。
