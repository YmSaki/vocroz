# 0013. インストーラー、pa-updater、起動スタブの構成

- 状態: 採用（2026-11-07）

## コンテキスト

`docs/adr/0004-side-by-side-updates.md` で、更新はバージョン別フォルダの切り替えで行い、初回導入とアンインストールは WiX Burn バンドルで行うと決めた。
実装に入るには、次の点を決める必要がある。

- 更新の判断（マニフェストの検証、本番中のブロック、ロールバックの判定）をどこに置くか。AGENTS.md は `apps/` にビジネスロジックを置かないと定めている。
- 更新マニフェストの形式と、Ed25519 と SHA-256 の実装に使うライブラリ。
- 「現行版」を指す仕組みと、固定の起動スタブの振る舞い。
- `pa-updater` の引数（`docs/adr/0007-launch-interface.md` で P5 に先送りした）。
- コード署名の名義が未決のまま、署名なしで配布の仕組みを通す方法。

## 決定

### モジュールとディレクトリ

- 新しいドメインモジュール `update` を作る。責務は、セマンティックバージョン、更新マニフェストの検証、更新の適用可否の判断（本番中のブロック）、更新トランザクションのステートマシンとロールバックの判定、「現行版」を指すポインターファイルの形式、起動するバージョンの選択。依存してよいのは `common` だけ。
- 起動スタブを `apps/launcher/`（実行ファイル `vocroz.exe`）として追加する。ショートカットと URL スキーム `vocroz://` は、`remote-pa.exe` ではなくこのスタブを指す。
- インストーラーの定義（WiX）を `installer/` に、リリース作業用のツール（鍵の生成とマニフェストの署名）を `tools/release/` に置く。

### 更新マニフェスト

- テキスト形式の `key=value` の行で書く。`format`、`product`、`version`、`url`、`sha256`、`size`、`publisher` の 7 つのキーを、この順に 1 回ずつ書き、最後の行を `signature=<128 桁の 16 進数>` とする。
- 署名は、`signature=` 行より前のすべてのバイトに対する Ed25519 の署名とする。JSON にしないのは、署名対象のバイト列を正規化なしで一意に決めるためと、JSON ライブラリの導入（F2）を待たずに済ませるため。
- `url` は `https://` だけを受け付ける。`version` は現在のバージョンより新しいものだけを受け付ける（ダウングレード攻撃の防止）。`size` には上限を設ける。
- 公開鍵はビルド時に CMake のキャッシュ変数 `VOCROZ_UPDATE_PUBLIC_KEY`（64 桁の 16 進数）で埋め込む。空のときは、すべてのマニフェストを拒否する（フェイルセーフ）。
- Ed25519 と SHA-256 には libsodium を使う。AGENTS.md 4.2 の外部ライブラリの表で、libsodium の使用範囲に `update` を加える。暗号プリミティブを自作しない規則（AGENTS.md 6.4）と、すでに `transport` が採用しているライブラリに合わせるため。

### 更新パッケージと Authenticode

- 更新パッケージは、`app-x.y.z\` の中身をまとめた ZIP ファイルとする。展開には Windows 10 1803 以降に標準で入っている `%SystemRoot%\System32\tar.exe` を使い、ライブラリを増やさない。
- ZIP には Authenticode の署名を付けられないので、パッケージ全体の改ざんはマニフェストの SHA-256 で検出し、展開した `.exe` と `.dll` の Authenticode を個別に検証する。自分たちの実行ファイル（`remote-pa.exe`、`pa-engine.exe`、`pa-updater.exe`）は、署名者の証明書の名前（CN）が `publisher` と一致することまで確かめる。同梱する VC++ ランタイムなど他社が署名した DLL は、信頼できる署名があることだけを求める。
- マニフェストの `publisher` が空なら、Authenticode の検証を省く（署名証明書が届くまでの期間）。`publisher` はマニフェストの署名の対象なので、攻撃者が空に書き換えることはできない。証明書が届いたら、`publisher` に証明書の名前を入れるだけで検証が有効になる。

### 現行版の切り替えと起動スタブ

- インストール先は `%LOCALAPPDATA%\Programs\VOCROZ\` に固定する（ユーザー単位、管理者権限なし）。
    - `vocroz.exe`: 起動スタブ（インストーラーが置き、更新では書き換えない）
    - `app-x.y.z\`: バージョンごとのフォルダ（`remote-pa.exe`、`pa-engine.exe`、`pa-updater.exe`、VC++ ランタイム）
    - `current.txt`: 現行版と直前の版を指すポインターファイル（`pa-updater` だけが書く）
- 起動スタブは、ポインターファイルの現行版と、スタブ自身のバージョン（インストーラーが入れた版）のうち新しい方を先に試し、起動できなければ直前の版を試す。インストーラーで新しい版を上書き導入したとき、古いポインターに引きずられないようにするため。
- スタブは受け取ったコマンドラインをそのまま `remote-pa.exe` に渡し、待たずに終了する。引数の解釈は `remote-pa` だけが行う（`docs/adr/0007-launch-interface.md`）。
- ポインターファイルは一時ファイルに書いてから置き換える。古い版は直前の 1 つだけ残す。

### pa-updater の引数と流れ

| 引数 | 意味 |
| --- | --- |
| `--check` | 更新マニフェストとパッケージを `<データフォルダ>\updates\` にダウンロードし、検証する。セッション中でも実行してよい |
| `--apply` | 検証済みのパッケージを適用する。`remote-pa` が「更新して再起動」の操作を受けたときだけ渡す |
| `--restart` | `--apply` の成功後に起動スタブを起動する |
| `--install-dir=<パス>`、`--data-dir=<パス>` | 既定（上記のインストール先と `%LOCALAPPDATA%\VOCROZ\`）を変える。検証と自動テスト用 |
| `--version` | バージョンを表示して終了する |

- `--apply` は次の順に進める。どこかで失敗したら、それまでの変更を戻して終了する。
    1. セッションが稼働中なら、何も変えずに終了する（本番中のブロック）。
    2. マニフェストとパッケージ（SHA-256）を検証し直す。
    3. 設定ファイルをバックアップする。
    4. パッケージを `app-x.y.z\` に展開し、Authenticode を検証する。
    5. 新しい版の各実行ファイルを `--version` で起動し、期待するバージョンを返すか確かめる（起動確認）。
    6. ポインターファイルを切り替え、直前の版より古い版を削除する。
- 起動確認に失敗したら、展開したフォルダを削除し、設定をバックアップから戻し、ポインターは切り替えない。
- 「セッションが稼働中」は、`pa-engine` がセッションの稼働中に保持する名前付きミューテックスの有無で判定する。名前は `update` の公開ヘッダーで 1 か所に定義し、`pa-engine` の組み立て（E1）で同じ関数を使う。
- 終了コード: 0 適用または更新なし、1 致命的なエラー、2 引数の誤り、10 更新あり（`--check`）、20 セッション中のため適用しない、21 検証に失敗してパッケージを破棄した、22 起動確認に失敗してロールバックした。
- 更新ファイルの適用中に旧版のファイルは書き換えないので、旧版のプロセスの終了を待たずに適用できる。

### インストーラーとアンインストーラー

- WiX Toolset 5.0.2 を使う。v6 以降は配布バイナリの利用条件（Open Source Maintenance Fee）が加わったため、MS-RL だけで使える 5 系に固定する。WiX はビルドツールで、バンドルに入る Burn エンジンは製品とは別のプログラムとして同梱される（単なる集合）ため、AGPL の製品と組み合わせて配布できる。
- MSI はユーザー単位（`Scope="perUser"`）で、起動スタブ、`app-x.y.z\`、スタートメニューの 2 つのショートカット（「VOCROZ（親機）」と「VOCROZ（子機）」）、`HKCU\Software\Classes\vocroz` を入れる。
- VC++ ランタイムは、CMake の `InstallRequiredSystemLibraries` でアプリのフォルダに同梱する（app-local 配置）。管理者権限の要る再頒布パッケージは使わない。
- WebView2 Evergreen Runtime は、Microsoft の Evergreen Bootstrapper をバンドルに入れ、未導入の場合だけユーザー単位で導入する。アンインストールでは削除しない（他のアプリと共有するため）。
- アンインストールでは、Burn の画面で「設定とログを保持する（既定）」か「すべてのアプリデータを削除する」かを選ぶ。全削除は確認の画面を経てから実行する。どちらの場合も、`pa-updater` が追加した `app-x.y.z\` とポインターファイルを含め、インストール先は丸ごと削除する。
- 署名は `installer/sign.ps1` の 1 か所で行う。署名用の証明書が設定されていなければ何もしない。CI は未署名のインストーラーを成果物として出し、証明書が届いたらこのスクリプトと CI の Secrets を設定するだけで署名を差し込めるようにする。

## 理由

- 更新の判断を `update` に集めれば、OS なしで Linux の CI から単体テストできる。`apps/updater` と `apps/launcher` は、Windows のアダプターと組み立てだけを持つ。
- 判断と I/O を分けると、ロールバックの判定と本番中のブロックをフェイクで決定的に試験できる。
- テキスト形式のマニフェストと `tar.exe` によって、ライブラリを増やさずに配布の仕組みを先に通せる。

## 結果

- AGENTS.md の 2.1、3.2、3.3、4.2 の表に `update`、`apps/launcher`、`installer/`、`tools/release/` を追記し、`cmake/DependencyRules.cmake` に `update` を加える。
- アンインストール時にセッションが稼働中なら確認を出す要件と、`remote-pa` からの `--check` と `--apply` の呼び出し、`pa-engine` のセッション中ミューテックスは、アプリの組み立て（E1、E2）で接続する。
- 実際に署名した 2 つのビルドでの更新試験は、署名証明書が届いてから行う。
