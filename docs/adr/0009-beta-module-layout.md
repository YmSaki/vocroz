# 0009. Beta1〜Beta5 の機能をどのモジュールに置くか

- 状態: 採用（2026-11-07）

## コンテキスト

Beta1〜Beta5 では、ルーティング、返送モニター（Minus-Me）、子機の入力拡張、録音とファイル再生、VST3 エフェクト、MIDI と VSTi を追加する。
これらは並行して実装するので、各担当が AGENTS.md の 2.1、3.3、4.2 の表と `cmake/DependencyRules.cmake` を別々に書き換えると、衝突するうえに依存の向きが担当ごとにばらつく。
そのため、新モジュールの要否、レイヤー、責務、依存の向きを、実装の前に 1 回で決める。

判断の前提は次のとおり。

- 低レイテンシが必須要件で、オーディオスレッドは第 9 節のリアルタイム制約に従う。
- JUCE の型はドメインの公開ヘッダーに出さない（AGENTS.md 4.2）。仕様書は VST3 のホストに JUCE の `AudioProcessorGraph` を例示しているが、グラフ自体を JUCE にすると `audio-core` が JUCE に依存し、Linux の CI での単体テストと RealtimeSanitizer の検査ができなくなる。
- VST3 のスキャンは別プロセス（ヘルパー）で行い、不良プラグインで本体を落とさない（仕様書の Beta4 の要件）。

Beta2 の SRTP 外部出力と Beta3 の仮想音声ドライバーは、ライブラリと署名の方式が決まっておらず、今週は着手しないので、この ADR では置き場所の見込みだけを示す。

## 決定

### 新モジュール

アダプターレイヤーに 2 つのモジュールを新設する。ドメインのモジュールは増やさない。

| モジュール | レイヤー | 責務 | 依存してよいモジュール |
| --- | --- | --- | --- |
| `plugin-host` | アダプター | JUCE（`AudioPluginFormatManager`、`VST3PluginFormat`）による VST3 のスキャン、読み込み、処理、状態の保存と復元、エディターのウィンドウ。`audio-core` の `PluginProcessor` ポートと、`session` の `PluginLoader`、`PluginScanner`、`PluginEditorHost` ポートを実装する。スキャン用ヘルパーとの間のメッセージのスキーマ | `session`、`audio-core`、`common` |
| `media` | アダプター | JUCE の `AudioFormatManager` による音声ファイルの書き出し（WAV、FLAC）と読み込みとデコード。`audio-core` の `AudioFileWriter` と `AudioFileReader` ポートを実装する | `audio-core`、`common` |

どちらも、3.3 の既存のモジュールに該当せず、フェイクのポートを相手に単独で単体テストでき、循環依存を作らない（AGENTS.md 第 7 節の手順 6）。
FLAC の書き出しは JUCE に含まれる FLAC のコーデック（BSD ライセンス）を使い、別のライブラリを追加しない。

### 機能ごとの置き場所

| 機能 | ドメイン（状態とロジック） | アダプター | UI |
| --- | --- | --- | --- |
| ルーティング（ノードグラフ、バス、センド、手動ディレイ） | `audio-core`: グラフの記述（値型）、オーディオスレッド外でのレンダーグラフの構築、ダブルバッファリングによるスワップ、フィードバックループの検出、PDC の算出。`session`: ステージングと適用、リビジョン、ループの例外（明示的なディレイノードとオペレーターの承認）の判断 | なし | `ui/src/screens/routing/` |
| 返送モニター（Minus-Me） | `audio-core`: 子機ごとの、その子機の入力を除いたミックス。`transport`: 親機から子機への下りストリーム。`session`: 返送の ON / OFF とミュート、OFF とミュートの間は送信を止める判断 | 子機の再生は `device` の `AudioOutput` を `client-desktop` で使う | 子機画面とミキサー画面 |
| 子機の入力拡張（ステレオ、複数入力、アプリ音声） | `transport`: ステレオと複数ストリーム。`session`: ストリームとストリップの対応 | `capture`: WASAPI のループバック収集を含む | 子機画面 |
| 録音とファイル再生 | `audio-core`: 録音タップと再生ノード（オーディオスレッド側はロックフリーのリングバッファの読み書きだけ）、ディスク I/O スレッド側の排出と先読み。`session`: トラック、録音の開始と停止、書き込み失敗と容量不足の扱い | `media` | `ui/src/screens/media/` |
| VST3 エフェクト | `audio-core`: プラグインノード（`PluginProcessor` ポートを呼ぶ）、PDC、処理の失敗やタイムアウトでそのノードをバイパスかミュートにする扱い。`session`: プラグインの一覧、挿入位置、状態とプリセットの保存の指示 | `plugin-host`。スキャン用ヘルパーは `apps/plugin-scanner` | チャンネル詳細の画面 |
| MIDI と VSTi | `audio-core`: MIDI イベントの値型、タイムスタンプからブロック内のサンプルオフセットへの変換、MIDI のルーティング、発音中のノートの追跡と All Notes Off（Panic）。`transport`: 子機からの MIDI の伝送。`session`: 承認済みの子機だけを受け付ける判断、切断時の Panic の指示 | MIDI デバイスの入力は `device`（JUCE の `MidiInput`）。VSTi は `plugin-host` | ミキサー画面とルーティング画面 |

### オーディオグラフ

- オーディオグラフは `audio-core` が自前で持ち、JUCE の `AudioProcessorGraph` は使わない。VST3 のプラグインは、`audio-core` が定義する `PluginProcessor` ポート（オーディオスレッドから呼び出し可能な `process()`、報告されたレイテンシー、リセット）を `plugin-host` が実装し、グラフの 1 ノードとして組み込む。
- フィードバックループの検出と PDC は、グラフの構造だけから決まる純粋関数として `audio-core` に置く。ループを例外として許可するかどうかは、オペレーターの承認を扱う `session` が決める。
- PDC は、遅延のあるノードを通る経路と同じバスで合流する経路にだけ遅延を足す。合流しない経路には遅延を足さず、低レイテンシを保つ。

### スレッド

- 録音の書き出しと再生ファイルの読み込みは、新しく **ディスク I/O スレッド** で行う。ブロッキング I/O を含んでよく、オーディオスレッドとはロックフリーの SPSC リングバッファだけで受け渡す。書き込みが遅れてリングバッファが溢れたら、そのトラックの録音を欠落として記録し、オーディオスレッドは待たない。
- プラグインのインスタンス化とエディターのウィンドウは JUCE のメッセージスレッドでしか扱えないので、`pa-engine` のコントロールスレッドは JUCE のメッセージスレッドを兼ねる。エディターのウィンドウは `pa-engine` が開く独立したネイティブウィンドウで、閉じても音声処理は続く。

### VST3 のスキャン用ヘルパー

- 実行ファイル `pa-plugin-scanner` を新設し、`apps/plugin-scanner/` に置く。エントリポイントとコンポジションルートだけを持ち、スキャンの処理は `plugin-host` のものを使う。
- `pa-engine` は、プラグインファイル 1 つにつきヘルパーを 1 回起動し、結果を標準出力の JSON で受け取る。ヘルパーが異常終了するか、一定時間内に終了しなければ（タイムアウトの値は B4 で実測して決める）、そのファイルを読み込み不可として記録し、以降のスキャンから外す。
- ヘルパーとの間のメッセージのスキーマは `plugin-host` で 1 か所に定義し、両側で同じコードを使う（AGENTS.md 4.4）。
- スキャン結果はファイルのパスと更新日時をキーに、`session` の設定の永続化ポート経由で保存し、変更のないファイルは再スキャンしない。
- 実行モードは、まず信頼済みインプロセス（低遅延）だけを実装する。アウトオブプロセス実行（クラッシュ隔離）は、`plugin-host` の中で `PluginProcessor` と `PluginLoader` の別の実装として追加し、ドメインは変えない。プロセス間の音声の受け渡し方法は、追加するときに ADR で決める。

### 子機からの MIDI の伝送

- 子機からの MIDI は、`transport` の信頼制御層の上の MIDI 専用チャンネルで送る。順序と到達を保証し、他の制御メッセージとは順序を共有しない（他の制御メッセージの再送待ちで MIDI を遅らせないため）。
- 各イベントは送信側のタイムスタンプを持つ。親機はそれをセッションのタイムラインに写してサンプルオフセットに変換し、すでに過ぎた時刻のイベントは捨てずに次のブロックの先頭で処理する（Note Off を捨てると音残りになるため）。
- 子機が `LOST` になったら、`session` がその子機から入力される MIDI の経路に Panic を指示し、`audio-core` が発音中のノートすべてに Note Off を出す。

### 既存のモジュールの責務の追加

- `audio-core`: ルーティンググラフ、PDC、録音タップと再生ノード、プラグインノード、MIDI の処理。ポート `PluginProcessor`、`AudioFileWriter`、`AudioFileReader`、`MidiInput` を定義する。
- `session`: ルーティングのステージングと適用、返送の設定、録音の状態、プラグインの一覧と挿入。ポート `PluginLoader`、`PluginScanner`、`PluginEditorHost` を定義する。
- `device`: JUCE の `MidiInput` による MIDI デバイスの列挙（永続 ID）、入力、抜去の検知。
- `capture`: WASAPI のループバックによるアプリ音声の収集。
- `transport`: 親機から子機への下りストリーム、ステレオと複数ストリーム、MIDI 専用チャンネル。
- `webui`: ルーティング画面などの独立したサブウィンドウのホスト。

### 対象外（見込みだけ）

- **SRTP 外部出力（Beta2）**: 外部機器向けの標準 RTP / SRTP で、`transport` の独自プロトコルとは独立させる。ライブラリ（libsrtp など）を採用するときに ADR を書き、アダプターのモジュールを新設するかを決める。
- **仮想音声ドライバー（Beta3）**: カーネルモードのドライバーで、C++ のモジュール構成の外になる。着手するときに ADR を書き、トップレベルのディレクトリを決める。

## 理由

- グラフを `audio-core` に置けば、ルーティング、Minus-Me、PDC、Panic をすべて OS と JUCE なしで単体テストでき、RealtimeSanitizer でオーディオスレッドの処理を検査できる。JUCE の `AudioProcessorGraph` を使うと、グラフの変更時の内部の確保やロックを自分で管理できない。
- プラグインと音声ファイルは JUCE が実装を持つ外部の技術なので、ポートの向こうのアダプターにする。両者は変更の理由（VST3 の仕様と、ファイル形式）が異なるので別のモジュールにする。
- スキャン用ヘルパーをプラグインファイルごとに起動すれば、落ちたプラグインを特定でき、本体は巻き込まれない。起動の回数は増えるが、結果を保存して再スキャンを避けるので、起動時間への影響は初回だけで済む。
- MIDI の Note Off が届かないと音残りになるので、到達の保証を優先して信頼制御層に載せる。再送が起きたときの遅れは、合奏で問題になる音の欠落や音残りより影響が小さい。実装も信頼制御層を流用でき、専用の冗長化方式を作らずに済む。

## 結果

- AGENTS.md の 2.1、2.2、2.3、3.2、3.3、4.2、4.4 の表と `cmake/DependencyRules.cmake`、`modules/README.md` を更新する。新モジュールのディレクトリは、ファイルを置く PR で作る。
- B1a（ルーティング）、B2a（録音と再生）、B4（VST3）、B5（MIDI と VSTi）は、この ADR の置き場所に従う。
- E1（`pa-engine` の組み立て）は、コントロールスレッドを JUCE のメッセージスレッドとして作る。
- 受け入れテストに、スキャン中に落ちるプラグインで本体が落ちないこと、録音中に書き込みを遅らせても音声が途切れないこと、子機の切断で音残りがないこと、を加える。
