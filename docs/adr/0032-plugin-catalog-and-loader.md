# 0032. プラグインの一覧のキャッシュ、読み込み不可の記録、読み込みと状態の保存のポート

- 状態: 採用（2026-11-09）

## コンテキスト

ADR-0009 で、VST3 のスキャンはファイルごとに別プロセスのヘルパー（`pa-plugin-scanner`）で行い、異常終了かタイムアウトのファイルを読み込み不可として以降のスキャンから外すこと、スキャン結果をパスと更新日時をキーに保存して変更のないファイルを再スキャンしないことを決めた。
プラグインの一覧と挿入の判断は `session`、スキャンと読み込みの実装は `plugin-host` に置き、`session` が `PluginLoader`、`PluginScanner`、`PluginEditorHost` のポートを定義する。
ADR-0024 では、グラフのプラグインノードと PDC を `audio-core` の `PluginProcessor` ポートで決めた。

この ADR では、ADR-0009 で B4 に残した次の点を決める。

- 変更の有無の判定に使う値と、読み込み不可の記録をいつ解除するか
- ヘルパーの制限時間の既定値
- 記録の保存先のポート
- スキャンの進め方（呼び出し側のスレッドを止めない方法）
- プラグインの記述の型をどのモジュールに置くか
- 読み込んだプラグインの状態の保存と復元の形

エディターのウィンドウ（`PluginEditorHost`）と、失敗をオペレーターに知らせる経路は、続く PR で決める。

## 決定

### 記録と再スキャンの判定

- ファイルごとの記録 `PluginScanRecord` は、ファイル（パス、更新日時、サイズ）、結果の区分（`kScanned`、`kCrashed`、`kTimedOut`、`kInvalidOutput`）、見つけたプラグインを持つ。
- パス、更新日時、サイズのすべてが記録と同じファイルは再スキャンしない。どれかが違えば再スキャンする。サイズを加えるのは、日時を保ったままのコピーで置き換えたファイルを見逃さないため。
- VST3 のバンドル（ディレクトリ）は、中の通常のファイルの最も新しい更新日時と、サイズの合計で判定する。更新でバンドルのディレクトリはそのままに、中のバイナリだけが入れ替わることがあるため。
- 読み込み不可の記録も同じ判定に従う。ファイルが変わらない限りスキャンせず、更新されたら（修正版に入れ替えられたら）もう一度スキャンする。
- 更新日時の値は実装（`std::filesystem::file_time_type` の刻み）に任せ、等しいかどうかだけを比べる。
- ヘルパーを起動できない（`kScannerUnavailable`）ときは、プラグインではなくインストールの問題なので、そのファイルを記録せずにスキャンを中断する。記録はそれまでのまま保存せず、次の起動でやり直す。
- 変更されたファイルの古い記録は、再スキャンを始めた時点で消す。古い記述でプラグインを読み込むと、中身と食い違うため。なくなったファイルの記録も消す。

### スキャンの進め方

- `session` の `PluginCatalog` が、`begin_rescan()` で対象のファイルを決め、`scan_next()` でファイル 1 つずつ進める。対象がなくなったら記録を保存する。
- ヘルパーの起動にはファイルごとに時間がかかり、まとめて行うと呼び出し側のスレッド（コントロールスレッド）を長く止めるので、呼び出し側が `scan_next()` を繰り返し呼ぶ形にする。どのスレッドで回すかは E1（`pa-engine` の組み立て）で決める。

### ヘルパーの制限時間

- 既定値は 30 秒（`plugin_host::kDefaultScanTimeout`）。大きなサンプルライブラリを持つ VSTi は初回のスキャンで 10 秒を超えることがあり、正常なプラグインを読み込み不可にしない余裕を取る。止まったプラグイン 1 つで一覧の用意を何分も待たせないよう、それ以上は延ばさない。
- ADR-0009 では実機で測って決めるとしていたが、手元に多くの市販プラグインを用意できていない。Beta4 の実機確認で、正常なプラグインのスキャンの最長時間を測り、30 秒に収まらなければこの値を見直す。

### 記録の保存先

- `session` に新しいポート `PluginCatalogStore`（`load()`、`save()`）を置き、`SettingsStore` とは分ける。
- 理由は次のとおり。
    - 記録はプラグインの数だけ大きくなり（シェルプラグインは 1 ファイルに数百）、スキャンのたびに書き換わる。設定は小さく、操作のたびに保存する。同じファイルにすると、設定の保存のたびに大きな記録も書き直すことになる。
    - 記録は壊れても再スキャンで作り直せるので、読めなければ記録なしとして続ける。設定は壊れたらバックアップから戻す（P1、ADR-0027）。壊れたときの扱いが違う。
    - P1（#55）の `SettingsStore` の形と独立に進められ、互いの PR が衝突しない。
- 実装は `persistence` が持つ（ファイルの形式もそちらで決める）。`SettingsError` は同じものを使う。

### プラグインの記述の型

- `PluginDescription` を `plugin-host` から `session`（`vocroz/session/plugin_description.h`）に移す。ポートのシグネチャはドメインの型だけを使い（AGENTS.md 5.1）、内側の `session` が外側の `plugin-host` の型を参照できないため。
- `plugin-host` には型の別名 `plugin_host::PluginDescription` を残し、スキャン結果のスキーマ（ADR-0009、AGENTS.md 4.4）とその利用側を変えずに済ませる。

### 読み込みと状態

- `PluginLoader::load()` は、`PluginInstance` を返す。`PluginInstance` は、グラフのノードに渡す `processor()`（`audio_core::PluginProcessor` の `shared_ptr`）と、状態の `save_state()`、`restore_state()` を持つ。処理と状態は同じプラグインのインスタンスで扱う必要があり、`audio-core` のポートに状態の保存を足すと、DSP と関係のない責務が `audio-core` に入るため。
- 状態はプラグイン独自の形式のバイト列で、`session` は中身を解釈しない。どの挿入の状態をいつ保存するか（セッションの保存、プリセット）は `session` が決める。
- プラグインが例外を送出したら `PluginStateError::kRejected` を返し、エンジンを落とさない。
- 実装は信頼済みインプロセス（`JuceVst3PluginLoader`）だけとし、アウトオブプロセス実行は同じポートの別の実装として加える（ADR-0009）。

## 理由

- 更新日時とサイズの組は、ファイルの中身のハッシュより安く求められ、再スキャンを避ける目的には十分。ハッシュは大きなバンドルで起動のたびに数百 MB を読むことになる。
- 読み込み不可をファイルの変更で解除すれば、オペレーターが記録を手で消さなくても、修正版に入れ替えるだけで使えるようになる。
- 型の別名を残すことで、スキーマとヘルパーのコードを変えずに `session` へ移せる。

## 結果

- `session` に `PluginCatalog`、`PluginDescription`、`PluginScanRecord`、ポート `PluginScanner`、`PluginCatalogStore`、`PluginLoader`（`PluginInstance`）が加わる。`session` は `audio-core` に依存する（AGENTS.md 4.2 で許可済み）。
- `plugin-host` に `make_helper_plugin_scanner()`、`make_vst3_plugin_loader()`、`kDefaultScanTimeout` が加わる。ファイルの列挙は JUCE を使わず、Linux の CI でもテストする。`make_vst3_plugin_processor()` は `make_vst3_plugin_loader()` に置き換える（利用側はまだない）。
- `persistence` は `PluginCatalogStore` を実装する必要がある。E1 は、`PluginCatalog` を回すスレッドと、読み込んだプラグインをグラフに渡す経路を組み立てる。
- 記録の手動の削除（読み込み不可の解除）と、探す場所の設定は、UI の作業と合わせて加える。
